# Codex GUI 分批代码质量评审设计

日期：2026-09-08

状态：设计已整理，八项实质决策已确认，待整体设计确认；尚未编写执行计划或开始正式评审。

## 目标

为 `codex-gui` 建立一套代码划分与分批质量评审方式，使每批能够在有限上下文内完成检查、保留可追溯证据，并最终汇总形成整体评审结论。

分批用于控制评审上下文和保证覆盖，不把目录边界视为行为边界，也不以文件大小直接判断代码质量。

## 已确认的决策

| 决策 | 已确认内容 |
| --- | --- |
| 质量范围 | 同时覆盖缺陷与可维护性，分开记录确定缺陷和结构改进建议。 |
| 修复时机 | 所有批次基于固定代码基线完成评审，统一汇总后再安排修复。 |
| 证据深度 | 静态评审结合相关现有测试的定向验证；不修改源码或测试。真实运行环境验证另行授权。 |
| 外部范围 | 以前端为评审对象，允许只读追踪直接相关的协议来源、GUI host 或 app-server 实现，不扩展为后端全面评审；不包含外部测试或运行操作。 |
| 推进方式 | 按确认后的方案连续推进，各批保留独立结果与续接记录；需要扩大范围或追加授权时暂停受影响部分。 |
| 无问题代码的记录 | 逐文件记录覆盖状态，按职责给出批次结论；不为每个无问题文件单独撰写分析。关键链路仍保留检查依据。 |
| 问题交接深度 | 附涉及模块、修正方向、必须保留的约束、验收条件和关联问题，不展开具体实现计划。 |
| 历史报告关系 | 独立评审当前基线。历史报告仅作线索，所有结论重新核实，不承诺逐项核对历史问题。 |

## 评审范围与基线

正式评审前记录基线提交、工作区状态及实际纳入评审的文件清单。存在未提交内容时，必须明确其是否属于快照并保留足以识别该快照的记录，不能仅用提交号代表实际内容。

各批评审及其测试证据必须对应同一基线。发现评审对象发生变化时，不将新旧证据混合汇总；先记录漂移与受影响范围，再恢复明确的基线条件。

前端实现、测试、公共设施、配置和工程脚本都需要覆盖归属。生成文件应关联权威来源与生成路径，区分生成契约检查和手写业务逻辑检查；不得因数量多而静默遗漏。最终文件范围和明确排除项在执行计划中依据实际清单确定。

外部代码只作为理解前端契约、调用链和行为的关联证据。前端消费的协议以权威定义及其机械生成产物为依据，不另建一套手写契约作为评审标准。

## 分区与实际批次

以下是职责分区，不是固定数量的执行批次，也不声称现有模块已严格分层。

| 职责分区 | 主要检查对象 |
| --- | --- |
| 应用入口与页面组织 | 应用启动、路由、页面装配、布局以及当前任务、新建会话、历史页面。 |
| 后端连接与协议边界 | 连接、认证、初始化、命令与通知、协议校验及权威生成来源。 |
| 会话管理与恢复 | 多会话生命周期、查看与激活、恢复与清理、浏览器持久化。 |
| 运行状态与对话数据 | 快照与增量接入、事件连续性、运行状态和对话记录维护。 |
| 输入与执行控制 | 草稿、技能选择、待发送队列、发送、追加指令与中断。 |
| 对话内容展示 | 消息与 Markdown、工具和子代理活动、分块展示与上下文分页。 |
| 公共设施与工程支撑 | 主题、国际化、错误反馈、通用工具、协议生成、测试基础设施和构建配置。 |

每个分区按完整职责进一步拆成实际批次。一个批次应包含其核心实现、必要的直接调用方及相关测试，避免仅因目录或行数切断关键行为链路。

每个范围内文件有一个主要覆盖归属，允许作为关联证据被其他批次读取。关联读取不自动等于完成该文件的主评审。跨批依赖和未闭合问题要显式交接。

## 统一检查标准

| 维度 | 关注点 |
| --- | --- |
| 行为正确性 | 真实入口与用户操作是否得到预期结果，边界条件是否改变行为。 |
| 状态与生命周期 | 状态归属、隔离、切换、清理、异步回调和持久化是否一致。 |
| 异常恢复 | 失败是否正确传播，重试、断线、交付未知和恢复是否保留原有约束。 |
| 契约与安全 | 权威来源、消费者、生成链和校验是否一致，输入与授权边界是否被正确处理。 |
| 性能 | 热路径、重复工作、渲染和数据增长是否存在有证据支持的风险。 |
| 职责与耦合 | 是否存在重复逻辑、多重权威来源、职责混杂或增加实际维护成本的接口复杂度。 |
| 测试有效性 | 现有测试是否覆盖关键行为与失败路径，断言是否能捕获相关回归。 |

不适用的维度说明原因。不能仅以文件大、代码多、命名偏好或个人风格提出结构问题；必须说明具体维护成本或行为影响。

## 证据与验证边界

静态证据包括实现、构造方、调用方、权威定义和测试内容。静态链路足以证明的问题可以确认，不强求所有问题都有运行复现；但阅读测试不能表述为测试已通过。

对影响结论的疑点运行相关现有测试，记录命令、环境、基线、实际命中的测试及结果。执行遵循当前项目工具链和授权限制，不安装依赖、不运行禁止的后端构建，不以放宽检查或改变测试来获得通过结果。

无法确认时记录具体复现条件、缺失证据和下一步验证要求。既有测试失败须区分与当前发现的关系，不能直接当作其根因证明。

真实运行环境验证不属于默认授权。适用时区分 Level 1 自动化回归、Level 2 无头真实运行验收与 Level 3 可见桌面验收；未执行的层级不由其他证据替代，也不因此阻止无依赖批次继续评审。

### 各批报告

各批报告记录职责边界、覆盖清单引用、检查维度及结论、关键链路依据、详细发现、验证结果和交接事项。

未发现问题的文件只在覆盖清单中记录状态，按职责汇总检查结论；关键链路即使未发现问题，也要说明检查依据。“未发现问题”仅表示在声明范围与证据下的结果，不代表不存在缺陷。

### 问题记录

每个问题使用稳定编号，至少包含：

- 分类：确定缺陷、待验证风险或可维护性建议。
- 标题、基线中的代码位置、证据及关联调用链。
- 触发条件与行为影响，或具体维护成本。
- 已确认根因，或尚未闭合的证据缺口。
- 优先级及其依据；证据充分程度与影响程度分开表达。
- 定向验证结果，或尚未执行的验证要求。
- 涉及模块、修正方向、必须保留的约束、验收条件和关联问题。

待验证风险不强行给出确定根因或整改结论。整改说明用于后续交接，不构成修复实现计划或修复授权。

每个问题正文只保留一个权威位置，其他批次和总报告通过编号及链接引用。去重时保留原编号的归并关系和各处证据，避免断开已建立的引用。

## 跨模块复核与全局汇总

局部批次完成后，专门检查发送到展示、会话切换与恢复、连接中断等完整链路。根据实际生产入口补齐相关链路，不能仅把批次报告拼接后宣布完成。

复核检查接口两侧假设、状态归属、生命周期、错误传播和验证覆盖是否一致。跨模块复核允许形成新的跨模块发现，并在该报告中保留完整证据；总报告引用其结论。

全局汇总合并同一根因的问题，保留独立影响与关联证据，分别呈现确定缺陷、待验证风险和可维护性建议。统一优先级服务于后续修复排序，不在本次执行修复。

## 连续推进与完成条件

执行方案确认后按批连续推进，无需逐批人工审批。每批结束更新结果与进度，记录已完成检查、待闭合问题及下一步位置，以支持跨会话续接。未完成批次不能仅凭文件已创建标为完成。

需要扩大范围或追加授权时，仅暂停受影响部分，继续其他无依赖工作。

整体评审完成须同时满足：

- 范围内文件均有覆盖归属，已完成相应检查，或具有明确排除理由。
- 所有批次和跨模块复核均有报告与实际检查依据。
- 跨批问题已确认、排除、归并，或明确列为待验证项并说明证据缺口，不能无记录悬置。
- 所有验证结果可追溯到固定基线，未执行和不适用项明确区分。
- 总报告完成去重、分类、优先级收敛和索引核对。

评审完成可以包含明确的待验证风险，不等同于产品完全验证通过或所有问题已解决。
