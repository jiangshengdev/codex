# 执行图没有形成有效并行

日期: 2026-08-24
状态: 🔴 仍需处理
范围: 多代理执行图、ready set、资源锁与关键路径调度
优先级: P2

## 摘要

多代理调用增加了并发数量，但任务没有稳定按真实依赖、读写集合和资源锁调度，因此没有持续缩短关键路径。

## 问题

当前执行流程曾把微阶段拆分误解为逐节点串行等待：独立的读取、解析和验证被逐文件执行，多个代理集中审查同一份 diff，而真正可独立推进的节点仍被无依据延后。

是否能够并行没有由当前 ready set 决定，Git index 等短时独占资源也被错误扩大为整个工作流的串行约束。结果是子代理更像需要主代理逐次驱动的远程命令执行器，而不是持续消费可执行节点的 worker。

## 证据

- 月度审计保守确认“子代理权限和调度不受控”至少涉及 5 条任务链。
- 处理 9 个生成物时，7 个彼此独立的文本验证被逐文件串行处理，形成接近 18 次往返：`/Users/jiangsheng/.codex/sessions/2026/08/20/rollout-2026-08-20T07-16-02-01a01c4f-6b8a-73f2-bd2c-954dad1618e2.jsonl` 第 1171–1212 行。
- 一个写集合与接口语义均独立的 Task 4，仍等待前三个任务全部提交后才启动，被无依据延后约 2 小时：rollout `01a02d92…` 第 232–243 行。
- 多个代理曾集中审查同一份 diff，没有形成关键路径上的有效 fan-out。
- 月度审计据此判断：“调用了很多子代理”不等于“有效并行”；并发必须由依赖、读写集合和资源锁决定。

## 判断

问题仍然成立。现有流程能够创建多个子代理，但缺少稳定的全局执行图和动态调度状态，因而会同时出现过度串行、重复审查和资源锁范围过大的情况。

## 影响

- 独立任务被不必要地阻塞，增加端到端完成时间和对话往返。
- 微阶段越细，若没有执行图，调度开销反而越大。
- 主代理上下文被大量节点级状态占用，更容易发生压缩和重复调查。
- 共享 Git index 等局部资源冲突会被误判为整个任务不可并行。

## 后续处理

需要单独进入设计阶段，明确以任务节点的真实依赖、读写集合、执行上下文和资源锁计算 ready set，并定义 worker 持续取任务、短时独占写入和最终 fan-in 审计的调度语义；不能把固定批次或固定子代理数量当作并行模型。
