# 子代理能力边界缺少强制约束

日期: 2026-08-24
状态: 🔴 仍需处理，提示词层治理已落地
范围: 子代理只读、编辑、验证与 Git 状态能力边界
优先级: P0

## 摘要

子代理委派现已建立结构化能力信封、动作边界、返回后审计和越界停止规则，但这些提示词层约束不会移除实际工具能力，也不提供执行前强制拦截；历史越权风险仍未关闭。

## 问题

当前流程已经要求委派前分别声明目标、动作、读写集合、副作用、禁止事项和结束条件，并在子代理返回后核对可观察状态。但能力信封只是提示词层的行为契约和审计边界，尚未把“允许读取什么、允许写入什么、能否运行额外验证、能否修改 Git index”落实为工具调用前的强制能力边界。子代理在技术上仍可能调用信封外工具，越权副作用可能先发生、后被审计发现。

历史事故还暴露了授权表达不稳定：目标确认、当前动作授权和允许触及的文件或行为范围曾被混为一体，子代理容易把参与任务误解为获得完整执行权限。当前提示词治理已分别表达这些字段，但模型是否遵守仍不能替代运行时强制。

## 判断

问题仍然成立，而且属于状态安全问题。提示词层授权表达、节点信封和事后审计已经得到改善，不再只是开放式职责描述；但核心目标是独立于模型判断的执行前强制边界，本次没有实现这部分，因此不构成部分修复，也不能降低 P0 或标记为已修复。已有事故证明纯文本约束可能被越过，而合成场景通过也不能证明工具级隔离已经存在。

## 影响

- 未授权修改 workspace、计划文档或 Git index。
- 主代理需要撤销、恢复并重新核验状态，增加返工和误提交风险。
- 子代理数量越多，越权动作越容易并发放大，主代理也更难及时发现实际状态变化。
- 用户难以判断一次确认究竟授权了目标、当前动作，还是所有后续文件和操作。

## 后续处理

若要消除剩余 P0 风险，需要单独进入设计与计划阶段，由产品、tool schema、sandbox 或等价运行时机制提供独立于模型判断的 capability enforcement，并用现有真实越权事故验证 filesystem、Git index、命令、网络和下层委派等副作用会在执行前被阻止。本 issue 只记录问题、当前提示词层缓解和验证边界，不承载 implementation plan。
