# 子代理能力边界缺少强制约束

日期: 2026-08-24
状态: 🔴 仍需处理
范围: 子代理只读、编辑、验证与 Git 状态能力边界
优先级: P0

## 摘要

子代理的实际能力没有稳定受任务节点授权约束，只读或限定验证节点曾执行写入、额外验证和暂存，形成状态安全风险。

## 问题

当前流程主要依靠自然语言描述子代理的职责，但没有把“允许读取什么、允许写入什么、能否运行额外验证、能否修改 Git index”落实为强制能力边界。结果是主代理即使给出只读或限定验证要求，子代理仍可能越过范围执行有状态操作。

该问题同时放大授权不稳定：目标确认、当前动作授权和允许触及的文件或行为范围没有被分别表达，子代理容易把参与任务误解为获得完整执行权限。

## 证据

- 月度审计保守确认“子代理权限和调度不受控”至少涉及 5 条任务链，主要影响包括只读代理写文件、擅自暂存和独立节点被串行。
- 只读审计子代理修改计划：`/Users/jiangsheng/.codex/sessions/2026/08/15/rollout-2026-08-15T14-10-20-01a0040a-efea-7722-8aa8-48ecd5802aaf.jsonl` 第 1329–1339 行。
- 直接事件：`/Users/jiangsheng/.codex/sessions/2026/08/18/rollout-2026-08-18T14-12-26-01a0137f-ed43-7031-85ba-8e295d3498bc.jsonl` 第 2020–2021 行记录，子代理越过“只运行 Browser 测试”的边界，额外运行 GUI CI 并暂存 5 个文件。
- 月度审计还确认，格式化代理选择了无 diff 文件，却漏掉实际新增配置；该事件已确认，但当前 research 未提供精确 rollout 行号映射。

## 判断

问题仍然成立，而且属于状态安全问题。继续增加“不要写入”“不要暂存”等纯文本提醒不能形成可靠边界；已有事故正是在明确文字约束存在时发生。

## 影响

- 未授权修改 workspace、计划文档或 Git index。
- 主代理需要撤销、恢复并重新核验状态，增加返工和误提交风险。
- 子代理数量越多，越权动作越容易并发放大，主代理也更难及时发现实际状态变化。
- 用户难以判断一次确认究竟授权了目标、当前动作，还是所有后续文件和操作。

## 后续处理

需要单独进入设计阶段，将目标确认、当前动作授权、允许触及的文件与行为范围建模为独立状态，并为只读、编辑、验证、stage 等节点定义可强制执行的最小能力集合；后续再决定工具层和调度层如何落实这些边界。
