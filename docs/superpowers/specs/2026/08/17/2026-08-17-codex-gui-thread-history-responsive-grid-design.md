## 唯一主目标

把现有历史任务列表改为适配手机和 PC 的响应式网格，控制超长标题与摘要的视觉溢出，并在
标题与摘要去除首尾空白后完全相同时不重复显示摘要。

本设计只调整历史列表的呈现方式，不改变历史数据、分页、状态、路由或只读查看语义。

## 与旧设计的关系

本设计是 2026-08-16 历史任务列表设计的定向补充，不替换旧设计。旧设计已经确认并实现的以下
语义继续有效：

- 历史记录仅展示当前工作目录下的未归档任务，并按现有 cursor 流程加载；
- 每条任务继续使用 HeroUI v3 `Card`，展示标题、可选摘要、最近活动时间和状态 `Chip`；
- `Card.Footer` 继续提供明确的“查看”按钮，不把整张非交互 Card 伪装成链接；
- “查看”继续进入只读历史详情，不恢复任务、不挂载 Composer；
- 路由导航继续保留 `search: true`，从而保留启动查询参数；
- 追加分页、错误显示以及列表与详情之间的导航行为保持不变。

旧设计中“`name` 与 `preview` 均非空时展示摘要”的规则由本设计收紧：两者 `trim()` 后完全相同
时隐藏摘要；只要不是完全相同，即使部分相似，也仍保留摘要。

## 当前实现与问题证据

### 当前列表被限制为单列窄内容区

`ThreadHistoryListPage` 的 `main` 当前使用 `max-w-3xl`，列表 `section` 只有未声明列数的 `grid`，
因此手机和 PC 都按单列展示：

- `codex-gui/src/features/threadHistory/ThreadHistoryListPage.tsx:22`
- `codex-gui/src/features/threadHistory/ThreadHistoryListPage.tsx:98-114`

这使宽屏 PC 不能利用可用宽度展示更多任务，同时把大量历史条目压成长列表。

### 当前摘要会与标题精确重复

Card 当前先对 `thread.name` 和 `thread.preview` 执行 `trim()`，但只要两者都非空便直接把
`preview` 作为摘要，没有比较两者是否相同：

- `codex-gui/src/features/threadHistory/ThreadHistoryListPage.tsx:121-124`
- `codex-gui/src/features/threadHistory/ThreadHistoryListPage.tsx:133-157`

因此 `name` 与 `preview` 内容相同的任务会连续显示两次同一文本。

### 连续长文本会撑宽网格轨道

在 2026-08-17 的可见浏览器实测中，历史列表 `main` 的预期内容宽度为 768px，但包含长 URL、
Markdown 或无空格连续文本的 Card 将网格轨道撑至约 1314px，页面 `scrollWidth` 达到 1425px。
这不是单纯的视觉截断缺失：不可收缩的网格子项已经破坏主内容宽度并产生横向滚动。

因此实现必须同时处理网格轨道可收缩、Card 子元素的最小宽度和文本断行；只给文本加省略号而
不消除轨道的 intrinsic minimum，不能解决根因。

## 已确认设计

### 响应式列数与页面宽度

历史列表使用响应式网格：

- 手机：1 列；
- 中等屏幕：2 列；
- 宽屏 PC：3 列。

列宽必须允许内容收缩到网格分配宽度，任何 Card、Header、Content、Footer 或文本节点都不得以
min-content 宽度把轨道撑开。列表页面本身不得产生横向滚动。

只在历史列表路由扩大主内容区，并让该路由下顶栏的内部内容宽度与网格外沿对齐。当前任务页、
历史详情页及其他页面继续使用各自现有内容宽度，不随本设计加宽。顶栏本身仍然横跨视口，变化的
只是历史列表路由下的内部对齐范围。

具体响应式断点、最大容器宽度和 gap 数值属于实现细节，应使用项目现有 Tailwind 响应式能力和
语义 spacing token，不在设计或测试中固化主观数值。无论选用何种具体数值，实测结果必须满足
上述 1/2/3 列拓扑。

### Card 结构与同行整齐度

继续使用 HeroUI v3 `Card variant="default"` 及其 compound components：

- `Card.Header` 承载标题和可选摘要；
- `Card.Content` 承载最近活动时间与状态；
- `Card.Footer` 承载明确的“查看”按钮；
- `Card` 保持 `role="article"`，并由完整标题提供 accessible name。

同一网格行内的 Card 外框保持等高，Footer 操作区对齐；内容较短的 Card 不因填充高度而改变信息
顺序，内容较长的 Card 也不得扩大该行之外的视觉密度。加载更多和追加错误不是历史条目，必须
跨越完整网格宽度，不能占用单个 Card 的一列。初始加载、初始错误和空状态仍作为页面级反馈。

网格容器使用语义化 `section` 配合 Tailwind 布局类，不引入新的 layout component、依赖、图像或
装饰资源。

### 标题、摘要与超长文本

标题最多显示 2 行，摘要最多显示 3 行。视觉上的超出部分使用 CSS 行截断处理，但完整字符串仍
保留在 DOM 中，并继续参与 Card 的 accessible name 或可访问描述；不得为了视觉截断而在
JavaScript 中裁剪、改写或丢弃原始文本。

标题和摘要都必须：

- 能在网格分配宽度内收缩；
- 对长 URL、Markdown、路径、token-like 字符串和其他无空格连续文本进行安全断行；
- 在达到 2 行或 3 行视觉上限后省略；
- 不撑宽 Card、网格、页面或视口；
- 不引入横向滚动条。

标题回退顺序保持为 `trim(name) || trim(preview) || 本地化默认标题`。

摘要使用以下唯一规则：

1. 分别计算 `trim(name)` 与 `trim(preview)`；
2. 任一为空时不展示摘要；
3. 两者完全相同时不展示摘要；
4. 两者不完全相同时展示完整的 `trim(preview)`，即使摘要以标题开头或与标题部分相似也不删除
   前缀。

该规则不做大小写折叠、标点归一化、Markdown 解析、Unicode 模糊匹配或语义相似度判断，避免
误删有意义的补充内容。

### HeroUI v3 与视觉语义

现有组件和语义 variant 保持不变：

- 历史条目使用 `Card variant="default"`；
- 普通状态使用 `Chip variant="soft"` 与默认语义色；
- `systemError` 使用同一 `soft` variant 的 danger 语义色；
- “查看”和“加载更多”继续使用 `Button variant="secondary"`；
- 加载错误继续使用语义化 danger `Alert`。

布局与文本样式使用 HeroUI/Tailwind 已有语义 token，例如前景、muted、边框、圆角和 spacing；
不得新增硬编码颜色来表达状态，也不得为响应式网格引入另一套 Card 视觉语言。

## 保持不变

- `thread/list` 请求参数、cursor、去重、首次加载和追加加载所有权；
- 状态 `Chip` 的四种协议状态映射；
- 最近活动时间的 `recencyAt ?? updatedAt` 回退；
- 明确的“查看”按钮及其 `search: true` 导航；
- “加载更多”的 pending、防重复请求和末页隐藏行为；
- 初始错误、追加错误、重试与空状态；
- 详情页只读边界、详情加载和返回语义；
- 当前任务的 live projection、Composer queue 与恢复任务流程；
- 现有本地化文案和可访问焦点语义。

## 非目标

- 不修改 app-server 协议、生成类型或历史 owner 状态模型；
- 不增加搜索、过滤、排序控制、虚拟列表、网络分页策略或持久化缓存；
- 不让 Card 整体可点击，不删除“查看”按钮；
- 不重新设计历史详情页、当前任务页或 Drawer；
- 不新增展开全文、tooltip、modal、复制按钮或 hover-only 交互；
- 不把响应式断点解释为特定手机或 PC 设备型号；
- 不新增依赖、字体、图标、插图或其他图像资产；
- 不以隐藏 overflow、缩小字体或移除文本作为横向滚动问题的替代修复。

## 预计影响边界

实现预计只触及历史列表的页面与 Card 渲染，以及承载顶栏内部宽度的现有布局 seam：

- 历史列表网格列数、跨列反馈区和 Card 等高布局；
- 标题/摘要去重与视觉行截断；
- 历史列表路由专属的内容宽度和顶栏内部对齐；
- 与上述稳定行为直接对应的组件测试或浏览器验证。

若实现需要修改协议、history owner、历史详情、当前任务布局、路由查询语义或其他计划外文件，说明
设计边界判断错误，必须暂停并重新确认范围，不能借“响应式适配”扩大改动。

## 验证设计

### 自动化验证

组件级或浏览器级验证应覆盖稳定、用户可感知的行为：

- 在代表手机、中等屏幕和宽屏 PC 的视口范围分别形成 1、2、3 列；
- 长 URL 和无空格连续文本不会让页面 `scrollWidth` 超过视口或内容容器；
- 标题具有 2 行视觉上限，摘要具有 3 行视觉上限，同时原始完整文本仍存在于 DOM 和可访问名称
  或描述中；
- `trim(name) === trim(preview)` 时不渲染重复摘要；
- 部分相似但不完全相同的摘要仍完整渲染；
- “查看”仍导航到对应历史详情并保留现有 search；
- “加载更多”和追加错误跨越整个网格；
- 状态、时间和按钮仍可被其现有 accessible name 定位。

测试断言应面向列拓扑、可收缩性、横向溢出、文本存在性、去重与导航结果，不断言具体 gap、
padding、颜色、阴影、圆角或单个断点像素值。

### 可见浏览器验证

使用可见的 Google Chrome for Testing 检查至少三类视口范围：手机、普通 PC、宽屏 PC。每类都
验证列数、Card 同行整齐度、顶栏与历史网格对齐、页面无横向滚动，并用包含长 URL、长 Markdown
和精确重复标题摘要的真实历史记录检查截断与去重。

响应式验证只确认实际 metrics 与布局结果，不宣称或锁定特定设备型号。

## 验收条件

1. 手机显示 1 列，中等屏幕显示 2 列，宽屏 PC 显示 3 列。
2. 历史列表使用更宽的路由专属内容区，顶栏内部与其对齐；其他页面宽度不变。
3. 标题视觉上最多 2 行，摘要视觉上最多 3 行，完整文本仍可访问。
4. 长 URL 和连续长文本不能撑宽网格，历史列表页面不产生横向滚动。
5. `name` 与 `preview` 分别 `trim()` 后完全相同时只显示一次；部分相似时仍显示摘要。
6. 同一网格行 Card 整齐，“加载更多”和追加错误跨完整网格。
7. Card、状态、时间、“查看”、`search: true`、分页、错误和只读导航语义保持不变。
8. 未增加依赖、图像资产、协议改动或范围外页面改造。

## 否决条件

出现以下任一情况，方案不得验收：

- 只用 `overflow: hidden` 掩盖页面横向滚动，未消除网格轨道或子元素不可收缩的根因；
- 通过 JavaScript 截断字符串，导致 DOM 或 accessible name 中丢失完整文本；
- 把 Card 整体改为点击区域、删除明确的“查看”按钮，或移除 `search: true`；
- 用“包含标题”“忽略大小写”或语义相似度代替已确认的 `trim()` 后精确相等规则；
- 为了三列网格同时加宽当前任务页或历史详情页；
- 让加载更多或追加错误只占单列，破坏网格信息层级；
- 固化特定设备型号或主观 gap、颜色、阴影数值作为产品约束；
- 新增依赖、图片、协议字段、缓存、虚拟化或其他未确认功能；
- 通过删除内容、缩小字体、放宽验证或新增 overflow 豁免来隐藏问题。
