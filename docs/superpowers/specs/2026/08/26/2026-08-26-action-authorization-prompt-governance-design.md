## 唯一主目标

为本机所有 Codex 使用入口建立一致的提示词层动作授权治理，使 GUI、CLI、TUI、普通执行和子代理都按同一组授权公理解释用户请求，并把阶段、动作族、目标范围、附带副作用和特殊确认分开管理，降低越权执行与重复设门两类误判。

本设计只定义提示词与 skill 的责任分层、授权语义、授权记录、能力信封、生命周期和验收分类。它不是 implementation plan，不定义任务顺序、执行图、提交拆分或实施命令，也不授权修改任何提示词、skill 或产品代码。

## 保证边界

本方案是提示词层治理，只能降低模型误读、错误继承和错误扩张授权的概率。它不能提供工具调用前的强制能力检查，不能在运行时隔离文件系统、Git index、网络或子代理能力，也不能证明所有未来模型都严格遵守自然语言约束。

因此，本设计完成以及后续提示词和 skill 实施完成，都不足以关闭关联 P0 issue。只有未来存在独立于模型判断的结构化授权状态与工具级执行约束，并用真实事故场景验证其强制性后，才可重新判断该 issue 是否满足关闭条件。

## 已确认的设计决策

### 覆盖所有本机 Codex 入口

治理语义适用于本机 GUI、CLI、TUI、普通主代理执行和子代理执行，不以某个前端、某种协作模式或某个模型为唯一入口。不同入口可以有各自的展示和上下文拼装方式，但不能定义互相冲突的动作授权语义。

### 全局用户指令保持简洁

本机实际生效的全局用户指令是 `codex-config/AGENTS.md`，并通过 `~/.codex/AGENTS.md` 指向它。仅就本次动作授权治理涉及的规则而言，该文件只保留三类必须在 skill 触发前生效的内容：

- 少量、稳定、跨任务成立的动作授权公理；
- `~/.codex/AGENTS.md` 受保护文件的专门确认门禁；
- 把动作授权判断路由到中央 `action-authorization` skill 的短规则。

动作族词表、继承矩阵、生命周期、例外、事故案例和完成前检查不继续堆叠在全局用户指令中。动作授权部分只负责建立最小语义和触发中央 skill，不承担详细流程手册。所有不属于本次动作授权治理的其他全局规则均保持原有内容和职责；本设计不授权也不要求对整个 `codex-config/AGENTS.md` 做通用精简、迁移或重写。

### 不修改无关提示词入口

本轮治理不修改 upstream base instructions、Default collaboration prompt 或 `codex-gui/AGENTS.md`。

- upstream base instructions 是上游通用模型行为，不作为本机授权语义的定制载体；
- Default collaboration prompt 只定义协作模式，不成为动作授权的第二权威来源；
- `codex-gui/AGENTS.md` 只保留前端工程约束，不承载跨 GUI、CLI、TUI 的通用授权规则。

`codex-config/AGENTS.md` 和中央 skill 都以 user role 进入模型上下文，不能覆盖与之冲突的 system、developer、tool 或 safety 规则。本设计只能在不与这些更高层规则冲突时补充本机动作授权语义。若实施前发现高层规则与本设计存在真实冲突，必须停止受影响部分、报告精确冲突及影响，并另行设计处理，不能宣称由本机规则将其“收紧”或覆盖。首轮也不通过复制同一套规则到多个提示词来追求一致性。

### 新建中央自动发现 skill

在手工维护 skill 的正确位置新建 `codex-config/skills/action-authorization/`，作为动作授权语义的中央 owner。它必须能被自动发现，并通过准确、覆盖面足够但不过度触发的 metadata 描述，使涉及动作解释、有状态操作、范围变化、特殊确认或子代理授权的任务能够加载它。

中央 skill 的主 `SKILL.md` 保存核心判断流程和 reference 路由；详细内容可以放入 `references/` 渐进披露。渐进披露只减少无关上下文，不允许把决定当前动作能否执行的关键规则藏到永不触发的 reference 中。

建议的详细语义分区包括动作族与固有步骤、授权记录与生命周期、canonical target 与特殊确认、子代理能力信封以及事故验收案例。具体文件拆分属于后续实现机制，不在本设计中固定为实施任务。

### 阶段 skill 消费中央授权

`managing-work-stages` 继续只管理调查、设计、计划、实现、文档落盘和已定义阶段例外。它不再自行维护一套平行的通用动作授权模型，而是消费中央 `action-authorization` skill 给出的当前动作族、授权范围和重新确认结论。

阶段确认只确认该阶段明确包含的行为。设计目标确认不自动授权落盘、计划或实现；计划确认只授权计划中明确声明的动作和固有步骤；阶段推进不能替代特殊目标的专门确认。中央授权语义决定“现在允许做什么”，阶段 skill 决定“当前流程处于哪里”，两者不能合并成单一门禁。

### 子代理采用最小能力信封

`delegating-micro-stages` 与其 execution-graph reference 增加最小能力信封。每个子代理或执行节点的有效授权是父级当前有效授权与该节点显式授权的交集，不是父级能力的完整复制。

能力信封中未列出的动作、目标、写入、副作用、验证、Git 操作或外部影响默认不授予。子代理发现需要额外能力时，只能返回所缺能力和受影响后继；不得先执行再补记，也不得把“完成任务所需”解释为开放式授权。

## 授权公理

### 目标、阶段、动作和范围彼此独立

用户想达成的目标、当前讨论或阶段、此刻允许执行的动作、允许触及的目标以及允许产生的副作用必须分别解释。确认其中一项不能自动确认其他项。

用户对事实、方案或结果的评论，包括批评、纠正、追问、催促和要求说明，不构成新的有状态动作授权。只有直接表达要执行某项动作的指令，或已确认设计/计划中精确包含的动作，才能形成对应授权。

### 授权不能跨动作族推导

修复、提交、监控等动作族相互分离。某一动作族可以包含完成该动作不可缺少且边界清楚的固有步骤，但不能据此获得另一个动作族的权限。

- 修复可以包含定位当前目标、修改明确范围、执行与本次修改直接相关的有界验证，以及闭环本次修改直接引入且仍在原范围内的问题；它不推出 stage、commit、远程操作、持续监控或修复无关问题。
- 提交可以包含只读检查现有变更、只暂存明确范围以及创建本地提交；它不推出编辑、修复、生成新变更、扩大验证或远程操作。
- 监控可以包含按约定读取状态、等待、轮询和报告变化；它不推出重试、修改、推送、合并或处理新发现的问题，除非用户另行授权或动作专用 skill 已获得对应明确授权。
- 调研、分析、诊断、审计和解释只包含只读事实核验与汇报；它们不推出实现、格式化、生成、stage 或 commit。

用户的直接限制可以继续缩小固有步骤。例如“修复但不要验证”会移除修复族中的验证能力；“只提交这个文件”会把提交族的 target set 收窄到该文件。固有步骤不是绕过负面约束的理由。

### 授权只覆盖明确目标和副作用

授权必须同时匹配动作族、目标集合和允许副作用。编辑一个文件不授权修改其相邻文件；验证不授权接受快照、更新基线或自动修复；读取符号链接不授权改写其实际目标；修改代码不授权新增文档或关闭 issue。

低层工具动作只有在它们表达已授权动作且没有扩大目标或副作用时才被覆盖。工具可用、项目惯例、历史计划、skill 建议和“通常需要”都不能单独产生授权。

### 当前直接授权不被旧计划遮蔽

新的用户直接指令只覆盖与其冲突或重叠的旧授权字段。它可以新增、缩小、替换或撤销当前局部动作，但不会无依据地使整份既有计划失效，也不会要求用户重新确认没有变化的其他范围。

旧计划不得否定用户刚刚明确授予的局部动作。若新指令与旧计划能够同时成立，则合并为当前授权记录；若只有局部冲突，则仅替换冲突部分；若实质目标、接口、数据、安全或高风险边界发生冲突，则暂停相关动作并请求用户决定。

### 只暂停受影响动作

授权缺失、目标不明、特殊确认不足或范围扩大只暂停依赖该能力的动作及其后继。无依赖、仍在有效授权内的只读调查、独立分支或其他节点可以继续。不得把一个节点的授权问题升级为无证据的全局停工，也不得借其他节点仍可执行来绕过受影响动作的门禁。

## 授权记录模型

每项当前有效授权在设计语义上至少包含以下字段：

- `source`：用户对目标和动作的哪一条直接请求，或用户对已经明确展示的设计、计划、特殊操作所作的哪次有效确认；system、developer、tool 和 safety 规则不能作为用户语义授权的来源；
- `governingConstraints`：system、developer、tool、safety 以及其他适用规则对已获用户授权动作施加的限制、禁止条件或执行方式；这些约束可以收窄或阻止执行，但不能代替用户产生目标或动作请求；
- `objective`：该授权服务的已确认目标；
- `phase`：调查、设计、计划、实现或不进入阶段流程的直接动作；
- `actionFamily`：调研、修复、验证、文档写入、提交、监控、委派或其他明确动作族；
- `allowedOperations`：该动作族内被允许的具体操作和固有步骤；
- `targets`：允许读取、写入或操作的逻辑目标集合；
- `canonicalTargets`：解析路径别名、符号链接和底层资源身份后的目标集合；
- `sideEffects`：允许的生成、格式化、测试状态、Git index、本地提交、外部通信等副作用；
- `negativeConstraints`：用户明确排除的动作、目标、验证和副作用；
- `specialApprovals`：只能由目标专属确认满足的受保护操作；
- `delegation`：是否允许委派，以及可传给子代理的最大能力信封；
- `lifecycle`：授权的生效、消费、覆盖、撤销和终止状态。

实现可以使用自然语言结构、内部表格或其他等价表示，但不得删除这些语义维度后又依赖模型临场猜测。

## 覆盖、撤销与生命周期

授权从明确指令或有效确认产生，在对应任务、阶段或动作完成前保持有效，除非用户撤销、后续指令覆盖、前提失效或安全边界要求重新确认。

覆盖按字段和目标相交范围处理：

- 后续指令明确替换同一动作和目标时，新授权覆盖旧授权；
- 后续指令只增加独立动作时，两项授权并存；
- 后续指令缩小范围或加入负面约束时，立即收窄尚未执行的相关动作；
- 后续指令撤销动作时，停止该动作及其后继，但保留不依赖它的有效授权；
- 新事实导致目标身份、风险、接口、数据或安全语义变化时，相关授权进入待重新确认状态。

一次性动作在成功完成后被消费；持续监控授权在用户指定终止条件、任务关闭或用户停止时结束；计划节点授权在节点完成、被替换或计划取消时结束；子代理能力在该微阶段结束时到期，不保留到后续新任务。

“继续”“确认”“看着办”等回复只能满足当前明确展示且正在等待的确认点，不能被重放到其他目标、其他动作族或其他特殊确认上。若对话中不存在唯一等待确认点，这些表达不能凭空产生新的动作授权。

## Canonical target 与特殊确认

目标匹配必须同时保留用户可见路径和 canonical 底层资源身份。路径别名、符号链接、相对路径、直接链接目标和 fully resolved physical target 指向同一资源时，不能被当作不同资源规避读写范围、资源锁或受保护文件门禁。

canonical target 用于识别实际影响面，不用于扩大授权。用户只授权逻辑路径时，发现它解析到未获授权或受保护的底层资源必须暂停相关动作并披露映射；不得因为两个路径最终相同，就把对其中一个表示的授权自动扩张成对所有表示的授权。

`~/.codex/AGENTS.md` 的修改继续需要面向该受保护文件的单独明确确认。设计确认、计划确认、其他文件写入确认、一般性的“继续”、通过符号链接修改实际目标，或对子代理的普通写入授权，都不能替代这一 special approval。实施本设计前仍必须再次取得该专门写入确认；本设计的确认本身不满足该门禁。

## 中央 skill 的职责边界

`action-authorization` 是以下语义的唯一详细 owner：

- 从用户当前请求与已确认上下文识别动作族；
- 建立并更新授权记录；
- 应用负面约束、动作族固有步骤和跨族禁止推导规则；
- 处理当前直接授权与旧计划的局部覆盖；
- 解析 canonical target 并检查 special approval；
- 为主代理和子代理计算有效能力信封；
- 在授权不足时指出精确缺口和受影响动作；
- 根据动作族路由到阶段或动作专用 skill。

中央 skill 不接管项目工具链、文档目录、Git 回退、worktree 创建、PR 监控、冲突解决或具体测试入口。它只回答这些专用流程当前获得了哪些动作、目标和副作用权限；专用 skill 继续负责自己的领域流程。

## 与阶段和委派 skill 的契约

### `managing-work-stages`

阶段 skill 读取中央授权结论，并负责：

- 设计主目标以及设计、计划、实现之间的阶段门禁；
- 调研和 BUG 首轮的只读阶段语义；
- 文档落盘、已有变更提交等已经定义的阶段例外；
- 实质范围或产品语义变化时回到对应确认点。

它不重复定义动作族、canonical target、special approval 或子代理能力继承。阶段确认准备进入下一阶段时，必须把该阶段实际包含的动作交给中央授权判断，而不是用“阶段已确认”概括所有能力。

### `delegating-micro-stages`

委派 skill 在创建子代理前构造最小能力信封，至少声明：

- 单一预期结果；
- 允许的动作族与具体操作；
- read set、write set 和 canonical targets；
- 允许的验证、格式化、生成和外部副作用；
- 是否允许操作 Git index、stage、commit 或继续委派；
- 必须返回而不能自行处理的范围扩大条件；
- 能力到期条件。

有效子代理能力按父授权与节点声明逐字段取交集。父级没有的能力不能下发；节点未列出的能力默认拒绝；special approval 只有在原确认明确允许该目标由该节点操作时才可进入交集。

### Execution graph reference

执行图中的 `authorizationGate` 不再只记录“已确认/未确认”，而要引用或内联最小能力信封。节点进入 ready set 之前，授权门禁必须证明动作族、目标、canonical target、副作用和 special approval 均满足。节点实际访问超出信封时，只暂停该节点及其依赖后继并触发重编图。

## 首轮实施边界

首轮只覆盖通用授权链：

- 简化本机全局用户指令中的动作授权规则；
- 建立中央 `action-authorization` skill 及必要 references；
- 让 `managing-work-stages` 消费中央授权；
- 让 `delegating-micro-stages` 和 execution-graph reference 使用最小能力信封。

首轮不修改 worktree、revert、PR、merge/rebase conflict 等动作专用 skills。它们继续执行当前领域流程，但受全局授权公理与中央 skill 的动作、目标和副作用边界约束。只有后续独立任务用证据发现某个专用 skill 存在真实冲突时，才单独设计其适配；不得在首轮顺手统一重写。

## 七类事故验收分类

以下分类是设计验收边界，不是实施任务清单。后续实现必须能对每类输入给出稳定、可解释且不扩大授权的结果。

### 排除范围反转

输入包含“不要处理 X”“只管 Y”等负面约束时，`X` 必须进入 `negativeConstraints`，不得被解释成待处理目标。只有 `Y` 及其有界固有步骤可获得授权。

### 分析升级为实施

调研、分析、诊断、审计、解释或报告只产生只读能力。即使已经得出明确修复方案，也必须等待用户另行发起修复，除非此前已有仍有效的实施授权。

### 批评被当作授权

用户批评方案、指出错误、要求重新说明或表达不满，只更新事实、约束或待决策内容，不产生编辑、修复、委派或验证授权。

### 只读子代理写入

父级只读授权与节点只读信封取交集后，子代理没有 write、format、generate、stage 或 commit 能力。即使子代理认为修改很小或有助于完成调查，也必须返回建议而不是写入。

### 限定任务附带动作扩张

只获准执行某一限定任务的节点，不得额外运行 GUI CI、扩大验证、修改其他文件或暂存结果。固有步骤必须来自该动作族并受明确目标和副作用边界约束。

### Symlink 受保护资源绕过

任何路径解析到 `~/.codex/AGENTS.md` 的实际目标时，都必须识别为同一 canonical protected target。没有该文件的专门写入确认时，直接路径、符号链接路径和实际目标路径均不得写入。

### 当前局部授权被旧计划遮蔽

用户明确授权一个当前局部动作时，只更新对应授权字段。旧计划不能要求重复确认没有变化的全部内容，也不能被无依据地宣布整体作废；只有真实冲突或范围变化的部分进入重新确认。

## 一致性与验收不变量

- GUI、CLI、TUI、普通执行与子代理对同一请求得到相同的动作族和授权边界。
- 全局用户指令中与本次动作授权治理相关的部分只保留授权公理、受保护文件门禁和中央 skill 路由，不复制详细流程；其他不在本设计范围内的全局规则保持不变。
- 所有详细动作授权语义只有 `action-authorization` 一个中央 owner；阶段和委派 skill 通过契约消费它。
- 任何授权结论都能追溯到具体来源、动作族、目标、canonical target、副作用和生命周期。
- 负面约束优先收窄授权；固有步骤不能跨动作族或覆盖用户明确排除。
- 当前直接指令按相交范围覆盖旧状态，不制造整份计划的无关失效。
- 子代理有效能力永远不大于父授权和节点信封中的任一方，未列出能力默认不授予。
- special approval 不能被普通确认、阶段确认、其他目标授权或路径别名替代。
- 授权问题只暂停受影响动作及其依赖后继。
- 提示词层实施完成后，关联 P0 issue 仍保持打开，不把概率性约束描述成工具级保证。
