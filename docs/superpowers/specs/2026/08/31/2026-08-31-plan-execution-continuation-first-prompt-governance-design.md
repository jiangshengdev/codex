## 与旧设计的关系

本设计是对[计划执行不可恢复失败冻结提示词治理设计](2026-08-31-plan-execution-unrecoverable-failure-freeze-prompt-governance-design.md)的替代设计。旧文档作为历史保留，不覆盖、不删除；本设计确认后，旧文档中“无法立即证明可恢复即不可恢复”“失败后禁止补读现场”“不可恢复立即冻结整个计划”的结论不再作为后续计划依据。

## 唯一主目标

修改 `/Users/jiangsheng/cnb/codex-config/AGENTS.md` 及相关用户维护 skills 中职责合适的部分，使已确认计划在既有目标、授权和安全边界内尽可能持续执行，只有确实不存在安全有效的继续路径时才中止；全局提示词保持简洁，详细失败处理机制下沉到唯一 owning skill。

本设计只定义提示词治理目标、失败后的持续推进语义、真正中止条件、owner 分层和验收边界。它不是 implementation plan，不授权修改全局提示词、skills、前端提示词或 Git 状态。

## 问题与根因

当前详细规则位于 `skills/delegating-micro-stages/references/execution-graph.md`。节点未达到完成证据时，它要求协调者只使用失败当时已经取得的信息，并且只有五项条件全部已经被证明，才能把失败视为可恢复；任何暂时未知都直接归入不可恢复失败，随后冻结整个执行图并禁止补读、诊断、修正、重试或继续无关分支。

该模型无法区分：

- 尚未调查、因此暂时不知道是否可恢复；
- 已有明确证据证明无法在现有边界内继续。

于是普通 fixture 错误、测试失败、跨浏览器差异、类型或 lint 问题等计划执行反馈，会在取得根因证据之前被提前判为终态。实际结果是失败分类优先于完成计划，正常 TDD 和实现闭环被提示词自身阻断。

`action-authorization` 已采用“只暂停受影响动作及后继、其余继续”的局部模型，不是本次根因。`codex-gui/AGENTS.md` 只拥有前端工具链、契约和验收增量，也不拥有通用计划失败语义。

## 已确认设计决策

### 计划默认持续推进

节点失败是新的执行证据，不是默认终态。只要仍存在至少一个具体、已授权、安全，并且能够产生新证据或推进目标的下一步，协调者就必须继续执行计划。

计划内的以下情况本身均不得成为中止理由：

- fixture、helper、测试初始化或断言失败；
- 类型、lint、格式、构建或生成失败；
- Chromium、Firefox、WebKit 或其他平台之间出现差异；
- 实现细节、预估文件范围、节点拆分或验证命令与计划预测不完全一致；
- 首个候选修正无效，或需要依据新证据尝试另一条计划内路径。

处理这些反馈时，默认动作是有界诊断、修正、验证和重新调度，而不是先证明“可恢复”。

### 按可行动性而不是次数或成本中止

不设置固定重试次数、时间、token、命令次数或成本阈值作为中止条件。只要新的动作与上一轮不同，并能产生新证据或推进目标，就不得仅因已经失败多次而停止。

重复执行完全相同、没有新输入且不能产生新证据的动作不算继续推进。协调者应选择新的具体路径；只有所有安全有效路径均已耗尽，才可能形成终态。

### 允许计划在既定边界内自动适应

计划是实现目标的工具，不是不可变合同。若用户目标、产品结果、授权动作、安全和风险边界均未改变，协调者可以直接：

- 调整执行图节点、依赖、失败域和验证顺序；
- 替换已经证明不准确的实现机制或验证命令；
- 在现有授权覆盖的目标集合中增加、删除或调整实现文件；
- 插入新的诊断、修正和重新验证节点；
- 让不受失败影响的分支继续执行。

这些变化属于动态重编图，不需要用户重复确认，也不要求回写已确认计划正文。若变化需要新的授权、改变产品结果或越过风险边界，则只暂停受影响部分并请求对应决定；其他独立路径继续。

## 真正硬阻塞

中止必须由正面证据支持，而不是由未知、首次失败或模型缺乏把握反推。只有出现以下情况之一，且不存在安全替代路径时，才构成硬阻塞：

- 继续需要用户尚未授予的动作、目标或副作用，或者需要会改变产品结果的用户决策；
- 继续会越过安全边界、造成不可接受的破坏，或无法安全保留现有工作与证据；
- 必需工具、运行时、外部系统或权限不可获得，并且没有已授权的替代入口；
- 当前有效约束彼此矛盾，或者已有证据证明目标在这些约束下不可能实现；
- 所有具体、已授权、安全且能够产生新证据或推进目标的路径均已实际耗尽。

局部硬阻塞只暂停受影响节点及其依赖后继。只有硬阻塞覆盖全部剩余目标、共享前提或所有继续路径时，整个计划才进入终态。保护现场仍是硬约束，但保护现场意味着禁止破坏性清理、恢复或覆盖，不意味着禁止安全只读诊断和其他无关分支。

## 失败处理状态模型

执行图不再使用“可恢复/不可恢复”二元门槛决定是否允许调查。节点未达到完成证据后进入以下流程：

1. 记录失败证据和受影响产物，释放已经结束的资源锁。
2. 在现有授权与安全边界内识别下一项具体动作；必要时读取现场、诊断根因或验证候选假设。
3. 若存在有效下一步，插入或更新诊断、修正、验证节点，重算 ready set，并继续所有无冲突的有效分支。
4. 若某一步需要新授权或用户决策，只暂停依赖该缺口的部分；其他分支继续。
5. 只有取得硬阻塞的正面证据且所有替代路径均已排除时，才形成局部或全局终态并向用户报告。

失败后的读取、修正和重试仍受 `action-authorization`、能力信封、read/write set、资源锁及用户否定约束限制。本设计不把“尽可能继续”解释为扩大授权、修改基线、删除覆盖、增加 fallback、降低测试标准或执行破坏性操作。

## 验收设计

### 结构与静态 owner

- 对受改 skills 使用全局规则规定的 `quick_validate.py` 入口；它只证明 skill 结构有效，不证明行为语义。
- 检查 `execution-graph.md` 是唯一详细失败处理 owner，其他文件只保留摘要或路由。
- 静态确认不存在“无法立即证明可恢复即不可恢复”“失败后禁止补读现场”“普通首次失败立即冻结全图”等旧语义残留。
- 检查引用可达、路径准确、全局 AGENTS 保持简洁，并且未复制详细状态机。

### 独立行为验收

使用彼此隔离的 fresh context 运行单一场景，预期 oracle 只提供给最终审查者，至少覆盖：

- fixture/helper 首次失败：继续读取失败位置、修正 fixture 并重跑；
- 普通测试、类型、lint 或格式失败：在原目标内诊断、修正和验证；
- 跨浏览器差异：继续取得浏览器特定证据，不因首次差异中止；
- 计划预测的文件或命令不准确：在目标、授权和风险不变时动态重编图继续；
- 需要新增产品行为、外部目标或高风险副作用：只暂停受影响分支并请求授权；
- 工具缺失且禁止安装：排查已有权威替代入口；确无替代时形成硬阻塞；
- 继续会破坏现场或越过安全边界：拒绝破坏性动作，继续安全替代路径；无替代时停止；
- 约束矛盾或目标已被证明不可能：形成终态，不进行无意义重试；
- 同一命令在无新输入下重复失败：不得盲目循环，必须选择能产生新证据的下一步；没有下一步时停止。

行为验收要证明两侧：既不能再次过早中止正常计划，也不能用“尽可能继续”绕过授权、安全、用户决策或现场保护。

## 风险与控制

### 无限盲目重试

控制：继续必须对应具体的新动作、新输入、新证据或修正；完全相同且不能产生新信息的重复不计为有效路径。

### 借动态重编图扩大授权

控制：自动适应只允许发生在既有目标、产品结果、授权和风险边界内。新增外部目标、高风险副作用或用户可见语义变化仍需相应确认。

### 为通过验证降低标准

控制：禁止修改基线、放宽断言、删除覆盖、添加静默 fallback 或隐藏错误。若检查本身错误，必须用证据证明，并且修正仍在当前目标和授权范围内。

### 破坏现场

控制：失败后默认保留现有工作和证据；恢复、回滚、删除、清理或覆盖仍需明确授权。安全只读诊断和不相交分支不因现场保护而被禁止。

### 规则重复

控制：全局 AGENTS 只保留结果级原则；执行图是详细 owner；managing-work-stages 和 delegation-contract 只路由并消除冲突；前端不复制通用规则。

## 设计结论

新治理模型以完成已确认计划为默认方向：失败首先触发继续工作的证据循环，而不是触发停止资格审判。计划可以在目标、授权和风险不变时自动适应；只要仍有安全有效的下一步就必须继续。中止需要硬阻塞的正面证据，并且只有在所有替代路径均已耗尽后才成立。
