## 唯一主目标

重构本机实际生效的全局用户指令与相关 skills，使子代理委派不依赖 `explorer`、`worker` 等显式角色类型，并将能力信封准确定位为行为契约和审计边界，在保持全局指令简洁的同时，为后续委派提供一致、诚实且可审计的详细规则。

本设计只定义提示词治理的语义、owner 分层、拟修改范围和验收边界。它不是 implementation plan，不定义任务顺序、执行命令、执行图或提交拓扑，也不授权修改任何提示词、skill、issue、产品代码或 Git 状态。

## 术语与事实校准

### `AGENTS.md` 的实际层级

`codex-config/AGENTS.md` 是通过 filesystem 加载的全局用户指令，不是产品内部以 system role 注入的 system prompt。本文为延续用户术语可以统称其为“全局提示词”，但后续实现和验收不得据此声称它拥有 system role 的优先级或强制能力。

同理，`codex-gui/AGENTS.md` 是 Codex 仓库中约束 `codex-gui/**` 工作的前端工程指令，不是跨 GUI、CLI、TUI 生效的子代理治理 owner，也不是产品 system-role prompt。

### `agent_type` 的接口与使用历史

当前源码事实不是“v2 已删除 `explorer`”。v1 与 v2 的子代理接口都支持 `agent_type`，但该字段只在当前配置提供可用角色时才暴露；本次对话所用的 `spawn_agent` schema 没有暴露该字段。因此，接口能力与当前会话可调用参数必须分开描述。

历史记录显示，主动指定角色已经从高频用法退出当前实际工作流：

- 2026-06-20 至 2026-07-06，共有 882 次 `spawn_agent` 调用，其中 875 次显式指定角色：`explorer` 616 次、`worker` 233 次、`default` 26 次。
- 2026 年 8 月审计覆盖 137 个 rollouts、1615 次真实 `spawn_agent` 调用，`agent_type` 使用次数为 0。

进一步核对源码、历史角色定义、本机配置历史和真实子会话后，可以区分“角色字段被填写”和“角色配置产生实际效果”：

- 产品机制允许角色配置覆盖模型、推理强度，并关闭部分 feature 或工具；因此不能笼统声称角色永远只是标签或绝不改变工具。
- 2026 年 6—7 月实际使用的内置 `explorer` 配置为空，`worker` 与 `default` 没有配置文件；这些角色没有缩减工具，真实 `explorer`、`worker` 子会话都保有 `exec_command`。
- `explorer` 早期仅覆盖过模型和推理强度，该配置已于 2026-02-20 清空；本机当前配置及其已检查的 Git 历史也没有自定义角色配置。

因此，历史上高频使用的是角色标签，不是角色的能力缩减机制；近期连角色标签也已退出实际工作流。该证据支持从治理路径中完全移除角色，但不支持宣称产品接口或角色配置机制已经废弃。

## 已确认的设计决策

用户已确认两项选择：

- 保留“能力信封”概念，但明确它只是行为契约和审计边界，不是权限控制机制。
- 委派治理完全不使用 `agent_type`；即使接口暴露该字段，也不把角色作为兼容路径或专业化提示。

由此得到以下不变量：

- 子代理与主代理可能拥有相同的工具自由度；提示词、角色名称、任务名称和能力信封都不能把这种工具能力变成真正的权限沙箱。若产品运行时已通过角色配置、sandbox 或 tool schema 实际移除工具，那是独立生效的 `governing constraint`，不是提示词层授权。
- 能力信封继续记录节点被要求执行的动作、目标、读写集合、禁止事项、副作用和结束条件，用于任务说明、返回后审计、越界识别与停止。
- 能力信封描述的是提示词层“允许怎样行动”，不是运行时“技术上只能怎样行动”。不得用 `effectiveCapability` 等表达宣称工具调用已经受到强制拦截。
- 绝对控制不属于本次提示词与 skill 修改能够实现的结果。未来只有独立于模型判断的 sandbox、allowlist、capability enforcement 或等价工具级机制，才可能提供强制边界。

## 当前问题与根因

### 角色被错误混入治理语义

显式角色分配已经基本退出近期实际调用，但讨论和规则仍可能把 `explorer`、`worker` 当作稳定存在的接口参数，或者把角色名称误解为只读、可写、授权范围或工具能力。这样会造成两类错误：字段未暴露时，委派规则无法按设计工作；字段暴露时，角色又可能被当成授权或安全边界。

角色配置在产品层可能改变模型或真实缩减部分工具，但当前内置角色与本机历史没有利用这项能力；角色名称本身也不能替代任务目标、动作范围、读写集合和禁止事项。把角色保留在治理路径中，既不符合当前使用事实，也不能解决关联 P0 issue 中的越权风险。

### 能力信封的文字强度超过实际机制

当前提示词治理已经承认不提供工具调用前的 capability enforcement，但能力信封 reference 仍以“有效能力”“未授予即不能执行”和集合交集等措辞描述节点边界。这些规则可以作为规范性许可模型，却容易被理解为运行时已经强制限制子代理工具。

关联 issue 的历史事故恰恰证明，清晰的自然语言限制仍可能被子代理越过。若继续把声明性信封描述成实际能力隔离，就会隐藏而不是解决问题，并可能错误关闭 P0。

### 规则 owner 的粒度不清

跨入口稳定不变量、委派操作细节和授权语义说明目前分散在全局用户指令、`delegating-micro-stages` 与 `action-authorization` 的 reference 中。若同时在全局指令和多个 skills 复制详细流程，后续容易出现措辞漂移；若只保留一句抽象公式，又不足以指导字段未暴露时的实际委派和返回后审计。

因此需要按职责分层：全局用户指令只路由并声明不可误解的不变量，委派 skill 负责详细运行规则，能力信封 reference 负责精确定义其声明性、非强制语义。

## Owner 分层

### `codex-config/AGENTS.md`：简洁路由与不变量

全局用户指令只保留必须在 skill 加载前成立的最小规则：

- 角色、任务名称、skill、工具可用性和能力信封都不产生额外授权，也不构成工具级权限隔离。
- 子代理能力信封是行为契约和审计边界；详细委派规则由 `$delegating-micro-stages` 承担，动作授权语义仍由 `$action-authorization` 承担。

这里不复制角色选择流程、信封字段表、返回后检查步骤、越界处理清单或兼容分支，避免继续膨胀全局用户指令。

### `delegating-micro-stages`：委派行为 owner

`codex-config/skills/delegating-micro-stages/SKILL.md` 负责子代理创建前、运行中和返回后的详细行为规则：

- 委派始终以明确任务目标、节点职责和能力信封为主路径，不读取、选择或传入 `agent_type`。
- 无论当前工具 schema 是否暴露 `agent_type`，都不伪造角色字段，不把 `explorer`、`worker` 等标签塞入任务来模拟接口角色，也不把角色保留为可选专业化路径。
- 产品若通过其他独立配置实际改变模型或缩减工具，应按当前真实 tool schema 和 `governing constraints` 处理；这种运行时事实不重新产生角色治理路径，也不授予动作或替代信封字段。
- 委派前仍要建立最小能力信封；其目的在于清楚传达允许行为和预期结果，而不是宣称已经限制子代理的真实工具集合。
- 子代理返回后，主代理必须依据任务风险核对其报告、实际文件变化、Git 状态、命令副作用或其他可观察证据，不能仅因信封已下发就假定边界得到遵守。
- 发现实际动作越过信封时，将其识别为行为契约违约，停止该节点及依赖其产物的后继，报告精确越界字段并重新评估受影响状态；无依赖且仍安全、仍获授权的工作不被无条件停止。

该 skill 继续负责何时委派、微阶段拆分、并行调度和返回格式；本设计不把这些既有职责迁移到其他文件。

### `capability-envelope.md`：声明性语义 owner

`codex-config/skills/action-authorization/references/capability-envelope.md` 继续保存能力信封字段、构造方法、生命周期和节点示例，但需要校准以下语义：

- 将 `effectiveCapability = parentAuthorization ∩ nodeEnvelope ∩ governingConstraints` 明确定义为提示词层的规范性许可边界，不是运行时工具能力集合，也不是执行前拦截器。
- “未声明能力默认不授予”表示子代理按行为契约不应执行，不表示相关工具在技术上不可调用。
- `owner`、角色、工具可用性和任务重要性既不能产生授权，也不能证明实际工具受到限制。
- 信封用于委派前说明、委派后审计、越界识别、失败域隔离和能力生命周期管理；它不能提供 filesystem、Git index、网络、进程或下层子代理的强制隔离。
- 如果真实执行越界，规则要求停止、核验和报告，不得把“模型理论上不该执行”写成“越界不可能发生”。

该 reference 只澄清既有能力信封的性质，不取消字段结构，也不把动作授权 owner 转移给委派 skill。

## 角色无关的委派行为

### 委派输入

每个委派节点仍需明确表达：

- 唯一目标与可观察结果；
- 当前阶段和单一动作类型；
- 允许执行的动作及其参数边界；
- 允许读取、写入和产生副作用的目标；
- 明确禁止事项、结束条件与需要返回重规划的触发条件。

这些内容可以继续使用现有能力信封字段承载。角色字段无论存在与否，都不替代上述输入。

### 不使用角色字段

无论当前接口是否提供 `agent_type`，委派都不读取、选择或传入该字段，只使用接口真实支持的任务描述、上下文继承、模型参数和能力信封。规则不得报错、等待角色接口、把任务名称当作角色，也不得在自然语言中声称已经创建某种 `explorer`、`worker` 或受限角色。

任务职责可以写成“只读核对”“编辑指定文档”等具体行为，但这是能力信封的一部分，不是角色身份。若当前运行时已经独立移除某项工具，节点必须服从该实际限制；这不改变父授权、`readSet`、`writeSet`、`stateEffects`、`commandScope`、special approval、阶段门禁或返回后审计要求。

### 返回后审计与越界停止

能力信封的价值在于提供可比对的预期边界。子代理返回后，主代理根据风险和副作用检查实际结果是否与信封一致。低风险只读节点可以核对引用和状态摘要；涉及写入、生成、验证、Git index、提交或外部影响的节点必须核对相应可观察状态。

若发现越界：

- 不把越界结果直接视为可信产物；
- 停止消费该结果的后继并界定受影响资源；
- 记录越过的动作、目标、参数或副作用字段；
- 在当前授权范围内只做必要的状态核验，不自行恢复、删除、提交或扩大修正动作；
- 按现有阶段和动作授权规则决定后续是否需要用户重新授权。

该停止规则是发现后的治理响应，不是事前强制控制。

## 拟修改范围

后续实施只考虑以下三个 owner 文件：

- `codex-config/AGENTS.md`：把跨入口规则收敛为简洁的路由与不变量，明确角色和能力信封不产生实际权限。
- `codex-config/skills/delegating-micro-stages/SKILL.md`：完全移除角色依赖，加入禁止读取、选择、传入或伪造角色，以及行为契约、返回后审计和越界停止的详细规则。
- `codex-config/skills/action-authorization/references/capability-envelope.md`：澄清能力信封与集合交集是声明性的许可和审计模型，不是工具级强制能力。

最终精确措辞和最小 diff 由后续 implementation plan 在只读核验当前文件内容后确定。本设计不授权提前修改这些文件。

- `codex-config/skills/action-authorization/SKILL.md`：主文件已经明确提示词层不提供 capability enforcement，本次只校准其能力信封 reference。

## 验收边界

### 结构验收

- 全局用户指令中的新增或改写内容保持简洁，只声明稳定不变量并路由到 owning skills，不复制详细流程。
- 禁止使用角色、委派前信封、返回后审计和越界处理只在 `delegating-micro-stages` 中形成完整行为闭环。
- 能力信封的字段与生命周期继续由 `capability-envelope.md` 拥有，并明确区分规范性许可与实际工具能力。
- 三个 owner 之间不存在互相冲突的“角色即权限”“角色仍是可选治理路径”“信封可强制拦截”或“未暴露角色就不能委派”表述。

### 行为验收

- 在 `spawn_agent` 未暴露 `agent_type` 的上下文中，委派规则可以只靠真实接口字段和能力信封完整表达任务，不伪造角色。
- 在接口暴露 `agent_type` 的上下文中，委派规则仍不读取、选择或传入该字段；授权判断、任务边界和审计要求不依赖角色。
- 只读、编辑、验证、stage、commit 等节点继续拥有不同的行为契约；其区分来自父授权与节点信封，而不是 `explorer`、`worker` 或 `default` 标签。
- 子代理实际越界时，规则要求识别、核验并停止受影响后继，而不是以信封存在为由断言越界不可能发生。
- 合成 prompt 检查和结构检查只能证明规则表达完整，不能证明未来运行时一定遵守，也不能替代真实行为证据。

### 范围验收

- 后续 diff 只包含三个拟修改 owner 文件，不修改 `codex-gui/AGENTS.md`、其他 skills、`.agents/skills/**`、产品源码或 issue。
- 不以“角色已经废弃”“v2 不支持 `agent_type`”或“角色配置绝不影响工具”作为实施依据。
- 不引入新的角色兼容层、伪字段、产品代码分支或多份重复权威规则。

## P0 保留判断

关联 issue 描述的是缺少强制能力边界造成的状态安全风险。本设计选择保留能力信封，是为了改善任务表达、授权推理、审计和越界后的停止行为，不是因为自然语言契约可以实现绝对控制。

因此，即使本设计随后完整实施并通过全部提示词层验收，关联 P0 仍必须保持未关闭。只有未来引入独立于模型判断的工具级限制，并以真实越权事故场景证明文件写入、Git index、命令和外部影响会在执行前被强制阻止，才具备重新评估关闭条件的基础。
