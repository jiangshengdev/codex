## 唯一主目标

针对“执行图没有形成有效并行”的问题，建立一套只对已落盘计划文件的执行生效的提示词治理：全局系统提示词只保留简洁、稳定的强制规则，完整节点协议与调度语义由专门 skill 承载；执行时以真实依赖、授权、读写集合、执行上下文、资源锁和并发容量计算 `ready set`，优先保护关键路径，并在最终回复中提供可核验的真实并行证据。

本设计只定义提示词与 skill 的责任分层、强制触发边界、调度不变量、审计输出和首轮修改边界。它不是 implementation plan，不定义任务顺序、提交拆分、执行命令或精确写入文本，也不授权修改任何提示词、skill、issue 状态或 Git 状态。

## 已确认的产品决策

### 只有落盘计划文件才强制使用执行图

强制执行图的触发条件是：当前动作正在执行已经落盘的计划文件。聊天中的临时计划、尚未落盘的计划讨论、调研、设计和普通多代理委派不因本设计而强制建立执行图。

这个边界是有意选择，不得在实施时扩大为“只要使用两个及以上子代理就必须建图”，也不得缩小为“只有计划显式声明并行时才建图”。普通委派仍可根据任务需要并行，但不纳入本设计的强制执行图和最终并行证据契约。

### 最终回复必须提供真实并行证据

执行落盘计划结束时，最终回复必须简短说明：

- 哪些独立分支实际发生了时间重叠；
- 哪条路径构成粗粒度关键路径；
- 是否存在已经就绪但没有启动的节点；若存在，给出当时仍有效的容量、授权、canonical 资源冲突或负收益证据。

不能用子代理调用次数、存活代理数量、任务标签或计划中的 `parallelizable` 声明替代真实并行证据。没有发生可并行工作时，应直接说明当时不存在有实际价值的独立 ready 节点，不得制造任务来展示并发。

## 当前事实与问题校准

### 现有规则已经包含大部分调度机制

当前全局 `AGENTS.md` 已要求计划提供可调度执行图，并在节点完成、失败、资源释放或图变化后重算 `ready set`。`delegating-micro-stages` 及其 `references/execution-graph.md` 已经定义节点字段、动态读写锁、关键路径优先、task-boundary fan-in、唯一 Git owner、失败域和运行记录。

因此问题不是从零缺少调度协议，而是触发边界和责任层级不够清楚：全局提示词复制了过多字段级细节，阶段 skill、委派 skill 和 execution-graph reference 多处重复相同规则；与此同时，落盘计划执行与普通委派是否都必须建图没有形成单一、明确的入口语义。

### 多代理数量不是并行结果

关联 issue 的历史证据表明，独立读取、解析和验证曾被逐节点串行等待，多个代理也曾重复审查同一份可变 diff；短时 Git index 冲突还被扩大为整个工作流的串行约束。另有写集合与接口语义独立的任务被无依据延后约两小时。

这些现象的共同根因不是代理数量不足，而是没有稳定消费当前 `ready set`，没有把资源冲突限制在最小 canonical 冲突域，也没有用实际重叠和关键路径缩短证明调度有效。

### 实际提示词资源只有两个 canonical 单元

`~/.codex/AGENTS.md` 是指向 `/var/folders/x7/7d55d2z55012f5_h3jbfdjj40000gn/T/tmp.xHZfTk2RTH-config/AGENTS.md` 的符号链接，两者是同一个全局规则资源。`/var/folders/x7/7d55d2z55012f5_h3jbfdjj40000gn/T/tmp.xHZfTk2RTH/codex-gui/AGENTS.md` 是独立普通文件，只作用于 `codex-gui/**`。

本设计不把符号链接和实际目标误算成两份待修改文件。任何后续全局规则写入都会命中 `~/.codex/AGENTS.md` 的专门确认门禁。

## 保证边界

本方案属于提示词层治理，只能提高模型形成执行图、及时重算 `ready set`、缩小锁冲突域和汇报调度证据的稳定性。它不能提供运行时任务调度器、工具调用前的强制 DAG 校验、真实资源锁、进程级并发控制或不可伪造的时间线证明，也不能保证未来所有模型都严格遵守自然语言规则。

因此，提示词和 skill 后续实施完成并不自动证明关联 issue 已经关闭。issue 状态仍需依据实施后的合成行为验收和真实落盘计划执行证据另行判断；本设计不授权更新 issue。

## 责任分层

### 全局系统提示词：短触发规则与不可绕过的不变量

`codex-config/AGENTS.md` 只保留足以在 skill 加载前生效的简洁规则：

- 执行已落盘计划文件时，必须使用执行图，并路由到 `$managing-work-stages` 与 `$delegating-micro-stages` 的详细协议；
- 初始调度及节点完成、失败、资源释放或图变化后，必须重算 `ready set`，在授权、依赖、资源和并发容量允许时优先保护关键路径；
- 串行等待必须有仍有效的硬依赖、授权门禁、最小 canonical 资源冲突、容量限制或可核验负收益证据；
- 执行结束时必须提供简短的真实并行证据。

全局文件不继续复制节点字段清单、状态机、动态锁算法、运行记录 schema、fan-in/fan-out 细节或逐项完成检查。与 worktree 直接请求、特殊授权、本地提交边界和禁止 Git 远程有关的其他治理语义不能因精简执行图规则而丢失；它们继续由各自 owner 承载。

### `managing-work-stages`：阶段触发与计划文件边界

`skills/managing-work-stages/SKILL.md` 负责判断当前是否正在执行已落盘计划文件，并把该情形路由到执行图协议。它保留设计、计划、实现三轮门禁、计划确认、事实闭包、计划文档结构和实施前文档提交门禁，但不复制字段级调度协议。

该 skill 必须消除“所有已确认计划都强制建图”的歧义。未落盘的计划讨论即使已经口头确认，也不命中本设计的强制执行图；一旦执行对象是落盘计划文件，则不能因为计划较短、代理数量较少或任务看似线性而绕过执行图编译。执行图可以按任务规模保持轻量，但仍需表达真实依赖和初始 `ready set`。

### `delegating-micro-stages`：委派职责与调度入口

`skills/delegating-micro-stages/SKILL.md` 继续负责何时委派、如何拆分单一结果微阶段、能力信封、范围扩大停止、主代理上下文和返回后审计。普通调研、设计和其他未执行落盘计划文件的委派不强制加载完整执行图协议。

当执行已落盘计划文件时，该 skill 必须切换为执行图调度入口：主代理维护全局图和动态状态，子代理只消费边界明确的节点；同一结果不得交给多个代理重复生产或重复审查，除非审查具有稳定输入、独立职责和独立完成条件。

主 `SKILL.md` 只保留触发、职责、停止条件和 reference 路由。节点 schema、ready-set 状态机、锁、fan-in、失败域和审计格式统一由 execution-graph reference 负责，避免多个详细 owner。

### `execution-graph.md`：唯一详细调度协议

`skills/delegating-micro-stages/references/execution-graph.md` 是完整执行图语义的唯一详细 owner，继续承载：

- 节点字段、稳定产物、完成证据与授权门禁；
- 初始及动态 `ready set`、关键路径和并发容量；
- `readSet`、`writeSet`、执行上下文与 canonical 资源锁；
- task-boundary fan-in、唯一 Git owner 和组合验证；
- 局部失败域、修正节点和失效验证；
- 运行记录与最终并行审计。

该 reference 需要补足两个当前可审计性缺口。

第一，明确“有实际价值”的最低判定：节点必须有独立、必要或能解锁后继的稳定产出，且并行收益不能被当前可核验的冲突或协调成本抵消。不得用这个词主观搁置 ready 节点；暂缓必须形成完整 `deferralEvidence`。

第二，规定最终并行证据的固定最小内容：实际重叠分支、粗粒度关键路径、未启动 ready 节点及其当时有效原因。详细运行状态可以只在执行上下文中维护，不要求在计划文件执行期间持续回写计划正文。

### `project-doc-workflow`：保持计划文档的权威结构

`skills/project-doc-workflow/SKILL.md` 已规定长计划正文以 execution graph 作为权威执行结构，并把线性任务清单降为展示层。该职责与本设计一致，首轮不修改。

计划文件保存确认时的权威结构，不作为并发子代理共同写入的动态运行日志。执行期间的事件、锁和节点状态由唯一协调 owner 维护；最终用户可见证据在回复中汇总。只有未来独立需求明确要求持久化执行记录时，才设计单独的 execution-record 文档，不在本轮把动态状态混入计划文件。

### `codex-gui/AGENTS.md`：保持不变

`codex-gui/AGENTS.md` 只负责前端工程、权威契约、GUI 事实闭包、HeroUI、性能和测试 fixture 等前端专属规则。执行图、`ready set`、关键路径和多代理调度是跨 GUI、CLI、TUI 和普通任务的通用流程，不属于前端专属责任。

现有前端提示词已经要求 GUI 高风险任务追踪真实入口、契约、Browser Mode、E2E 和生命周期路径。这些信息应在具体计划中成为节点的输入、完成证据或资源声明，不需要在前端提示词中复制通用调度算法。

## 调度语义

### 编译落盘计划

执行开始前，把落盘计划中的任务、验证和提交边界编译为结果单一、完成条件可观察的节点。任务编号、文档顺序、同一仓库、同一 agent 或最终需要汇合都不产生依赖；每条硬边必须说明后继等待的稳定产物。

计划文件中的 execution graph 是权威结构。如果旧计划已经落盘但缺少本设计要求的最小图信息，不能在执行时臆造关键依赖并宣称计划有效；应停在受影响的计划边界，说明缺失信息并回到适用的计划确认流程。本设计不要求重写历史计划。

### 初始与事件驱动调度

首次进入执行循环时计算初始 `ready set`。此后任一节点完成、失败、资源释放、暂缓证据失效或图变化时，在同一调度循环重新计算状态，并先启动所有当前有实际价值且可运行的 ready 节点，再等待、汇报或处理无关协调工作。

资源暂时冲突不会形成新的 DAG 边；节点保持 ready 并等待对应最小资源锁。锁释放后必须重新参与调度，不能继续沿用历史冲突作为延期理由。

### 容量与关键路径

可用代理或执行槽位只表示容量上限，不是并行目标。容量足够时，启动所有有实际价值、已获授权且无冲突的 ready 节点；容量不足时优先保护粗粒度关键路径，再参考节点预计成本和可解锁后继数量。

不得为了填满槽位制造节点、拆出没有独立产出的微阶段，或把同一结果交给多个代理。也不得为了减少调度次数，把原本独立、可并行且有价值的工作合并成一个开放式大节点。

### 写入隔离与 fan-in

不同 task boundary 的并行写入使用独立 worktree、branch 和 Git index。同一 task boundary 内写集合不相交的编辑可以共享 worktree 并行，但编辑节点不得操作共享 Git index；生成、格式化、会修改组合状态的 fix、stage 和 commit 由唯一 owner 在 fan-in 后执行。

共享运行记录只有一个写 owner。子代理返回结构化节点结果，不并发追加同一文件。局部验证不能替代 task-boundary 的组合验证，fan-in 前的共享工作树中间态也不能作为依赖稳定产物的后继输入。

### 局部失败与重调度

节点失败只暂停该节点及其传递后继。只有失败推翻共享前提、污染共享状态或改变安全与授权边界时，才扩大暂停范围。计划内修正以新节点插入受影响链路，并重新计算关键路径、`ready set`、资源锁和失效验证；无关分支继续运行。

## 最终并行证据

最终回复中的并行证据保持简洁，不复制完整执行日志。最小结构为：

- `实际并行`：列出真正发生时间重叠的独立节点或分支；
- `关键路径`：列出决定端到端完成时间的粗粒度链路；
- `未启动 ready 节点`：列出执行期间曾就绪但没有立即启动的节点及其当时有效原因；若没有则明确写“无”。

原因只能来自并发容量已满、授权未满足、具体 canonical 资源或读写冲突、仍有效的完整 `deferralEvidence`。任务编号更小、另一个无依赖节点仍在运行、历史冲突、已释放的锁、agent 复用或“通常按顺序做”都不是有效原因。

该证据用于判断执行是否真实缩短关键路径，不等同于不可伪造的运行时审计，也不要求向用户展示所有内部节点字段、时间戳或能力信封。

## 验收边界

### 触发范围

- 执行已落盘计划文件时必须加载并遵循 execution-graph reference；
- 已确认但未落盘的聊天计划不因本设计强制建图；
- 普通调研、设计和多代理委派不因本设计强制建图；
- 旧落盘计划缺少必要图信息时回到计划边界，不在执行时静默补造依赖。

### 调度行为

- 首次调度会计算初始 `ready set`；
- 节点完成、失败、资源释放、暂缓证据失效或图变化后，会在同一调度循环重新计算并启动可运行节点；
- 槽位不足时优先关键路径，槽位空闲时不无依据搁置有价值的 ready 节点；
- 资源锁只阻塞访问同一 canonical 资源的最小冲突域；
- 同一结果不会被多个代理无依据重复生产或重复审查；
- 节点失败只传播到声明的失败域。

### 最终证据

- 最终回复包含实际并行、关键路径和未启动 ready 节点三项简短证据；
- 实际并行以节点时间重叠和关键路径缩短判断，不以代理数量判断；
- 所有未启动 ready 节点都有当时仍有效、可复核的原因；
- 没有并行空间时如实说明，不制造节点或虚构并行。

### 责任分层

- 全局提示词只保留短触发规则和不变量，不复制详细协议；
- `managing-work-stages` 负责阶段与落盘计划触发；
- `delegating-micro-stages` 负责委派入口和主代理职责；
- execution-graph reference 是唯一详细调度 owner；
- `codex-gui/AGENTS.md` 与无直接缺口的其他 skills 保持不变。

## 实施前门禁

设计落盘不等于设计确认。本文获得用户明确“确认设计”或等价确认后，才能进入独立计划阶段；设计确认不自动授权创建计划、修改提示词、修改 skill、运行安装入口、验证、stage 或 commit。

任何实施开始前，必须向用户展示拟写入 `~/.codex/AGENTS.md` 的精确内容，并取得面向该受保护文件的单独明确“确认写入”或等价直接授权。由于该文件指向 `codex-config/AGENTS.md`，修改实际目标、符号链接、脚本改写、恢复或格式化都属于同一受保护资源写入，不能绕过该门禁。

后续若编写并确认实施计划，必须先把本设计及相关计划文档创建为独立本地 Git 提交；提交成功前不得开始任何实施任务。计划还必须只读核验 codex-config 的现有 skill 安装入口、目标路径冲突和验证方式，并遵守不安装程序、不操作 Git 远程以及每个计划任务独立提交等现有约束。
