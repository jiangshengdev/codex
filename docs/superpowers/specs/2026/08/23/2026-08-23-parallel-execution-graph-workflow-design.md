## 唯一主目标

重构当前实际生效的提示词与相关 skills，使计划必须生成可调度依赖图，并让所有满足条件的
独立工作真正并行执行，同时保留必要的安全、授权和验证边界。

## 决策来源

本设计落实
`docs/superpowers/research/2026/08/23/2026-08-23-parallel-execution-decisions.md`
机械记录的五项已确认决策：

1. 就绪且无资源冲突的节点必须立即并行调度，直到可用槽位用满；串行必须有硬依赖、资源锁
   或明确负收益证据。
2. 不同提交边界的并行写分支使用独立 worktree、branch 和 Git index；同一提交边界内写集合
   不重叠的子节点可以共享 worktree 并发编辑，但生成、格式化、stage 和 commit 只有一个
   owner。
3. 计划任务继续作为 Git 提交边界；执行拓扑不机械等于提交拓扑，不得合并多个任务提交。
4. 节点失败只暂停失败节点及其后继；独立分支继续。计划内修正作为新节点插图并重新调度。
5. 计划必须精确声明全部工作树创建动作；用户确认计划即授权这些精确动作。实施任务启动前
   先完成全部已声明工作树预配，计划外创建或参数变化仍须重新确认。

这些决策已经穷尽本次设计的实质产品语义。本文补充的字段命名、调度算法分工、reference
拆分和验证方式属于实现机制，不增加新的用户决策。

## 当前问题与根因

### 当前执行事实

最近的 Composer 待处理输入管理实施虽然创建了多个子代理，但 Task 1 至 Task 6 仍按
“完成当前任务提交，再启动下一任务”线性推进。同步 review、失败分析和后期回修与正在变化
的同一份 diff 重叠，不构成独立实现分支，也没有缩短原始关键路径。

该计划本身存在可证明的 fan-out/fan-in：

```text
Task 1 -> Task 2 -> Task 3 --\
                            -> Task 5 -> Task 6 -> 最终验证
Task 4 --------------------/
```

Task 4 的 Editor portal seam 与 Task 1 至 Task 3 的 queue/coordinator 链没有产物依赖，原本
可以并行；Task 5 才是两条分支的汇合点。线性任务编号和提交纪律掩盖了这段并行空间。

### 规则根因

直接串行根因是当前全局 `AGENTS.md` 中“提交，再开始下一个任务”的无条件规则。它把“每个
任务独立提交”错误地扩展成“任务必须依次启动”。其他相关 skills 没有主动制造同一条硬规则，
但也没有提供能够推翻线性默认值的执行协议：

- `managing-work-stages` 只要求计划给出执行顺序，没有要求 DAG、ready set、关键路径、汇合点
  或漏并行反向审计。
- `delegating-micro-stages` 只有原则性的“独立任务优先并行”，没有节点输入/产出、依赖边、
  资源锁、工作区所有权、完成条件和动态重调度契约。
- `project-doc-workflow` 保留了正确的逐任务提交边界，但没有明确该边界不是其他独立任务的
  启动栅栏；共享 research 记录也没有单写 owner。
- `codex-gui-worktree` 即使面对已确认计划中精确列出的创建动作，仍要求执行时再次确认，可能
  让实现图在部分节点已经运行后停下来等待授权。

### 必须保留的串行边界

并行化不能删除真实依赖。以下边界继续作为硬屏障：

- 设计、计划、实现之间的确认门禁，以及产品决策、范围、接口、数据、安全和高风险授权门禁；
- 实现前的相关工作文档独立本地提交；
- 消费者等待权威类型、接口、schema、生成物或生命周期语义稳定；
- 同一 Git index 的 stage/commit、共享生成物、格式化器和声明为 sequential 的 runner；
- merge/rebase 冲突逐文件处理并立即暂存的防覆盖流程；
- 节点验证、fan-in 汇合和最终全图验证的事实依赖；
- 计划外工作树创建、已确认参数变化，以及其他未被计划确认覆盖的工具授权；
- 用户限定的只读、准备、禁止安装、禁止远程 Git、force 确认与 ignored 文件边界。

## 设计原则

### 依赖来自证据，不来自编号

任务编号、文档顺序、同一模块或同一方向都不能自动形成依赖边。每条硬依赖必须记录原因和
所等待的稳定产物。文件不重叠也可能存在接口或生命周期依赖；文件重叠也不等于所有动作都
冲突，例如多个只读审计可以并行。

### 执行图与提交图分离

执行节点是可调度工作单元，计划任务是 Git 提交边界。一个任务可以展开成多个并行节点，再
由该任务的唯一提交 owner 汇总为一个提交；多个任务也可以在隔离分支上并行形成各自提交，
之后按依赖拓扑集成。集成只搬运或合并既有任务提交，不 squash、不 amend，也不把多个任务
重做成一个提交。

### 并行是强制默认值

调度器不能只在计划中标注“可并行”后仍逐个执行。每次图状态变化都必须计算 ready set，
立即占满所有可用并发槽位。若 ready 节点未启动，执行记录必须指出具体阻塞资源、硬依赖或
可核验的负收益；“为了稳妥”“同一方向”“先做完当前任务”不是证据。

### 资源冲突独立于依赖关系

资源锁只限制同时运行，不把两个节点永久改写成产物依赖。共享 Git index、格式化器、生成
目录、sequential runner 或同一写文件可以形成动态互斥；锁释放后，节点仍按原 DAG 就绪。

## 权威执行图契约

计划必须为每个可调度节点表达以下事实。具体采用 Markdown 表格、结构化代码块或等价格式
由计划作者决定，但字段语义不可省略。

### 节点身份与结果

- `nodeId`：图内唯一、稳定的节点标识。
- `taskBoundary`：该节点最终归属的计划任务/提交边界；只读调查可明确为无提交。
- `operationKind`：调查、编辑、生成、格式化、验证、审查、stage、commit 或集成。
- `outcome`：唯一产出及可观察完成条件，禁止用“处理相关内容”一类开放表述。
- `estimatedCost`：粗粒度成本，用于槽位不足时优先保护关键路径，不用于覆盖硬依赖或资源锁。
- `deferralEvidence`：仅在并发明确负收益时填写，记录预计并发收益、冲突或争用成本、暂缓对象、
  复查触发点和证据失效条件；不得伪装成硬依赖或永久资源锁。

### 依赖与产物

- `hardPredecessors`：必须完成的前置节点；每条边同时写明依赖原因和所等待的稳定产物。
- `consumes` / `produces`：类型、公开接口、schema、生成物、fixture、owner/lifecycle 语义、
  commit 或其他可跨文件消费的事实。
- `completionEvidence`：节点完成后解锁后继所需的验证结果、稳定快照或提交身份。代理返回一句
  “完成”不构成产物稳定屏障。

### 读写与执行资源

- `readSet` / `writeSet`：直接文件以及 catalog、schema、snapshot、lockfile 等间接生成物。
- `executionContext`：worktree、branch、Git index 及共享/独占关系。
- `resourceLocks`：运行时必须独占的 index、生成入口、格式化入口、浏览器 runner 或其他资源。
- `owner`：谁可以编辑、生成、格式化、验证、stage、commit 或集成；共享 worktree 的 Git
  操作必须收敛到唯一 owner。

同一 `executionContext` 中，任一节点的 `writeSet` 与另一节点的 `readSet ∪ writeSet` 相交时
不得并发。只有读取稳定快照、切换到独立 worktree，或证据确认输入不可变时才能消除该冲突。
该规则同时覆盖源码、间接生成物和验证所读取的组合状态，不能只检查“两个 writer 是否改同一
文件”。

### 验证、失败与重编图

- `verification`：项目固化入口、真实执行范围、成功条件，以及验证是否依赖 sequential runner。
- `failureDomain`：失败会阻塞的后继集合；不得笼统暂停整个计划。
- `replanTriggers`：实际写集合扩大、公开接口变化、生成物扩散、验证发现计划内问题、基线变化
  或资源声明失真时，哪些节点必须暂停并重新计算。
- `authorizationGate`：若节点依赖用户授权，明确所需授权和当前是否已满足；调度器不得借并行
  绕过阶段或风险门禁。

计划不能使用手写的 `parallelizable: true/false` 作为权威。可并行性必须由前置节点、产物、
读写集合、执行上下文和资源锁推导，避免布尔标记随计划演化而失真。

## 计划编译流程

### 建图

计划阶段先把每个任务拆成产出单一、完成条件明确的节点，再根据当前代码证据添加硬依赖边。
授权门禁、文档提交、权威产物稳定、节点验证和最终 fan-in 都作为显式屏障节点或前置条件。

### 计算调度视图

确认计划前必须至少给出：

- 初始 ready set；
- fan-out 分支与 fan-in 汇合点；
- 按粗粒度成本计算的关键路径；
- 各节点的 worktree/branch/index 隔离和资源锁；
- 所有工作树创建动作的精确命令、名称、branch、base、目标路径和 include 范围；
- 任务提交形成位置与后续集成拓扑；
- 最终验证等待的全图完成条件。

### 漏并行反向审计

复杂计划在既有影响面反向审计之外，再执行一次独立的调度反向审计。审计从每一条串行边反问：

- 后继实际等待哪个产物，还是只等待前一任务编号？
- 这是永久依赖还是可用隔离/资源锁消除的同时运行冲突？
- 能否先抽取稳定 contract，使后续分支提前 fan-out？
- 验证、review 或准备工作是否能在不读取 mutable diff 的情况下成为独立节点？
- 是否存在 fan-in 被误写成整条单链？

无法给出证据的串行边必须删除。仍有可廉价核验的依赖未知项时，不得请求计划确认。

## Ready-set 调度

`delegating-micro-stages` 成为执行图的调度 owner。实现开始后按以下状态机运行：

```text
等待 -> 就绪 -> 运行 -> 已完成
          |      |-> 失败
          |-> 暂缓（有明确负收益证据，触发点到达后重新评估）
等待/就绪 ------>|-> 暂停（仅依赖失败节点或触发重编图的节点）
```

1. 只把所有硬前置已完成且授权满足的节点加入 ready set。
2. 从 ready set 中排除与当前运行节点存在资源锁或同一上下文读写冲突的节点；资源冲突不改变
   其依赖边。
3. 只有已有 `deferralEvidence` 的 ready 节点可以进入暂缓；每次相关节点完成、资源释放、成本
   事实变化或预计复查时点到达，都必须重新评估，证据失效后立即回到 ready set。
4. 立即启动所有无冲突、未被有效负收益证据暂缓的 ready 节点，直到并发槽位用满。槽位不足时优先保护关键路径，再参考
   预计成本与可解锁后继数量。
5. 任一节点完成、失败、释放资源、暂缓证据到期或触发重编图后，立即更新图和 ready set，不等待整个 wave
   或编号更小的无关任务结束。
6. 关键路径节点不得等待非依赖分支；非关键路径分支也不得因为关键路径正在运行而空闲。
7. 每次无法填满槽位时记录原因：当前没有更多 ready 节点、具体资源/读写冲突、授权门禁，
   或仍有效的 `deferralEvidence`。

调度成功的衡量对象是独立节点的实际重叠与关键路径缩短，不是存活代理数量、调用次数或
“实现时同步 review”。依赖 mutable diff 的 reviewer 属于当前节点协作，除非计划给它稳定
快照和独立完成条件，否则不计为关键路径并行节点。

## 写隔离与 Git 所有权

### 工作树预配屏障

需要隔离 worktree 的计划必须把全部创建动作写入执行图和计划正文。计划确认同时满足这些
精确节点的 `authorizationGate`，不再在实施过程中逐个重复询问。

计划阶段先只读核验固化脚本、base、目标路径、branch 名称、include 范围及现有 worktree/
branch 冲突。实现阶段仍先完成相关工作文档提交；随后进入工作树预配屏障，在任何实现编辑、
生成、产物验证或任务提交节点启动前，创建并核验全部已声明 worktree。创建动作共享仓库
worktree 元数据锁时可以顺序执行，但不得与实现节点交错。这样，预配失败只阻止实现图启动，
不会让工作执行一半后再因缺少工作树授权暂停。

计划确认只覆盖正文中逐项展示且参数完全一致的命令。名称、branch、base、目标路径、include
范围或实际命令变化，以及新增计划外 worktree，都会使原授权失效；必须展示新的精确命令和
目标并重新确认。预配前仍禁止覆盖既有 branch、worktree、目录、文件或 symlink，冲突时停止
并报告精确阻塞路径。

### 不同提交边界

可独立推进的任务写分支必须使用不同 worktree、branch 和 Git index。每个分支基于计划声明
的稳定基线，拥有自己的编辑、验证、stage 和 commit 节点。后续集成节点按依赖拓扑把任务
提交带入目标分支，并保留原提交边界。

如果两个任务最终会改到同一文件，不能仅凭文件重叠否定所有并行：计划应判断它们是否消费
彼此产物。没有产物依赖但预计会发生集成冲突时，可以并行形成提交，并把冲突解决建模为明确
集成节点；若冲突成本有证据显示超过并行收益，才记录负收益并串行。

### 同一提交边界

同一任务可在同一 worktree 内并行执行写集合不相交的编辑节点。为防止共享状态竞态：

- 每个编辑节点只能修改声明的 `writeSet`，越界即触发暂停下游和重编图；
- 任一节点读取的文件或间接产物若正在被同一上下文的另一节点修改，必须等待、读取稳定快照
  或转入隔离 worktree；
- 生成、格式化、stage、commit 由该任务唯一 owner 执行；
- 任何子节点不得独立操作共享 Git index；
- 所有编辑/生成子节点先汇合到任务级验证节点，由 owner 基于完整组合 diff 运行该任务验证；
  只有组合验证成功，才允许 stage/commit 或向其他任务发布稳定产物；
- owner 在组合验证后汇总并审查完整任务 diff，只暂存该任务文件，再检查 staged diff；
- 子节点产出尚未汇总时，不得把共享 worktree 的中间状态描述为稳定提交基线。

## 失败隔离与动态修正

节点失败时，调度器只暂停该节点及其传递后继；不依赖它的运行节点继续，其他 ready 节点仍
按槽位调度。失败不能自动扩大用户授权或计划范围。

若失败属于已确认计划内、且修正保持既有目标、文件、行为与风险边界：

1. 创建新的修正节点，声明失败证据、写集合、验证、提交归属和被替代或补充的产物；
2. 把修正节点插入失败节点与受影响后继之间；
3. 重新计算关键路径、ready set、资源锁和需要失效的旧验证；
4. 修正完成并形成稳定产物后恢复后继；
5. 若修正已有任务提交，仍创建新的独立提交，禁止 amend。

若修正改变目标、实质范围、外部接口、数据、安全、风险或授权边界，保持对应依赖域暂停并
回到既有用户确认门禁。独立分支仍可继续，但不能越过它自己的未满足授权或产物依赖。

## 验证拓扑

验证不应全部延迟到末尾，也不能无证据全部并行：

- 节点局部验证在其产物形成后运行，但同一任务的局部验证不能替代 task-boundary fan-in 后的
  组合验证；只有组合验证成功才允许该任务 stage/commit 或解锁要求稳定产物的消费者。
- 不共享 runner、生成目录或可变 fixture 的验证可以并行。
- sequential Browser runner、生成器、格式化器和同一 Git index 使用显式资源锁。
- 集成后的跨分支类型检查、行为测试、snapshot 审阅或完整验证位于全图 fan-in 之后。
- 最终格式化或 fix 若可能修改多个任务文件，必须由全图唯一 owner 执行；其 diff 按既有提交
  规则归入独立修正提交或计划声明的边界，不得混入无关任务。

## 工作文档与进度记录

`project-doc-workflow` 继续管理日期目录、历史保留、research 授权和逐任务提交。需要新增的
并行语义只有：

- “单个任务是提交边界”不等于“其他独立任务必须等该提交后才启动”；
- execution graph 是计划正文的权威执行结构；线性清单只能作为展示，不能覆盖依赖图；
- 共享 `execution-log.md`、`current-findings.md` 或其他 research 记录由协调者单写汇总，子代理
  返回结构化结果，不直接并发修改共享日志；
- 汇合节点集成既有任务提交，不得合并提交边界。

当前 ignored research 仍只作为未提交决策记录。本设计不改变 ignored 文件规则，也不允许
强制暂存它。

## 验证设计

### 结构验证

- 对每个修改后的 skill 运行 `skill-creator` 提供的 `quick_validate.py`。
- 检查 symlink 实际目标，确保修改的是当前生效文件而不是影子副本。
- 检查 skill description、reference 路由和相互职责没有形成循环加载或重复权威定义。
- 检查 Git diff 只包含计划列出的提示词、skills、reference 和设计/计划文档，不包含 ignored
  research 或其他用户变更。

### 独立 forward tests

实现后使用不知晓预期答案的独立子代理，以最小原始材料执行现实场景：

1. 两个无依赖、不同提交边界的写任务：应建立隔离 worktree 并同时启动，而不是按编号等待。
2. 同一提交内两个不相交编辑节点：可共享 worktree 并发编辑，但只有 owner 执行格式化、stage
   和 commit。
3. 文件不重叠但消费者依赖生产者接口：必须保留产物稳定边，不能误并行。
4. 一个分支失败、另一分支独立：只暂停失败域，插入修正节点后恢复后继。
5. sequential runner 与共享 Git index：必须通过资源锁互斥，不把锁误写成全局计划串行。
6. 未确认设计/计划或缺少风险授权：并行调度不得绕过门禁。
7. 计划精确声明多个 Codex GUI worktree：确认计划后应先完成全部预配且不重复询问，再启动
   实现图；任一参数漂移或计划外创建仍必须重新确认。

评估重点是代理实际产出的执行图、调度顺序、资源所有权和暂停范围，不匹配固定措辞、标题或
正则。forward test 生成物放在隔离临时目录，不污染工作树。

### 回归审计

最后独立审计所有被保留的安全与授权边界，特别检查：

- 逐任务提交没有被弱化成可合并提交；
- `AGENTS.md` 写入门禁没有被计划授权替代；
- 并行 agent 不能共享 Git index 并发 stage/commit；
- 只读、准备、ignored、force、安装、远程 Git 和真实验证顺序仍然有效；
- 调度器没有用“增加代理数量”替代 ready-set 执行证据。
