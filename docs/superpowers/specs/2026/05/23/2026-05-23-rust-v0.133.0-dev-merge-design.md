# rust-v0.133.0 dev Merge Design

## 背景

`dev` 是当前 fork 的集成分支，承载本地核心 overlay：thread projection，以及 fork 专属 release、update 和 package channel 定制。当前目标是设计如何把官方 `rust-v0.133.0` 单向合入 `dev`，同时保留本地 overlay 和 fork channel 约束。

本设计不是一次从零迁移 projection。projection 已经作为本地 overlay 存在于 `dev`，包括：

- `thread/projection/attach`
- `thread/projection/detach`
- `thread/projection/event`
- projection subscription、`subscriptionId`、`headCommitId`
- per-thread `commitId` / `parentCommitId` chain
- listener-ordered attach
- projection generation gate
- projection snapshot canonical reconstruction reuse

官方 `rust-v0.133.0` 仍然没有 thread projection API 或 runtime。因此本次继续采用 `tag merge + overlay preservation` 模型：先接受官方 tag 的真实结构，再把本地 overlay 作为最小接线重新落回新结构。

## 已确认现状

- 当前分支：`dev`

- `rust-v0.132.0`：`13595c36e218fcbd13df118eeadf00d4eb0e6d31`

- 当前工作区没有处于 merge-in-progress 状态。
- 一次手动 merge 预演曾显示明确内容冲突集中在：
  - `.github/workflows/rust-ci-full.yml`
  - `codex-cli/bin/codex.js`

  - `sdk/python/scripts/update_sdk_artifacts.py`

这些冲突是设计依据，不表示当前仓库仍处于冲突状态。

## 目标

- 把官方 `rust-v0.133.0` 合入 `dev`。
- 保留官方 0.133 的 CI、package layout、app-server API、TUI、goals、permissions、plugins、extensions、Windows sandbox、network MITM 和 SDK/runtime packaging 变化。
- 保留本地 projection overlay 的 API、runtime、lifecycle、测试、schema 和 README 契约。
- 保留 fork 专属 npm/update/release channel，不恢复上游 OpenAI-only package side effects。
- 让最终树状态能作为后续 tag merge 的干净基线。
- 让验证范围聚焦在本次真实风险面，不默认跑全量测试或 release build。

## 非目标

- 不把 `dev` 合回 `main` 或上游。
- 不把 projection 改写成 upstream-ready PR。
- 不把 projection 退化成 `thread/read`、`thread/turns/list` 或普通 notification stream 的组合。
- 不通过整文件覆盖回退 0.133 的结构变化。
- 不手工维护 generated schema/TypeScript 的最终内容。
- 不主动运行全量测试或 release build；全量测试需要单独确认。

## 关键决策

### D1: 接受 0.133 reusable CI workflow

`rust-v0.133.0` 把 `rust-ci-full.yml` 的 tests job 从单个 monolithic matrix 拆成多个 reusable workflow 调用：

- `tests_macos_aarch64`
- `tests_linux_x64_remote`
- `tests_linux_arm64`
- `tests_windows_x64`
- `tests_windows_arm64`

每个平台 job 调用 `.github/workflows/rust-ci-full-nextest-platform.yml`，由该 workflow 负责 nextest archive、4 shard test run、runtime helper artifacts、Windows ARM64 cross archive、platform result 聚合。

本次合并应接受这个上游结构，而不是把旧 `tests` matrix job 拼回去。理由：

- 这是 0.133 的生产 CI 结构升级，不是局部文案变更。
- Windows ARM64、runtime helper artifact、Dev Drive/MSVC setup 等新逻辑集中在 reusable workflow 中。
- 保留旧 monolithic job 会让 fork 立刻偏离 0.133 后续维护路径，后续 tag merge 会重复冲突。

fork 层只允许做必要最小重放：

- runner / runner group / runner label 与 fork CI 环境保持一致。
- `remote_env` 保持在 Linux x64 remote test job 上。
- release/update channel guard 保留在对应 release workflow 或 update path 中，不塞进 tests workflow。

### D2: `codex.js` 接受新 package layout，但保留 fork npm scope

`rust-v0.133.0` 的 launcher 支持新的 native package layout：

- 主二进制优先从 `vendor/<target-triple>/bin/codex` 读取。
- PATH helper 优先从 `vendor/<target-triple>/codex-path` 读取。
- 兼容旧 layout：`vendor/<target-triple>/codex/codex` 和 `vendor/<target-triple>/path`。

本次合并应接受上游 `resolveNativePackage()` 结构和新旧 layout fallback。fork 层保留：

- platform package 名全部使用 `@jiangshengdev/codex-*`。
- meta package 更新命令使用 `@jiangshengdev/codex@latest`。
- `CODEX_MANAGED_PACKAGE_ROOT`、`CODEX_MANAGED_BY_NPM`、`CODEX_MANAGED_BY_BUN` 行为跟随上游。

不要恢复 0.132 旧 launcher 的 `vendorRoot` / `archRoot` 单一路径模型。

### D3: npm package script 接受 `codex-package` component

`codex-cli/scripts/build_npm_package.py` 在 0.133 中引入 package archive layout：

- `CODEX_PACKAGE_COMPONENT = "codex-package"`
- `CODEX_PACKAGE_ENTRIES = ("codex-package.json", "bin", "codex-resources", "codex-path")`
- platform package native components 改为包含 `CODEX_PACKAGE_COMPONENT`

本次合并应接受这些结构变化。fork 层保留：

- `CODEX_NPM_NAME = "@jiangshengdev/codex"`
- `CODEX_PLATFORM_PACKAGES[*]["npm_name"] = "@jiangshengdev/codex-*"`
- 注释中的 published package scope 使用 `@jiangshengdev/codex`

不要把 package archive layout 回退成逐 binary component staging。

### D4: Python SDK/runtime artifact script 接受新 runtime package root

`sdk/python/scripts/update_sdk_artifacts.py` 在 0.133 中引入：

- `RUNTIME_PACKAGE_ROOT = Path("src") / "codex_cli_bin"`
- `CODEX_PACKAGE_METADATA = "codex-package.json"`
- 基于 packaged runtime metadata 的 artifact 更新逻辑

本次合并应接受这些结构变化。fork 层的 distribution name 必须与当前 release workflow 和 package policy 保持一致。如果本地发布面已经定为 `jiangshengdev-codex` / `jiangshengdev-codex-cli-bin`，则保留 fork 名称并接入上游新增常量；如果 Python SDK 仍明确跟随上游 `openai-codex` 发布面，则不能只改冲突文件，必须在 release workflow、pyproject、runtime setup 和测试中一起确认。

本设计默认保持预演冲突中展示的 fork distribution name，不在本次 merge 中扩大 Python package rename 范围。

### D5: generated schema 后置再生

`ClientRequest.ts` 和 `ServerNotification.ts` 是 generated TypeScript。手动冲突解决只用于让 merge 暂时进入可继续状态，不能作为最终权威结果。

source 层必须同时保留：

- 本地 projection request / notification：
  - `thread/projection/attach`
  - `thread/projection/detach`
  - `thread/projection/event`
- 0.133 新增或转正 API：
  - `thread/goal/set`
  - `thread/goal/get`
  - `thread/goal/clear`
  - `thread/settings/update`
  - `thread/settings/updated`
  - `permissionProfile/list`

source 合并稳定后运行 `just write-app-server-schema`，用生成器统一更新 JSON schema 和 TypeScript fixtures。

### D6: TUI status 冲突做兼容合并

`status_line_setup.rs` 和 `status_surface_preview.rs` 的冲突来自两边都改了 status item 文案：

- 本地新增 `ContextUsedTokens`。
- 上游把 `FiveHourLimit` / `WeeklyLimit` 的描述抽象成 primary / secondary usage limit。

最终应同时保留：

- `ContextUsedTokens`
- 上游 primary / secondary 文案

不要为了减少冲突删除本地 status item，也不要恢复旧的 5-hour / weekly 固定文案。

### D7: projection 仍是本地 overlay

0.133 新增 thread settings、goal、permission profile list 等 API，但它们不替代 projection。projection 的协议、runtime 和 lifecycle 继续作为本地 overlay 保留。

需要复核的接线点包括：

- app-server protocol registry 中的 projection request / notification variant。
- app-server message dispatch 中的 projection processor。
- listener command 中的 projection attach response command。
- typed notification fanout 中的 projection event fanout。
- unload watcher 中的 projection subscriber watch。
- connection close tail 中的 projection cleanup。
- TUI notification handling 中对 projection event 的 no-op / global-none。

这些 hook 只能做 dispatch、delegation、watch 组合或 cleanup 调用。hook 内不保存 projection 状态，不实现 commit chain，不重排官方主控制流。

### D8: `dev` 版本号回到 `0.0.0`

`rust-v0.133.0` 会把 Rust workspace version 带到 `0.133.0`。在 `dev` 上完成 tag merge 后，必须单独恢复 development branch version state：

- `codex-rs/Cargo.toml` 回到 `0.0.0`。
- `Cargo.lock` 中对应本 workspace crate version 回到 `0.0.0`。
- 如果 TUI snapshots 或 generated fixtures 展示版本号，也应同步回到 `0.0.0`。

这一步是 branch-scoped release state，不是上游 0.133 功能冲突的一部分。建议作为独立收尾提交或独立 diff 检查点处理，避免和 CI/package/schema 冲突混在一起。

## 推荐执行顺序

1. 从干净 `dev` 创建 integration branch，例如 `codex/merge-rust-v0.133.0`。
2. 执行 `git merge rust-v0.133.0`。
3. 先处理 handwritten source 和 workflow 冲突：
   - `rust-ci-full.yml`
   - `codex-cli/bin/codex.js`
   - `codex-cli/scripts/build_npm_package.py`
   - `sdk/python/scripts/update_sdk_artifacts.py`
   - TUI status files
4. 暂时解 generated TS 冲突，保证 projection 和 0.133 新 API 都不丢。
5. 复核 projection source 接线点。
6. 运行 `just write-app-server-schema` 统一再生 schema / TypeScript。
7. 恢复 `dev` branch version state 到 `0.0.0`。
8. 做窄验证。
9. 再决定是否合回 `dev` 或提交。

## 验证策略

默认窄验证，不主动跑全量测试或 release build。

### source-shape checks

```bash
rg -n "thread/settings/update|ThreadSettingsUpdated|permissionProfile/list|PermissionProfileList" codex-rs/app-server-protocol/src codex-rs/app-server/src
rg -n "ThreadProjection|thread/projection" codex-rs/app-server-protocol/src codex-rs/app-server/src codex-rs/tui/src
rg -n "@openai/codex|@openai/codex-" codex-cli/bin/codex.js codex-cli/scripts/build_npm_package.py sdk/typescript/src/exec.ts codex-rs/tui/src/update_action.rs codex-rs/tui/src/npm_registry.rs
rg -n "@jiangshengdev/codex" codex-cli/bin/codex.js codex-cli/scripts/build_npm_package.py sdk/typescript/src/exec.ts codex-rs/tui/src/update_action.rs codex-rs/tui/src/npm_registry.rs
```

期望：

- 0.133 app-server API 和 projection 都存在。
- fork npm/update surface 不被 `@openai/codex` 覆盖。
- generated TypeScript 最终来自 schema generator，而不是手工冲突拼接。

### formatting and generation

```bash
cd codex-rs
just fmt
just write-app-server-schema
```

如果 config shape 发生变化且 `ConfigToml` / nested config type 改动要求 schema 更新，再运行 `just write-config-schema`。

### targeted tests

```bash
cd codex-rs
cargo test -p codex-app-server-protocol
cargo test -p codex-app-server thread_settings_update --no-fail-fast
cargo test -p codex-app-server permission_profile_list --no-fail-fast
cargo test -p codex-app-server thread_projection --no-fail-fast
```

如果 TUI status UI 或 snapshots 被实际修改，再运行对应 `codex-tui` 窄测试或 snapshot workflow。不要默认跑 workspace 全量测试；如需全量测试，先单独确认。

## 风险与注意事项

- `rust-ci-full.yml` 如果只保留旧 `tests` job，会绕过 0.133 的真实 CI 结构升级。
- `codex.js` 如果只保留旧 path layout，npm package archive 会构建成功但 launcher 找不到新 layout 中的 binary。
- package script 如果把 `CODEX_PACKAGE_COMPONENT` 丢掉，会破坏 0.133 的 canonical package archive pipeline。
- generated schema 如果手工拼接，后续 `just write-app-server-schema` 会产生二次大 diff。
- projection hook 如果被 `thread/settings/update` 或 goal API 的新增 dispatch 覆盖，客户端会丢失 projection subscription/event 能力。
- `dev` 如果保留 `0.133.0` version，会破坏 branch-scoped version state，并影响后续 release/version bump 判断。
