# Codex GUI 前端数据持久化设计

日期：2026-09-06

状态：设计已确认；按用户后续选择修订为仅 sessionStorage、恢复队列统一人工暂停。实施计划待确认，未实现。

## 1. 目标与范围

为现有 GUI 增加当前浏览器页面会话内的数据持久化，使刷新后能够恢复活动会话位置、输入框草稿和排队消息，并保留发送结果不确定时的处理边界。

用户最新范围是“先只做数据持久化”。本设计不实现多会话激活、后台多会话调度、已激活会话列表或新建会话。现有单活动会话模型、历史导航和会话切换保护继续适用。使用 threadId 标识持久记录不代表同时持有多个运行中的前端会话。

本轮不改变后端会话历史存储，不接入后端 QueueStore，不新增后端接收结果查询或幂等接口，不新增浏览器关闭后的持续任务执行能力。

此前讨论的多会话和新建会话产品选择保留为后续任务的背景，不作为本轮交付或验收条件。本设计不创建实施计划，不授权代码修改、生成、测试或 Git 提交。

## 2. 已确认的产品行为

| 事项 | 决定 |
| --- | --- |
| 保留期限 | 采用浏览器原生页面会话生命周期；刷新可恢复，普通关闭后新开不主动恢复，接受浏览器自身恢复原页面会话的行为 |
| 输入框草稿 | 已有活动会话的输入框草稿跨刷新保留 |
| 消息队列 | 排队消息跨刷新保留，核对后仍统一暂停；用户检查并明确继续后，才按原有规则推进 |
| 提交前保存 | 新消息必须先保存成功，再入队或发送；保存失败保留输入、阻止提交，并提示重试 |
| 发送结果未知 | 保留消息，暂停对应会话的后续发送，等待正向确认或人工处理，不自动重发 |
| 排队消息编辑 | 刷新时丢弃未点击“保存”的修改，恢复队列最后保存的内容，同样等待人工检查后继续 |
| 新建页草稿 | 此前决定刷新后不保留；本轮不新增该页面或实现该功能 |

普通编辑器草稿与排队消息的临时编辑是不同对象，不得把前者的自动保存规则应用到后者。编辑弹层、焦点、选区和进程内编辑 reservation 不作为刷新后的恢复对象。

后续决策：用户选择“仅用 sessionStorage，刷新恢复后的队列统一暂停自动发送，交由用户检查”。它替代此前明确未发送消息自动恢复的行为，不增加跨关闭保留的共享防重发元数据。发送结果未知时不自动重发的独立约束继续生效。

## 3. 当前事实与根本缺口

### 3.1 前端

- `codex-gui/src/features/browserLaunch/browserAuthorizationSession.ts` 使用 `sessionStorage`，键为 `codex-gui.browserAuthorizationSession.v1`，仅保存 token 和可选的 activeThreadId。非空启动令牌 fragment 会建立新的授权快照并清除原恢复会话 ID。
- `codex-gui/src/features/appShell/GuiHostConnectionBridge.tsx` 在启动时优先使用当前会话路由中的 threadId；历史页面使用保存的活动会话 ID。它创建新的活动会话控制器，不装载持久队列。
- `codex-gui/src/app/store.ts` 的 Redux store 保存运行与显示读模型，没有持久化接入。聊天内容通过后端数据重建。
- `codex-gui/src/features/composerEditor/composerDraft.ts` 将 Lexical 状态序列化后放入 WeakMap。现有草稿句柄只能在当前 JavaScript 实例内使用，不能直接 JSON 化后跨刷新恢复。
- `codex-gui/src/features/composerInputQueue/composerInputQueueCoordinator.ts` 新建内存队列，逐条调用 turn/start、turn/steer；恢复批次、发送 claim 和编辑管理状态没有跨刷新恢复入口。
- `composerStartQueueState.ts` 与 `composerSteerQueueState.ts` 的 clientUserMessageId 使用模块级计数器，刷新后可能复用。现有编号不能直接承担持久发送身份。
- `activeThreadSession.ts` 在连接失效时释放会话，在切换成功时释放旧会话并 detach 投影。本设计不能把存储接入当作多会话生命周期改造。

### 3.2 后端与确认能力

- `codex-rs/thread-store/README.md` 定义本地 JSONL canonical history 与 SQLite 查询元数据的职责；分页历史 SQLite 是可从持久 JSONL 重建的查询数据。
- `codex-rs/app-server/src/request_processors/thread_projection.rs` 的快照结合持久历史与当前运行状态，支持重建聊天显示，但不包含 GUI 尚未提交的本地草稿和队列。
- `codex-rs/thread-store/src/queue_store.rs` 已提供后端持久队列，但当前 GUI 未接入。本轮不建立前后端两个队列的双写或同步路径。
- `codex-rs/app-server/src/request_processors/turn_processor.rs` 将 clientUserMessageId 传递为用户输入的 client_id；当前发送链路没有据此提供幂等重试契约。
- `codex-rs/core/src/session/turn_input.rs` 允许 steer 先进入后端 pending input。请求已接收与历史 userMessage 可见之间存在间隔。
- `codex-rs/app-server-protocol/src/protocol/thread_history.rs` 在重建用户消息时保留 client_id，因此唯一标识匹配提供正向确认；未找到标识不能反向证明未送达。

根本缺口是前端缺少可恢复的数据表示与发送前后的持久转换边界，不能通过整体序列化 Redux 或队列对象解决。

## 4. 存储职责与数据边界

### 4.1 载体与隔离

使用 sessionStorage，与已确认的页面会话保留期限一致。授权信息继续由 BrowserAuthorizationSession 拥有；业务数据使用独立、带版本的记录，不把业务字段塞入授权记录，也不复制 token 到每条消息。

持久记录绑定当前 GUI 授权上下文与 threadId。新的授权上下文不得自动消费旧上下文的草稿或队列。当前活动会话恢复 ID 继续只有一个权威来源，不另建第二个可独立修改的“当前会话”字段。

存储版本、记录身份及跨记录引用由明确的格式契约管理。读取失败、版本不兼容或内容损坏必须向调用方传播；不得静默视为空队列、自动删除原始数据或退回无持久化发送。

### 4.2 保存与不保存的内容

| 对象 | 持久内容 | 恢复职责 |
| --- | --- | --- |
| 活动会话位置 | 现有 activeThreadId；页面目标继续由路由表达 | browserLaunch 与现有启动入口 |
| 会话输入草稿 | 编辑器拥有的版本化、可导入内容，包括文本和已有技能节点语义 | composerEditor |
| 排队消息 | 稳定消息 ID、threadId、最后保存的内容、队列顺序及原有通道语义 | composerInputQueue |
| 发送记录 | 稳定 clientUserMessageId、操作类别、必要目标信息、可恢复发送阶段及已确认结果 | 队列和发送协调者 |
| 待恢复消息 | 原有恢复语义所需内容、顺序和原因；未知结果不得改标为未发送 | 队列 owner |

不保存完整 transcript、投影 subscriptionId、Redux store、WebSocket、Promise、回调、计时器、DOM、监听器、WeakMap 句柄、claim/reservation 对象或临时弹层状态。后端事实仍通过 attach/read 获取，不把本地运行状态缓存当作后端真相。

### 4.3 功能 owner 与公共存储层

- 公共存储层只负责有界的读写、存储错误表达和版本信封，不管理会话生命周期、队列调度或重试策略。
- composerEditor 拥有草稿编码与导入，不向其他模块暴露 Lexical 内部状态作为公共业务协议。
- composerInputQueue 拥有可恢复的消息、顺序和发送阶段，将持久数据恢复为新的运行时对象；不复活旧实例的能力句柄。
- 现有活动会话 owner 负责将授权上下文、threadId、后端快照和对应持久记录关联起来。切换仍遵守现有释放条件。
- 后端 UserInput、TurnStartParams、TurnSteerParams 等契约继续直接引用权威生成类型或机械派生；不得在存储模块手工复制协议字段、枚举或验证器。
- 持久格式是明确的前端领域契约。涉及生成协议值的运行时验证必须复用或由权威源机械生成，不能以类型断言替代装载校验。

## 5. 写入与发送的一致性

### 5.1 草稿与入队

普通会话草稿随编辑器提交的内容变化保存，不能依赖离页事件才保存。存储失败时保留当前输入、明确提示未保存状态，并阻止新消息提交，直到保存成功。

提交消息时，把队列新增与源草稿清除视为一个可恢复的业务转换：持久化成功后才向用户发布提交成功和清空输入。不得出现输入已清空但队列尚未保存的窗口。具体记录布局需能表达该转换；不能假定多个 sessionStorage key 的连续 setItem 是一个事务。

队列中的编辑保存、删除、重排同样需要先持久成功再发布成功结果。未保存的临时编辑不替换持久消息；刷新后释放临时编辑语义，使用最后保存的队列版本。

### 5.2 发送记录

每条逻辑提交使用跨刷新稳定、不复用的 clientUserMessageId。标识先写入持久记录，再用于实际请求；恢复不能重新分配同一逻辑提交的身份，也不能与刷新前的其他提交碰撞。

必须在调用发送接口之前保存“发送已准备/可能发起”的边界。刷新落在保存与发送之间时，可以保守恢复为待核验，但不能猜测为未发送。网络副作用与浏览器存储没有跨系统事务，本设计不承诺恰好一次执行。

收到确定响应或运行时确认后先更新持久记录，再依据该事实释放后继发送。若保存确认结果失败，应阻止继续推进依赖该结果的队列转换；后端已运行的任务不因此自动停止。下次恢复允许通过后端正向证据重新确认。

自动清理已确认消息时不得同时丢弃其尚需用于恢复判断的信息。记录何时可删除由队列 owner 依据恢复不变量确定，而不是由公共存储层按条数或时间擅自淘汰。

## 6. 刷新后的恢复流程

1. 读取并校验授权上下文及对应业务记录。无记录是正常初始状态；读取失败和损坏记录不是无记录。
2. 在导入持久队列之前建立本实例的人工恢复 gate，再按现有路由和 activeThreadId 规则打开会话、获取快照及运行状态。核对完成也不自动解除暂停。
3. 导入该会话的普通草稿，并用持久队列记录构造新的队列对象。排队消息临时编辑按最后保存版本恢复，不恢复编辑 reservation。
4. 对发送记录分类：
   - 本地记录显示尚未进入发送边界的消息也先暂停；复制页面的本地记录可能过期，不能据此自动发送。
   - 持久响应或唯一 clientId 对应的后端正向证据足以确认的消息，不重复发送；具体后续阶段仍按原有队列契约恢复。
   - 可能发起但没有充分确认的消息保持结果未知，保留原文并阻塞后继，等待后续正向确认或人工处理。
5. 核对后的状态保存成功后展示恢复队列及“检查后继续”入口。用户在本实例明确继续才解除恢复暂停；结果未知、待恢复批次、存储失败和原有调度约束仍分别生效。不得以快照中没有消息、超时或重复刷新为自动重发依据。

人工继续许可不持久化；刷新、从存储重新导入或 BFCache 页面恢复时重新暂停。队列管理、保存重试、快照到达、turn 完成和新消息提交均不能旁路解除暂停。本实例人工继续后可正常调度，下一次恢复仍需检查。

现有恢复动作若没有跨刷新所需的原能力对象，必须重新以持久领域记录建立合法操作；不得伪造旧 claim 或调用旧实例的回调。人工处理未知消息也不等于自动授权重发。

## 7. 浏览器边界与失败处理

sessionStorage 按页面会话隔离，但 opener 可能使新页面获得其初始副本；浏览器自身也可能恢复页面会话。不能仅凭“使用 sessionStorage”推断两个页面绝不会拥有同一份待发送记录。

用户选择以统一人工暂停解决自动重放问题，不增加共享元数据或跨标签页发送所有权机制。原页面正常运行不受复制影响；副本无论原页是否存活都先暂停。保证是“没有本实例的用户操作就不重放恢复队列”，不是“多个页面分别得到用户继续操作后仍全局恰好一次执行”。界面应提示检查其他页面和历史，不能把本地未发送标记当作全局证明。

写入额度不足、访问被禁用或序列化失败时，明确报告失败并保留输入，不自动截断、淘汰待发送消息、静默退回内存发送或把持久失败当作提交成功。存储恢复前仍可展示已获取的历史与运行结果，但不能越过依赖持久化的提交边界。

浏览器关闭、进程崩溃或浏览器会话恢复不等于后端任务终止。本设计只规定 GUI 数据保留和恢复，不承诺关闭后继续推进浏览器内的未发送队列。

浏览器行为依据：[MDN sessionStorage](https://developer.mozilla.org/en-US/docs/Web/API/Window/sessionStorage)。用户已明确接受浏览器原生行为。

## 8. 验收边界

本节是设计验收条件，不是实施任务清单或已完成验证。

- 刷新恢复现有活动会话位置和普通草稿，技能节点内容由编辑器正确导入。
- 队列内容、通道、顺序和最后保存的编辑结果恢复正确；临时编辑不写回已保存消息。
- 入队、草稿清除、发送准备、确认和后继推进的持久转换失败时，不发生输入丢失或未保存消息发送。
- 刷新前后 clientUserMessageId 稳定且不复用；正向确认不会误认刷新前其他消息。
- 覆盖请求未发起、可能已发起、响应未保存、后端已接收但消息尚不可见、消息已经持久可见等窗口。未知结果阻塞，不能依赖缺席证据重发。
- 覆盖损坏记录、版本不兼容、存储不可写及授权上下文变化，不静默清空或自动消费旧上下文。
- 覆盖普通刷新、页面恢复、BFCache、复制页及原页退出后的旧副本；没有本实例人工继续时不发送恢复消息，人工继续不解除未知结果的独立阻塞。
- 保持现有单活动会话切换保护；不以本轮验证声称已支持多会话后台运行或新建会话。

Level 1 需要针对真实浏览器存储及队列行为做自动化回归；Level 2 需要基于当前实际 Codex runtime 验证刷新恢复与发送核对。Level 3 仅在验收结果依赖可见桌面行为时适用，需另行授权。本轮只落盘设计，三个级别均未执行。

## 9. 进入实施计划前需闭合的技术事项

- 明确现有队列各运行阶段的可恢复领域表示，尤其是 start/steer 结果未知、停止结果未知、待恢复批次与临时编辑的区分。
- 明确草稿清除与入队、消息更新与发送阶段的原子持久边界，不引入双权威存储或临时双写。
- 用户已确定恢复后统一人工暂停；验证每个导入和页面恢复入口先建立 gate，旧许可不能跨刷新或页面恢复复用。不再设计共享元数据所有权机制。
- 明确格式校验、升级与不可读记录的显式处理路径，不把不兼容记录静默迁移为空状态。
- 将变更映射到生产启动入口、功能 owner、权威协议生成链与现有验证入口，并完成必要的独立影响面核对。

这些事项是计划前的技术闭包，不要求用户选择存储实现细节，也不授权提前实现。若调查表明必须改变上述已确认产品行为或增加后端范围，应单独说明新证据并请求对应范围决策。
