# Codex GUI steer 响应与终态乱序收敛设计

日期：2026-09-10

关联问题：QR-B09-004。

状态：用户已确认设计、“继续发送”授权范围及测试入口，授权设计和计划落盘。本文为设计规格，不是实施计划；尚未修改产品代码或执行验证。

## 问题陈述

用户在运行中的 turn 提交 steer 后，如果目标 turn 的 terminal 先到、steer 的 accepted 后到，且该消息没有 userMessage commit，GUI 会一直将消息保留为交付中的只读 pending。用户无法正常处理这条消息，队列也不能安全释放；晚到 accepted 本身还缺少对后续 start 的调度。

当前 GUI 在 terminal 到达时保留 issuing，避免将交付未知的消息误判为可重发；但 accepted 随后只把它改成 acceptedAwaitingCommit，没有重新处理已经记录的 terminal。accepted 先到的顺序已有终态处理，因此两种顺序产生不同的消息归属和调度结果。

后端 accepted 表示输入进入 pending，不保证已写入对话历史。独立中断任务可以终止尚未消费的输入，且终态通知与成功响应没有响应先行的同步屏障。本次静态调查已闭合生产可达路径，尚未运行真实竞态复现。普通 turn/steer 与 turn/interrupt RPC 按 thread 串行，不能将“紧接着点击停止”直接视为该竞态的生产证据。

缺陷归属是 GUI 队列状态收敛，不以修改 Rust 后端契约为修复前提。影响不应扩大描述为“此后所有新消息永久无法发送”：其他独立调度仍可能启动新 turn，但不会因此清理旧 pending。

## 解决方案

使 steer 成功响应与原目标 turn 的 terminal 无论以哪种顺序到达，都能在交付事实充分后完成一致的消息归属处理，并沿现有规则推进队列。

本地停止后的消息保留在手动恢复区；非本地中断及其他终态沿用既有 rejected 消息排序和调度规则。未知交付不会因收到裸 terminal 而自动重发；已 commit 的消息不会再次恢复或发送。

用户已选择：一次“继续发送”只覆盖操作时恢复区内的消息。此前恢复内容已被消费后，旧目标才晚到确认、且没有 commit 的消息，需要重新进入待恢复状态，再次由用户决定发送。恢复操作不授权未来才确认的消息自动发送。

## 用户故事

1. 作为 GUI 用户，我希望 steer 成功响应晚于 turn 终态时消息也能收敛，以免一直看到交付中的只读内容。
2. 作为 GUI 用户，我希望响应顺序不改变消息是否需要恢复，以便获得一致的消息处理结果。
3. 作为 GUI 用户，我希望已写入对话历史的消息不再进入恢复区，以免重复发送。
4. 作为 GUI 用户，我希望交付未知的消息继续保留，以免系统错误丢弃我的输入。
5. 作为 GUI 用户，我希望交付未知的消息不被自动重发，以免同一指令被执行两次。
6. 作为 GUI 用户，我希望本地停止后的未提交消息等待手动恢复，以便保留对发送的控制。
7. 作为 GUI 用户，我希望晚到确认的本地停止消息能加入已有恢复内容，以免消息分散或丢失。
8. 作为 GUI 用户，我希望一次“继续发送”只处理当时恢复区内的内容，以便明确这次操作的发送范围。
9. 作为 GUI 用户，我希望此前恢复区已被消费后，晚到确认的消息重新等待手动恢复，以免出现未经本次确认的发送。
10. 作为 GUI 用户，我希望 terminal 当时没有形成恢复区时，后来确认的消息仍按原目标的停止归属处理，以免空恢复区改变发送规则。
11. 作为 GUI 用户，我希望非本地终止后的消息沿用现有恢复和排队规则，以免本次修复改变正常使用习惯。
12. 作为 GUI 用户，我希望 rejected 消息与普通排队消息保持既有优先级和顺序，以免后到响应打乱发送次序。
13. 作为 GUI 用户，我希望旧 turn 的晚到响应只处理属于它的消息，以免影响当前 turn 的输入。
14. 作为 GUI 用户，我希望重复响应、重复终态和过期回调不会重复消费消息，以免产生重复恢复或错误计数。
15. 作为 GUI 用户，我希望刷新或重连后仍保留原有停止意图，以免恢复过程擅自发送消息。
16. 作为 GUI 用户，我希望持久化失败时保留原有消息和恢复能力，以免状态只在界面上看似成功。
17. 作为 GUI 用户，我希望最后一条滞留消息完成处理后，不再有该消息留下的安全释放阻塞，以便正常结束会话管理。
18. 作为维护者，我希望通过现有公开队列入口验证这些行为，以免测试依赖内部字段排列或专用测试接口。

## 实现决策

- 修复集中于 GUI 的 steer 队列、组合输入队列、coordinator 与相关持久化表示。复用现有恢复交互，不新增按钮或改变 TUI。
- accepted 的入口保持既有 claim 归属校验；响应 turn 与预期目标不匹配时，继续按原有未知归属规则处理，不能进入正常终态收敛。
- 对合法 accepted，统一检查原目标是否已关闭。目标未关闭时继续等待 commit；目标已关闭且消息尚未 commit 时，执行该目标的既定终态处置。
- thread、turn、client ID 与 claim 生命周期共同约束消息所有权。不能依据当前活动 turn、当前恢复区是否为空或响应到达时间推断旧消息归属。
- 目标终态处置由一个权威 owner 保存，包含晚到响应所需的本地停止语义，并进入现有持久化和恢复链。不得另建与原终态记录并行的权威来源或双写同步路径。
- 本地停止归属遵循既有 interrupt 分类。它代表保守保留本地停止意图，不要求证明后端终止一定由该请求触发。不要混淆 interrupt 的 unknown 与 steer 的交付未知。
- 本地停止后的晚到确认消息进入手动恢复区。已有 userStopped 恢复内容时通过原有所有权机制汇合，保持一个有效恢复 owner；不得直接发出相互冲突的第二个 recovery batch。
- 原恢复内容已被消费或从未形成时，晚到确认消息仍依据原目标的停止语义形成待手动恢复内容。此前的“继续发送”不授权这些后来才确认的消息自动发送。
- 非本地中断和其他终态继续使用既有 rejected 消息优先级、顺序及调度屏障。晚到 accepted 完成收敛后补齐必要调度，不绕过正在运行的 turn、pending start、编辑、恢复或自动发送暂停约束。
- 收敛只消费对应消息一次。已被有效 commit 消费的 claim、重复 settlement、重复 terminal 和过期 generation 均不能重建已消费消息或再次释放所有权。
- bare terminal 继续保留 issuing、deliveryUnknown 和 responseTurnMismatch 等未确认交付状态。只有符合既有契约的后续事实才能改变其归属，不新增超时猜测或自动重试。
- 状态变更、恢复区合并、计数和所有权变化通过既有持久化事务提交。失败时保留原状态和可恢复事实，不能提前发布成功状态或发出发送效果。
- 服务端权威协议继续由 Rust 定义并机械派生 TypeScript 类型和运行时校验产物；本次不新增协议字段或消费者手写协议镜像。新增的目标处置语义属于 GUI 领域状态。
- 目标处置记录的具体类型、生命周期清理和持久化变更清单在实施计划中明确；必须覆盖仍有未决消息和恢复所有权的生命周期，不因目标 turn 已结束而提前丢弃所需语义。

## 历史数据迁移

用户已确认：旧格式一次性转换，终态处置缺失时使用明确的手动恢复语义，不推断 local/nonLocal。恢复 snapshot 先匹配 pending 的 commit；未提交的 accepted 转入手动恢复，unknown 保留且不自动发送。已转移 owner 保持既有恢复路径。成功后仅写新格式，临时存储失败保留原记录并可重试；非法记录显式报错，不当空队列恢复。

## 测试决策

已确认测试入口：以 Composer 输入队列 coordinator 的公开操作、accepted projection 事件入口和现有持久化恢复入口作为主要验证边界；仅在高层入口不足时补充 steer 状态机定向用例。用户随后回复“确认，落盘计划”。

好测试应断言用户可观察的消息内容、恢复区、pending 展示、发送效果、消息顺序、安全释放状态及失败后的恢复能力；不以私有集合名称、局部字段排列或辅助函数调用次数代替行为验证。优先复用现有测试夹具，不增加测试专用生产接口。

- 复用现有 coordinator steer delivery 测试中可控的异步响应，分别驱动 accepted 先于 terminal、terminal 先于 accepted，在没有 commit 时比较最终消息归属和应产生的调度。
- 覆盖正常完成、非本地中断和本地停止处置；区分生产可达性证据与前端入口的防回归事件序列，不把构造序列称作真实后端复现。
- 本地停止覆盖已有恢复内容、terminal 时无恢复内容、原恢复区已被用户消费三种情形；最后一种必须断言晚到消息再次等待手动恢复且没有自动发送。
- 覆盖晚到消息与既有恢复 owner 的汇合，断言消息不丢失、不重复、排序保持约束，且单次恢复不消费未来才确认的内容。
- 覆盖有效 commit 先于 settlement、重复 settlement、重复 terminal、错误 thread/turn/client ID、旧 generation 和目标结束后已有新 turn 的情形。
- 覆盖未知交付及响应目标不匹配，证明裸 terminal 不会让消息成为可自动重发内容；保留现有人工处理与恢复屏障。
- 复用既有 interruption recovery、coordinator persistence 和 projection recovery 测试模式，验证目标处置语义跨持久化恢复保留、事务失败回滚及再次恢复后的行为。
- 仅当高层入口不足以清晰定位所有权边界时，补充 steer 状态机定向测试；不为同一行为机械铺满每一层。
- Level 1：适用；以队列和 coordinator 自动化回归为主，现有恢复交互需要时补充浏览器行为验证。尚未执行。
- Level 2：真实运行时的完整竞态尚未复现。后续计划应分别记录真实恢复交互与竞态场景能否合法构造；未执行的场景不能由合成序列或自动化通过替代。
- Level 3：当前设计不依赖可见桌面状态，不适用。
