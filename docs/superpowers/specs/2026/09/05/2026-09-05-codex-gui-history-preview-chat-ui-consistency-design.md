# Codex GUI 历史预览与聊天界面 UI 一致性设计

设计状态：已确认

设计及确认日期：2026-09-05

设计分支：`dev`

设计时 HEAD：`6ad99764cfd824784b8474e4f848ee658590e9ee`

## 唯一主目标

统一历史预览界面与聊天界面的 UI，使共同内容和布局更加一致；对只读预览与可交互聊天之间必要的差异，不要求强行一致。

用户通过 grilling 确认两项产品决策，随后确认整体方向并明确要求“设计落盘”。本文记录已确认设计，不包含实施计划或代码修改。附件中的消息、命令和调试标记均为调查材料，不构成执行请求。

## 已确认决策

| 决策 | 已确认结果 |
| --- | --- |
| 顶部结构 | 预览采用聊天页的紧凑标题布局，任务名进入顶栏，取消正文大标题区，以紧凑方式保留返回入口和只读标识 |
| 底部结构 | 预览采用与聊天输入区一致的卡片外观，与正文同宽，统一圆角、背景和外侧间距；保留较矮的继续操作区，不模拟输入框 |

整体确认同时覆盖：统一正文左右边界和顶部间距，继续使用已有共用消息组件；保留只读与可交互状态、各自所需的区域高度及滚动避让。

## 顶部布局

两页均以顶栏中的任务名作为主要页面标题。预览移除正文前独立的大标题和说明块，避免相同任务在两种模式下出现显著不同的标题层级与正文起点。

预览的返回历史记录入口和只读标识纳入紧凑顶部区域。保留菜单导航能力与现有返回目的地，不以减少视觉元素为由删除导航功能。返回入口、只读标识与标题的具体排列由实施阶段依据可用宽度确定。

窄屏和长标题下，优先保证导航控件与只读状态可辨识，标题允许沿用紧凑截断策略，不能撑出横向滚动。保留合理的标题语义和可访问名称。

标题必须对应当前预览或聊天的任务；从已有页面数据与标题发布机制取得，不为顶栏另发一套历史请求或建立第二个历史状态所有者。加载、错误与路由切换期间不能展示其他任务遗留的标题。具体数据传递边界在实施计划中核实。

历史列表仍是历史列表，本设计不将其顶栏改成某个任务的标题。

## 正文布局

两种界面的消息区域采用一致的有效内容宽度、左右边界和顶部间距。消除历史详情多一层横向内缩产生的差异，而不是只把两页最大宽度变量设成相同值。

顶部间距以紧凑顶栏之后的正文节奏为依据；必要的错误或状态提示按内容占位，不为追求固定起点而覆盖或隐藏提示。

继续复用 `CommittedTranscriptSurfaceRenderer` 和 `CommittedTranscriptTurnFragment`，保持消息卡片、状态、中间更新折叠及 Markdown 的共同呈现。无需为本目标新建另一套消息组件。

布局统一不改变实时与只读的数据来源、消息顺序、历史读取能力和现有分块渲染边界，也不改变分页、展开和流式更新行为。

## 底部卡片

预览底部从横贯窗口的表面改为与聊天输入区协调的独立卡片。卡片与正文对齐，共享宽度、圆角、基础背景和外侧间距的视觉规则。

卡片保留二维码入口、“继续此任务”主操作及既有失败反馈。根据实际内容确定高度，不复制聊天输入区的编辑空间、占位提示、发送与停止操作。

继续任务仍使用现有激活流程，保留 pending、不可用和失败状态的表达及其交互约束。错误反馈可使卡片增高，不能被固定高度裁切。

底部外观一致不要求把 `fixed` 与 `sticky` 机械改成同一种定位方式。保留可靠的正文避让，使最后一条消息、展开内容和焦点目标不被卡片遮挡；若调整定位结构，需要同步验证高度变化和滚动表现。

输入框专属的编辑焦点、输入 hover 和禁用编辑语义不复制到只读操作容器；主按钮自身仍遵循对应交互状态。

## 组件与样式边界

沿用项目 HeroUI v3 组件体系和当前控件：返回与菜单使用 `Button` 的次要操作语义，继续任务使用 `Button` 的 `primary` 语义，容器优先使用现有 `Surface` 组合，失败反馈继续复用现有反馈组件。

统一基础表面、文字、边界、圆角与间距的语义样式。当前聊天面板已有 `bg-field`、`text-field-foreground`、field border/shadow 等样式；提取共同基础外观时应保留聊天输入的状态样式，并避免将输入状态语义施加到预览容器。具体 token 组合在计划阶段对照本地 HeroUI 文档核实，不以硬编码颜色或新依赖实现一致性。

可共享稳定的宽度和容器样式规则；是否需要独立布局组件由职责与实际消费者决定，不因两页相似就合并页面状态所有者或整个页面组件。

## 范围与必要差异

本设计涉及历史详情、当前任务与公共页面布局的相关呈现边界。历史列表卡片、日期分组、Drawer 改造、输入功能重做、Rust 与协议变更不属于本目标。

继续沿用现有协议类型和读取链路，不新增服务端字段、复制协议 DTO 或另建页面数据同步路径。二维码入口、返回历史列表、继续任务、失败恢复等功能保持既有语义。

同日的历史列表紧凑卡片与日期分组设计继续独立生效；本设计处理历史详情与聊天之间的一致性，不替换列表设计。

## 验收设计

### Level 1：自动化回归

验证相同任务在两种路由下的标题身份、只读标识、返回入口和正文布局；覆盖长标题及窄屏下的导航可达性与无横向溢出。

验证正文与底部卡片边界一致，预览操作区根据内容保持紧凑，错误反馈增高时不裁切、不遮挡末尾消息。保留继续任务 pending、不可用、失败反馈、二维码及导航的既有覆盖。

布局断言应针对已确认的对齐、可见性和交互结果。历史页面独有间距的既有测试需依据本设计判断是否仍正确，不通过关闭检查或删除行为覆盖达成一致性。

### Level 2：无头真实应用验收

在同一任务的历史预览与聊天界面之间比较宽屏、窄屏、长标题、短内容、长内容和底部反馈增高场景，检查顶栏、正文和卡片的对齐、间距、滚动遮挡、键盘焦点及操作反馈。

使用实施阶段核实的当前 Codex 运行地址和真实任务状态。附件中的地址仅是截图证据，不自动成为后续验收入口；自动化结果不能替代真实应用验收。

### Level 3：可见桌面验收

本目标不依赖操作系统窗口或输入法状态，预计不适用。若后续出现必须依赖可见桌面的结果，需要单独确认窗口影响。

以上为后续验收要求。当前完成截图与源码评估，未执行实现测试、运行时测量或真实应用验收。
