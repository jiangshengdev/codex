# Codex GUI 历史详情连接恢复设计

日期：2026-09-09

关联问题：QR-B04-001（P2）。

状态：主目标已确认；用户选择 A「连接恢复后等待手动重试」，并要求将设计落盘。本文整理已讨论方案，不包含实施计划或实现。测试边界随本文提交用户核对。

源码核查基线：`dev`，`0ad31f5b4f890cda61ee76ce7443675daa49b14a`。当前证据为源码与既有测试内容的只读核查，不代表运行验收通过。

## 问题陈述

用户打开历史详情时，如果读取失败，或者读取期间连接被替换，即使新连接已经恢复，点击加载历史记录仍然失败。退出详情再进入可以重新取得读取能力，但页面内的重试不能自行恢复。

根因是历史详情永久保存首次取得的 `readThread`。旧连接失效后，这个函数仍指向旧 gateway；新连接拥有的新读取能力没有进入详情 owner。原本为了断线时保留历史内容，却连同旧读取能力一起永久保留。

这是一项局部恢复缺陷，不代表整个应用不可用，也不意味着历史内容已经丢失。

## 解决方案

将已加载的只读内容与当前可用的读取能力分开管理。内容按所查看的 thread 保留，后续请求采用当前连接提供的能力。

用户已经选择：失败或中断的读取，在连接恢复后不自动重试；用户点击加载历史记录时才发起新请求。

| 情况 | 预期行为 |
| --- | --- |
| 首次进入，连接可用 | 正常读取当前 thread，保留现有首次加载表现 |
| 首次进入，尚无连接且从未开始读取 | 等待连接；连接首次可用时正常开始首次读取，不制造加载失败 |
| 已加载成功后断线或更换连接 | 保留内容与标题，不自动刷新 |
| 读取已失败，随后恢复连接 | 保留失败信息，等待用户手动重试 |
| 首次读取或重试途中连接失效、被替换 | 结束本次进行中状态，显示中断失败，等待手动重试，不持续转圈 |
| 连接尚不可用时处于失败状态 | 保留失败说明与诊断；不提供可执行的读取动作，不调用失效能力 |
| 恢复连接后点击重试 | 使用当前读取能力，请求当前 thread；进行中防止重复请求 |
| 新尝试成功或失败 | 成功展示详情；失败更新对应错误，继续允许后续手动重试 |
| 同一详情组件切换到另一 thread | 按新 thread 开始正常加载；无连接时等待连接，不展示上一 thread 的内容 |
| 旧连接或旧 thread 的请求迟到 | 不得覆盖当前内容、错误或执行状态 |

首次读取与失败后的重试分别处理：选择手动重试不意味着首次进入和正常切换历史记录也需要额外点击。

## 用户故事

1. 作为查看历史记录的用户，我希望连接可用时进入详情就能加载内容，以便沿用现有阅读流程。
2. 作为首次进入详情但连接尚不可用的用户，我希望页面说明连接依赖，以便知道为什么还没有内容。
3. 作为等待首次加载的用户，我希望连接首次可用后开始读取，以便不必额外点击。
4. 作为已经加载历史记录的用户，我希望断线时内容和标题仍然保留，以便继续阅读。
5. 作为已经加载历史记录的用户，我希望重连不会自动刷新内容，以便阅读不被加载过程打断。
6. 作为读取失败的用户，我希望重连后由我决定何时重试，以便保持明确的操作控制。
7. 作为读取中途断线的用户，我希望页面结束等待并说明失败，以便知道需要再次操作。
8. 作为点击重试的用户，我希望请求通过当前连接读取当前记录，以便无需退出页面就能恢复。
9. 作为正在重试的用户，我希望仍能查看上次错误与诊断，并避免重复触发，以便了解状态且不产生重复请求。
10. 作为重试再次失败的用户，我希望看到本次失败信息并保留重试机会，以便继续处理问题。
11. 作为切换历史记录的用户，我希望看到新目标的加载状态和内容，以免误把旧记录当作新记录。
12. 作为查看历史记录的用户，我希望迟到的旧响应不会覆盖当前页面，以便内容与所选记录保持一致。
13. 作为只读查看历史的用户，我希望加载和恢复读取不会自动激活会话或发送输入，以便查看行为保持只读。

## 实现决策

### 职责与生命周期

- `ThreadHistoryDetailPage` 向详情 owner 提供当前可用的读取能力，包括不可用状态；删除永久保留首次读取能力的做法。
- `ThreadHistoryDetailOwner` 继续作为详情内容、错误、执行状态和请求归属的唯一所有者。连接替换更新能力，不通过重建整个详情 owner 清除已经加载的内容。
- owner 的内容归属由 thread 身份确定；切换 thread 时隔离旧 owner 的内容和异步结果。重试回调在执行时使用当前能力，不捕获永久不变的首次能力。
- 能力失效或替换时，使关联的在途请求失去发布资格，并完成中断状态转换。旧请求随后成功或失败，都不能再次改变当前状态。
- 请求结果只有在 owner 仍有效、thread 与请求归属仍一致、能力与请求仍为当前版本时才能发布。保留现有请求代次与销毁保护，并覆盖连接替换这一新的失效边界。
- 保留 StrictMode 生命周期约束，避免订阅重放产生重复读取或错误销毁；不新增全局缓存、持久化状态或第二份详情快照。

### 展示与交互

- 沿用现有详情内容、失败面板、诊断入口和重试按钮组合，不重新设计布局或增加独立刷新入口。
- 重试保持既有 `Load task history` 与 `Loading task history…` 行为：执行期间保留上次错误，禁止同一动作重复触发；失败更新错误，成功解除对应错误。
- 动作可用性由当前连接和 owner 状态决定；底层请求门禁仍需生效，不能只依赖按钮状态阻止失效调用。
- 继续任务仍由现有 `ActiveThreadSession` 能力及其门禁决定。保留快照不意味着断线期间允许继续任务。

### 权威合同与保留约束

- 读取能力直接沿用 `GuiHostCommands["readThread"]`；请求与响应依赖现有生成协议及 request descriptor，保持编译期合同传播，不复制 DTO 或校验器。
- 请求继续携带当前 `threadId` 和 `includeTurns: true`。
- 保留响应 `thread.id` 与请求 `threadId` 的一致性检查；不匹配的响应不得进入 ready 状态。
- 读取失败与连接中断必须可观察，不以静默忽略、伪造成功或删除只读快照消除错误。
- 历史读取不新增 `thread/resume`、`thread/projection/attach` 或输入发送，不修改连接生命周期、gateway 或后端协议的职责。

## 测试决策

优先复用现有历史详情页面集成测试入口：通过 capabilities store 发布连接能力变化，操作真实渲染的页面，并观察请求与用户可见结果。它可以同时覆盖页面向 owner 传递新能力、手动重试和快照保留，是本问题的主要验证边界。无需为本设计新增生产测试接口。

好测试验证外部行为：请求发往哪一条连接、读取哪个 thread、是否需要用户操作、页面保留什么内容、迟到结果是否造成污染。不要断言私有字段、内部方法名、特定 hook 排列或具体代次数字。

主要场景：

- 连接 A 读取失败后经历 A→null→B：B 可用时没有自动请求；点击后只调用 B，参数仍指向当前 thread。
- 同一挂载中直接 A→B：即使 React 未呈现中间不可用状态，也不能继续使用 A。
- A 的首次读取或重试在途时发生替换：退出进行中并显示失败；B 可用后等待点击；A 后续成功或失败都不能覆盖当前状态。
- 已 ready 时经历 A→null→B：内容与标题持续保留，B 不自动读取；继续任务保持现有能力约束。
- 切换 thread 后采用 B 读取新目标，旧内容和旧响应不能错归属。
- 初始 null→B 与断线期间切换到未读取的新 thread：能力可用后执行该目标的首次加载，区别于失败后的手动重试。
- 重试执行期间保留错误与诊断，重复点击不产生第二个有效请求；再次失败及之后成功均能正确收敛。
- 保留响应身份校验、StrictMode 和卸载后结果隔离；只读请求不调用 resume、attach 或发送能力。

既有先例：`ThreadHistoryDetailRead` 页面测试已有普通失败后手动重试、初始无连接提示和 ready 后断线保留快照；`threadHistoryDetailOwner` 测试已有请求参数、身份检查及 dispose 后结果隔离；连接生命周期测试已有能力替换及旧回调隔离。现有这些分散断言没有证明详情在 A→null→B 后恢复正确。

owner 单元测试用于补充难以由页面测试稳定安排的请求竞态，沿用现有 deferred 请求与协议 fixture。无需在多个层重复完整用户流程。

证据分级：

- Level 1：适用。针对上述页面行为及必要 owner 竞态做无头自动化回归；本次未执行。
- Level 2：适用。后续在当前真实 Codex runtime 的历史详情中核验连接替换、快照保留和手动恢复读取。必须记录实际覆盖的场景；模拟 capabilities 或合成事件不等同于真实 BFCache 验收。本次未执行。
- Level 3：不依赖可见桌面状态，不适用。
