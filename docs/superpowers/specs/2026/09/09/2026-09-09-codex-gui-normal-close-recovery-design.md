# Codex GUI 正常关闭连接后的恢复设计（QR-X03-001）

日期：2026-09-09。

状态：主目标、页面保留方式、多任务恢复范围及设计摘要已确认；用户已授权设计落盘。本文不是实施计划，尚未修改产品代码。

核验基线：本地 `ffc118cdf`，包含 QR-X03-002 功能提交 `c80233091`。本轮证据来自当前源码、提交与既有测试内容，未执行测试或真实运行验收。

## 问题陈述

当前任务已加载且没有既存终止错误时，WebSocket 以 code 1000 关闭，客户端作废命令、清理会话。清理成功后，当前任务正文变为空白，页面提示条件没有覆盖 closed。用户既看不到关闭说明，也找不到恢复入口。

“正常关闭”是连接协议状态，不代表用户主动离开页面。此问题不泛指所有断线，也不表示持久化聊天记录被删除。页面卸载时的主动清理与仍打开的页面收到关闭事件必须区分。

根因是失效连接清理与可读内容生命周期耦合，同时页面缺少关闭状态的展示与恢复动作。仅增加提示不能满足本次已确认的旧内容、输入数据保留要求。

## 解决方案

连接关闭后保留旧对话供只读查看，在页面显示“连接已关闭，内容可能不是最新”和“重新连接”按钮。草稿、待发内容和结果不明记录需要保留，依赖连接的操作不可用。

用户手动点击后重建共享连接，恢复本页面所有已打开任务的同步，保持当前查看位置。其他任务也恢复更新，不把用户带回最初启动时的任务。共享连接建立失败时允许再次重连；共享连接成功后，各任务分别呈现恢复结果，某个任务失败不阻止其他任务恢复。

| 状态 | 用户可见行为 |
| --- | --- |
| 连接关闭 | 旧对话只读、内容可能过期的说明、“重新连接”按钮 |
| 正在重连 | 保留关闭说明、已有失败与诊断；同一按钮显示 Spinner 和“正在重新连接…”，禁止重复执行 |
| 共享连接恢复失败 | 显示本次失败与诊断，按钮恢复为“重新连接”，保留旧内容和输入数据 |
| 连接已建立、任务仍在恢复 | 明确任务仍在恢复；连接建立不代表任务已可操作 |
| 某个任务恢复失败 | 保留该任务旧内容、失败说明和可再次恢复的入口；其他任务独立完成恢复 |
| 任务恢复成功 | 取得有效状态后更新正文，撤下对应故障提示；独立错误与发送屏障继续保留 |

恢复连接不是继续发送的授权，不自动重发结果不明消息，也不绕过已有继续发送确认。

## 用户故事

1. 作为正在查看任务的用户，我希望连接关闭时看到说明，以便知道页面为什么停止更新。
2. 作为阅读对话的用户，我希望断开后仍能查阅旧内容，以便不被突然出现的空白打断。
3. 作为阅读对话的用户，我希望旧内容明确标为可能过期，以便不会误认为任务仍在实时同步。
4. 作为用户，我希望页面提供“重新连接”按钮，以便不必依靠浏览器刷新寻找恢复方式。
5. 作为用户，我希望手动决定重连时机，以便页面不会自行循环重试。
6. 作为正在输入的用户，我希望已有草稿得到保留，以便不必重新输入。
7. 作为有待发内容的用户，我希望队列在断开与重连期间保留，以便不丢失准备发送的内容。
8. 作为编辑待发内容的用户，我希望尚未完成保存的编辑也纳入保留设计，以便内存状态不因清理而丢失。
9. 作为有结果不明消息的用户，我希望重连不自动重发，以便避免重复执行任务。
10. 作为有恢复暂停队列的用户，我希望继续发送确认保持有效，以便重连不会顺带开始发送。
11. 作为打开多个任务的用户，我希望一次重连恢复所有已打开任务的同步，以便无需逐个重新打开。
12. 作为正在查看非启动任务的用户，我希望恢复后停留在当前任务，以便阅读位置不被启动目标覆盖。
13. 作为打开多个任务的用户，我希望各任务恢复结果彼此独立，以便一个失败不阻止其他任务更新。
14. 作为用户，我希望重连期间看到明确的进行中状态，以便知道操作仍在处理。
15. 作为用户，我希望重复点击只产生一个有效重连动作，以便避免恢复状态互相覆盖。
16. 作为排查失败的用户，我希望重连期间保留上次诊断，以便检查失败依据。
17. 作为重连失败的用户，我希望保留旧内容并能再次操作，以便失败不会把我留在无入口状态。
18. 作为用户，我希望任务取得有效状态后才被标记恢复，以便连接建立不会被误报为全部恢复成功。
19. 作为存在多个错误的用户，我希望恢复只解除对应故障，以便其他未解决的问题仍可见。
20. 作为窄屏用户，我希望说明、诊断和按钮按既有布局可读地排列，以便无需横向滚动。
21. 作为键盘用户，我希望重连和诊断入口可正常操作，以便无需依赖鼠标。
22. 作为用户，我希望旧连接的迟到结果不覆盖新连接状态，以便任务内容与操作始终属于有效会话。

## 实现决策

### 职责边界

- 连接生命周期拥有共享连接重建、旧连接释放及新连接能力发布；页面只发起恢复意图和展示状态，不另建连接 owner。
- 会话集合负责已打开任务及当前查看位置的恢复协调；各任务负责自己的同步结果、失败反馈与再次恢复能力。当前初始化已有恢复集合与后台成员的入口，可作为整合起点。
- 将失效命令清理与可读内容、输入数据保留解耦。禁止为了保留画面继续使用失效命令，也不能简单销毁输入 owner 后假设所有内存内容都已持久化。
- 展示、草稿、队列及恢复状态分别保持明确的权威来源，不以双写、平行旧新业务路径或临时兼容层维持中间状态。
- 重连请求需受页面生命周期与请求身份约束。连接替换、卸载以及异步交接后验证归属，旧回调不得清除或覆盖新连接状态。

### 与 QR-X03-002 的关系

- QR-X03-002 已实现手动“恢复同步”，在共享连接仍可用且 live 会话有效时，重新 attach 单个任务订阅，保留原 live 与队列。
- QR-X03-001 的连接已关闭，现有会话已 disposed，不能直接调用单任务 recoverProjection 完成重连。
- 沿用 FailureLayout、RetryActionButton 和诊断入口的交互：进行中保留失败信息，动作名称稳定，失败允许再次操作。不把单任务“恢复同步”误命名为共享连接“重新连接”。
- 共享连接恢复后的任务级处理需沿现有恢复能力整合；不能把普通任务状态刷新伪装为重新订阅。

### 合同与安全约束

- 连接状态以现有 GuiHostStatus 为权威来源；会话、恢复状态从其所属 owner 的权威 TypeScript 定义派生，保持消费者的类型检查传播。
- 后端消息与请求继续消费生成协议类型，不新增手写镜像协议合同。本设计未提出后端协议变更。
- 保留命令作废、清理错误传播、订阅身份隔离、投影连续性检查、持久化保护和 unknown 交付屏障。
- 不能仅凭 WebSocket open、握手完成或 Promise fulfilled 宣告所有任务恢复成功。连接可用、任务有效状态与允许发送是不同条件。
- 旧内容在任务恢复完成前保留；共享连接或单任务失败不能隐藏错误、丢失输入或伪造成功。
- 已选方案只承诺断开期间旧对话可读和输入状态保留，不新增离线编辑、离线发送或后台自动恢复能力。
