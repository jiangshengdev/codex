# Codex GUI 投影暂停恢复设计（QR-X03-002）

日期：2026-09-09

状态：根据本轮已讨论方案与用户纠正整理，用户已授权设计落盘；尚未进入实施计划或产品实现。

核查基线：本地 `dev`，`5dc0905db`。本设计依据源码、既有测试代码、历史设计及执行记录，不代表本功能已经通过运行验收。

## 问题陈述

任务的消息同步可能因更新积压、提交链不连续或缺少关联轮次而暂停。此时用户仍能看到旧对话，发送等操作被禁止，但现有通用提示没有解释具体原因，也没有可执行的同步恢复入口。

暂停是保护措施，不能通过清除错误标记、忽略连续性检查或提前开放发送来解决。问题在于暂停后的解释与恢复路径缺失。

现有任务重试在 ready 成员上只刷新任务状态，并不重新建立投影订阅。前端将恢复要求统一标记为 `connectionRestartRequired`，但已核对的后端实现支持同一连接对同一任务重新 attach：生成新订阅 ID，并替换原订阅。合法 backpressure 会使该任务的投影失效，不必然关闭共享连接。

错误面板重试行为统一工作已经实现并提交，包含 `RetryActionButton`、执行中保留旧错误及诊断、稳定的动作名称。本设计直接复用这些成果。

## 解决方案

在当前任务正文上方的通知区域展示同步暂停面板。保留旧对话，并提示其内容可能不是最新。用户点击“恢复同步”后，仅恢复当前连接对该任务的订阅，不重启共享连接、不切换到其他任务。

原因使用通俗说明，并与真实原因一一对应：

| 原因 | 用户可见说明的含义 |
| --- | --- |
| `backpressure` | 消息更新积压，同步已暂停，需要重新获取最新内容 |
| `commitChainMismatch` | 消息更新顺序不一致，暂时无法确认内容完整性 |
| `missingTurn` | 收到的消息更新缺少所属轮次，暂时无法完整展示 |

使用 `FailureLayout` 和 `RetryActionButton`，不另建一套错误面板交互。宽屏按钮位于内容区右侧，窄屏位于完整内容下方；诊断入口保留在内容区。按钮位置稳定指同一载体与相对布局区域，不承诺固定像素坐标。

| 状态 | 面板与按钮 |
| --- | --- |
| 等待恢复 | 原因、诊断入口及“恢复同步” |
| 执行中 | 保留上次错误与诊断；同一按钮显示 Spinner 和“正在恢复…”，禁止重复执行 |
| 恢复失败 | 更新对应失败说明，按钮回到“恢复同步”；不增加“重试恢复”等历史相关名称 |
| 恢复成功 | 对应同步故障解除后移除该面板；独立错误仍保留 |
| 再次暂停 | 按当前原因重新展示同一面板，按钮仍为“恢复同步” |

正文中已有的通用重连提示与新面板按现有错误归属规则合并，避免同一当前故障重复展示；不删除对话中的历史错误记录。菜单的任务注意标记仍按当前状态派生。

恢复期间保留草稿、待发队列和旧内容；恢复成功后更新到可信快照。恢复同步不等于同意继续发送，既有恢复暂停确认及 unknown 交付屏障继续生效。

## 用户故事

1. 作为当前任务的用户，我希望看到同步暂停的具体原因，以便理解为什么不能继续发送。
2. 作为阅读对话的用户，我希望暂停后保留旧内容并标明内容可能过期，以便继续查阅而不误认为它仍在实时更新。
3. 作为遇到消息积压的用户，我希望通过一次明确操作恢复同步，以便获取最新内容。
4. 作为遇到更新顺序异常的用户，我希望重新取得可信的完整状态，以免继续阅读不连续的数据。
5. 作为遇到缺少关联轮次的用户，我希望得到具体说明和相同的恢复入口，以免只能面对通用错误。
6. 作为用户，我希望自主决定恢复时机，以免页面未经操作就自动重试。
7. 作为同时打开多个任务的用户，我希望恢复只作用于故障任务，以免其他任务被连带重连。
8. 作为用户，我希望恢复期间保留当前查看的任务，以免被带回最初打开的任务。
9. 作为正在输入的用户，我希望草稿和待发内容不因恢复丢失，以免重新输入。
10. 作为用户，我希望执行中看到进行中文案和 Spinner，以便知道操作正在处理。
11. 作为用户，我希望重复点击不会创建多个并发恢复请求，以免状态互相覆盖。
12. 作为排查问题的用户，我希望恢复期间仍能查看上次错误和诊断，以便保留排查依据。
13. 作为再次遇到失败的用户，我希望看到本次失败并继续使用相同动作按钮，以免按钮名称随尝试次数变化。
14. 作为用户，我希望只有同步实际恢复后才撤下错误，以免请求结束被误报为成功。
15. 作为有发送结果不明消息的用户，我希望恢复不自动重发这些消息，以免重复执行任务。
16. 作为有恢复暂停队列的用户，我希望原有继续发送确认仍然有效，以免恢复同步顺便触发发送。
17. 作为窄屏用户，我希望说明、诊断和按钮保持可读顺序，以便无需横向滚动即可操作。
18. 作为键盘用户，我希望恢复按钮和诊断入口可正常操作，并在执行中阻止重复提交，以便获得一致的操作反馈。
19. 作为切换任务的用户，我希望旧恢复请求的结果不覆盖新任务状态，以免错误归属发生混淆。
20. 作为存在多个独立错误的用户，我希望同步恢复仅解除对应错误，以免其他尚未解决的问题被隐藏。

## 实现决策

### 职责与接口

- 当前任务页面负责展示暂停原因、恢复动作和执行状态；复用现有错误布局、诊断组件和共享重试按钮。
- activeThreadSession 的成员生命周期负责单任务恢复调用、请求身份和新订阅发布；live 会话及投影处理负责可信快照、连续性和队列状态的一致性。共享按钮不持有请求或业务状态。
- 提供明确的投影恢复能力，不能把普通 thread status retry 当作恢复。现有 `connectionRestartRequired` 前端合同须调整为与单任务恢复一致的语义，并由其权威定义向消费者传播；不保留误导性的共享重启声明或并行旧路径。
- 后端协议继续使用生成的 `@codex-protocol` 类型。复用 `thread/projection/attach`，不新增后端恢复接口，不手写镜像协议类型或运行时校验器。
- 原因从现有投影状态派生，消费者完整处理现有原因；进行中状态及失败结果由负责恢复的 owner 发布，不在页面另建相互竞争的业务状态来源。

### 恢复边界

- 用户手动触发一次恢复，不增加自动重试、后台循环或自动共享连接重启。
- 连接可用时重新获取故障任务的快照与新订阅。后端同连接、同任务再次 attach 已具备替换语义，不以“先移除任务再打开”绕过恢复保护。
- 新快照、订阅身份、必要状态核对和候选期间的消息处理全部有效后，才发布可操作状态；Promise fulfilled、blocked 或 unavailable 不等于业务成功。
- 请求绑定任务、会话身份和连接能力。每个异步交接后核对是否仍有效，旧结果不得修改替换后的会话或其他任务。
- 恢复期间的新通知按新订阅处理，旧订阅通知、delta 和延迟 closed 必须丢弃。不能只用 threadId 判断消息属于本次恢复。
- 同一任务同时只允许一个有效恢复动作。按钮 pending 与 owner 侧防重复共同生效，不因按钮禁用而省略生命周期保护。
- 恢复失败保留可查阅的旧内容、具体原因及再次操作能力，不能让任务停在无按钮的中间状态。连接实际失效时按真实连接状态限制恢复，不伪造单任务恢复成功。

### 数据与发送保护

- 草稿、待发项、编辑中的内容及发送结果不明记录必须保留。不得简单销毁整个 live owner 并仅假设持久化足以恢复全部内存状态。
- 同一恢复过程维持一个权威队列 owner 或明确的无损交接，不引入双写、双读或临时兼容路径。具体交接机制在实施计划前沿当前 owner 接口闭合，不把机制选择转化为新的产品选项。
- 旧内容持续可读与新状态发布分离；恢复前的不可发送门禁保持，快照更新不能触发 unknown 自动重发。
- 新快照与已有发送记录的核对沿用队列恢复规则。仍需用户确认继续发送、保存失败或结果未知时，不因投影恢复成功解除这些独立屏障。
- 不向后端发送中断或重新执行任务的请求来实现投影恢复。

## 测试决策

优先以现有应用级投影可用性 Browser 测试作为主验收入口，从合法协议通知触发暂停，经用户点击恢复到界面结果验证完整行为，不为本功能新增平行测试框架。

1. 应用级测试覆盖三种暂停原因、原因可见性、旧内容保留、发送禁用、恢复入口及成功后故障解除。
2. 覆盖“失败 → 点击 → loading → 再失败 → 再点击 → 成功”，断言动作名称稳定、进行中文案正确、诊断入口持续可用、重复操作只产生一次有效请求。
3. 复用既有多任务隔离测试入口，确认其他任务不重连、当前查看任务不改变、任务切换与旧请求完成不会串写状态。
4. 复用会话与队列测试支撑，覆盖草稿、待发项、未保存内容、持久化失败、restoredPaused 和 unknown 的保留及发送屏障；验证用户结果，不锁定私有字段或内部函数顺序。
5. 仅对应用级入口难以稳定构造的订阅竞态补 owner 层测试，包括旧通知晚到、恢复中再次关闭、连接替换及卸载。沿用共享合法协议 fixture，不手写平行协议对象模型。
6. 共享按钮已有测试负责通用 Spinner、名称切换及 pending 键盘防重复；本功能测试重点验证业务状态确实接入该组件，而非重复测试其内部实现。
7. 宽窄屏及键盘验收检查既有错误布局、无溢出、诊断打开关闭与焦点行为；不将固定像素坐标作为按钮稳定性的定义。

证据分级：Level 1 自动化适用；Level 2 无头真实 GUI 验收适用，需针对当前运行环境建立合法暂停与恢复场景并逐项记录。不能以 mock/harness 通过替代真实恢复证据。Level 3 不适用，本功能不依赖可见桌面状态。

本轮未运行上述验证。测试入口与案例是设计建议，并非已经执行的验收或已确认的精确测试命令。

## 范围排除

- 不重新设计或全面修改已经完成的错误面板重试行为统一工作。
- 不实现 QR-X03-001 的共享连接正常关闭恢复，也不新增通用自动重连系统。
- 不改变后台任务执行、任务历史、输入交付语义或后端协议。
- 不放宽连续性检查、订阅身份隔离、持久化保护或 unknown 屏障。
- 不把恢复按钮接到删除任务、普通状态刷新或完整页面刷新来代替实际恢复。
- 不处理原始质量报告中的其他独立缺陷，不以本设计授权额外修复。

## 补充说明

前置重试统一工作的执行记录表明实现与自动化已完成，真实 GUI 验收未执行。该记录不证明本次投影恢复已实现。

后端证据支持单任务重新订阅：重复 attach 替换该连接的订阅；backpressure 使该任务的订阅失效并携带旧 subscriptionId 通知客户端。其影响可能涉及同一任务的多个订阅者，但本页面恢复只替换本连接的订阅，不接管其他页面。

进入实施计划前须进一步闭合：现有 live 会话与队列如何无损保留或交接、恢复期间通知的接收与发布顺序、失败与连接失效的清理路径。上述机制不得改变本文的数据保留、隔离和发送保护要求。
