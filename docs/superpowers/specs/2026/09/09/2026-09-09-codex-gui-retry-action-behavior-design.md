## 1. 主目标与工作关系

统一现有错误面板中承担重试行为的按钮：非 loading 时保持具体动作名称；loading 时显示进行中文案并禁止重复点击；失败后恢复原动作名称，错误单独展示。

本设计作为 QR-X03-002 投影暂停恢复设计的前置事项。本文不实现投影重新订阅、连接重启或其他新的恢复能力；QR-X03-002 后续沿用本设计的交互规则。

本设计更新前述布局设计中“按钮行为继续服从现状”的范围，仅对本文纳入的重试交互生效；不回写历史文档，不改变既有错误归属和诊断布局。

## 2. 已确认的产品决策

1. 保留具体动作名称，不统一改成通用“重试”。例如“重新保存／正在保存…”、“恢复同步／正在恢复…”。这些是语义示例，不要求为同步保存制造进行中阶段。
2. 重试执行期间保留上次错误说明及诊断入口。按钮留在原操作区域，切换为进行中文案；成功后解除对应错误，失败后用本次错误更新说明。

按钮文案只随当前是否执行而切换，不随点击次数、以往成功或失败改名。保留的错误属于上次尝试，不表示正在执行的尝试已经失败。

## 3. 适用范围与现状

按实际行为确定是否纳入，不仅搜索按钮是否写有 `Retry`。同一动作按钮在失败后允许再次执行，也属于本设计的重试入口。

| 入口 | 已核验现状 | 设计要求 |
| --- | --- | --- |
| `CurrentTaskPage.tsx` | 任务加载、操作错误和恢复分支存在 `Retry`；部分异步操作没有按钮 pending 状态 | 依据实际动作使用稳定名称；保留错误及操作区到本次重试结束 |
| `ThreadHistoryListPage.tsx`、`threadHistoryListOwner.ts` | 首次重试切为骨架屏；追加失败时 `Load more` 切为 `Retry`，重试再切回 `Load more` | 首次正常加载维持现状；失败后的重试保留错误面板，追加动作不因失败改名 |
| `ThreadHistoryDetailContent.tsx`、`threadHistoryDetailOwner.ts` | 重试立即用 loading 内容替换错误面板 | 失败后的重试保留说明与按钮，成功才切正常详情 |
| `ContinueTaskAction.tsx`、`ContinueTaskFailureAlert.tsx` | `Continue this task` 名称稳定，但 pending 不切进行中文案，开始操作即清除错误 | 保留动作名称；重试期间保留上次错误并显示进行中状态 |
| `SkillTypeaheadPlugin.tsx`、`skillCatalogOwner.ts` | loading 状态和失败提示互相切换；存在部分加载失败的重试 | 保留已有技能内容及上次错误，重试按钮原位显示进度；部分失败仍按实际结果展示 |
| `ComposerPersistenceStatus.tsx` | `Retry saving` 名称稳定，调用同步持久化操作 | 保持同步执行；成功解除对应保存错误，失败保留原动作名称 |
| `NewSessionPage.tsx`、`newSessionOwner.ts` | 同一提交入口初始为 `Send`，失败锁定输入后显示 `Retry`，pending 又显示 `Send` | 同一入口的动作名称不因失败改名；异步重试采用进行中文案并保留错误说明；不改动创建及输入交付语义 |
| `ComposerPendingInputRegion.tsx` | `Continue sending` 承担待发恢复，已有 pending，但没有进行中文案 | 恢复执行期间显示进行中文案；保留原有待发说明和安全限制 |
| `ContextUsagePopover.tsx` | 已有 `Compress context`／`Compressing`，失败单独显示 | 保留符合的按钮文案规则；若失败后重试会清除旧错误，按统一的错误保留规则核对调整 |

最终实施计划须沿这些入口核对相关消费者，区分需要修改和已符合的行为，不能把表中每一项都机械当成必须改动的文件。

### 范围排除

- 普通首次发送、首次加载和普通导航不因本设计新增错误面板或改名。同一按钮兼任后续重试时，只协调其状态展示，使动作名称保持一致。
- 错误面板中确实重试失败导航的操作属于重试；纯“返回当前任务”“打开会话”等导航入口不因此改造成重试。
- 全局连接错误、历史上下文缺失、消息流历史错误、校验提示等没有可执行重试入口的提示，不凭空添加按钮。
- 不将历史错误记录当作当前操作故障；后续其他操作成功不删除历史错误。
- 不增加自动重试、不修改请求内容、消息队列交付语义或服务端协议。

## 4. 统一交互合同

| 当前阶段 | 错误内容 | 按钮表现 |
| --- | --- | --- |
| 失败后等待操作 | 当前错误说明及已有诊断入口 | 固定的具体动作名称；是否可用服从业务条件 |
| 异步重试执行中 | 保留上次错误说明及诊断入口 | 同一操作区显示 Spinner 和进行中文案，禁止重复触发 |
| 本次重试失败 | 用本次错误替换对应旧错误，不累积重复面板 | 恢复相同动作名称；是否可再次执行服从最新业务条件 |
| 本次重试成功且对应故障解除 | 移除对应错误面板或完成既定跳转 | 回到正常界面；常驻动作按正常功能规则展示 |

不能将 Promise 完成直接当成业务成功：返回 blocked、unavailable、部分失败或其他未解除故障的结果时，按真实结果保留或更新提示，不能制造成功状态。

同步操作不引入人为延迟、Spinner 或异步包装来满足外观统一。其非执行文案稳定、错误单独展示、成功解除对应故障等规则仍适用。

重试中只阻止同一动作重复执行及已有规则禁止的冲突操作，不扩大为全页面锁定。诊断入口继续可用。按钮位置稳定指保留同一载体和相对布局区域，不要求固定像素坐标。

## 5. 布局、状态与实现边界

沿用 `FailureLayout`：内容区为标题、说明和已有诊断入口，操作区放重试按钮；宽屏在内容右侧，小屏在完整内容下方。紧凑菜单、Popover、底部操作区保留各自载体，不强制把关联按钮迁入错误卡片。

使用现有 HeroUI `Button`、`Spinner` 与反馈组件，保留动作对应的 variant 和主题 token。危险操作不得因统一重试外观变为普通主操作。进行中反馈与防重复行为必须实际生效，不能仅改变文字或颜色。

错误与执行状态由负责该动作的现有状态所有者表达。历史列表、详情及继续任务需要能够同时表达“正在重试”和“上次错误”；不在共享展示组件中另建请求、业务错误或重试次数的权威状态。首次加载与失败后的重试必须可区分，不能为了保留错误让首次正常加载显示故障。

共享展示组合只接收动作名称、进行中文案、当前执行状态、可用性和回调等展示所需能力，不负责调用 API、解释错误、清空业务状态、持久化或决定成功。

每个请求仍绑定原任务、连接能力及请求身份。切换任务、替换连接或组件卸载后，旧请求不得修改新页面的错误和执行状态。保留既有过期结果隔离、防重复请求及业务门禁，不以按钮禁用代替底层保护。

### 合同与安全约束

- 后端协议继续以现有生成的 `@codex-protocol` 合同为权威，本文不新增或复制协议类型、校验器或生成链。
- 前端动作状态由现有 owner 的类型定义及其消费者直接引用或机械派生；不得在页面和共享组件中镜像另一套业务状态合同。
- 展示旧错误是当前重试的呈现语义，不提供重新发送或绕过授权的能力。
- `deliveryUnknown`、`handoffUnknown`、恢复暂停、持久化错误及发送屏障继续按现有规则阻断操作。原本只能打开已有会话核查的情况，不能因文案统一重新开放发送。
- 草稿、待发队列、任务归属和既有诊断数据保持其业务语义。重试成功仅解除对应故障，不能清除独立错误。

## 6. 验收要求

后续实施计划至少覆盖以下用户可见序列：

- 失败 → 点击 → 执行中 → 再失败 → 再点击 → 成功；按钮的非执行名称始终相同，loading 采用进行中文案。
- 执行期间错误说明和诊断入口仍在，重试按钮不被骨架屏或其他操作按钮替换；连续点击仅触发一次有效操作。
- 首次正常加载继续显示原有加载内容，不出现伪造错误；同步保存不出现人为 loading。
- 业务拒绝、部分失败、发送结果未知仍保持正确提示与限制；普通动作、纯导航及历史错误不被误改。
- 切换任务、连接替换或卸载期间完成的旧请求不污染新状态。
- 宽屏、小屏及紧凑载体中说明、诊断和按钮顺序稳定，无溢出或重复操作入口；键盘操作与焦点行为可用。

证据分级：

- Level 1：适用。后续运行针对状态转换、动作次数、文案、错误保留及隔离的自动化回归；当前未执行。
- Level 2：适用。后续针对真实 GUI 中可建立的失败与重试场景进行无头验收，逐项记录实际覆盖和未执行场景；不能用测试环境注入结果冒充真实运行证据。
- Level 3：本设计不依赖可见桌面状态，不适用。
