# Codex GUI 待发送编辑丢失修复设计

日期：2026-09-08。

关联问题：QR-B03-001。

状态：主目标及两项产品决策已确认；按用户“落盘设计”请求记录。未编写实施计划，未开始实现。

## 主目标

让待发送消息的编辑不受正常回复刷新影响，可以正常保存；同时保留消息或所属会话真正失效时的安全检查，并避免保存失败直接丢弃本次修改。

## 当前问题与证据

评审正文：[QR-B03-001](../../../../reports/2026/09/08/2026-09-08-codex-gui-quality-review/batch-03-sessions.md)。该报告是问题证据，不是实施授权。

当前源码核验确认：

- `codex-gui/src/features/activeThreadSession/liveActiveThreadSession.ts` 的 `beginPendingInputEdit` 捕获整个会话的 `capabilityRevision`，后续保存通过 `capabilityUnavailable` 校验。普通投影更新也推进会话 revision，因此与编辑目标无关的回复刷新会使编辑能力失效。
- 失效处理取消下层 reservation，恢复原待发送文本。`codex-gui/src/features/composerTurnControl/composerPendingInputSession.ts` 的 `settleEditResult`、`handleLiveFailure` 及目标失效协调路径随后清空编辑状态，卸载编辑器。丢失的是用户本次修改，原待发送消息并未因此丢失。
- 主输入框与待发送编辑器是两个独立的 `ComposerEditor` 实例。`ComposerTurnControl.tsx` 接入主草稿保存，`ComposerPendingInputEditor.tsx` 没有对应的草稿保存回调。不能把失败修改直接写进主输入框，否则可能覆盖另一个已有草稿。
- 下层 `composerPendingInputLiveManagement.ts` 已维护编辑 reservation 和 `targetInvalidated`，可用来区分编辑目标失效与一般展示更新。

本轮证据来自源码读取，未运行测试或真实 GUI 验收。报告中的既有测试记录不代表本设计已经验证。

## 已确认的用户行为

### 正常回复刷新

同一消息和所属会话仍有效时，AI 继续输出、一般展示刷新不应撤销编辑。用户保存后，修改替换原待发送内容，保留原消息身份、队列位置及所属队列语义。

### 真正失效

消息或所属会话真正失效后，拒绝向原消息保存。保留本次修改在原编辑位置，明确提示不能保存，提供复制与主动丢弃操作。

保留内容不代表继续保留可写 reservation，也不代表能够自动重试、重新入队或发送。主输入框草稿保持独立。

用户选择：留在原编辑位置，而非新增可恢复草稿管理入口。

### 关闭编辑面板

存在未保存修改时，关闭编辑面板先提示确认；用户可以返回复制，或明确丢弃后关闭。关闭按钮、Escape、点击遮罩等实际支持的关闭入口应遵守同一语义。

用户选择：关闭前确认丢弃。本次不增加跨刷新恢复，也不承诺浏览器刷新、页面关闭或程序退出后仍能找回修改。

## 职责与实现方向

### 编辑有效性

将长时间编辑能力的有效性与普通展示 revision 解耦。开始编辑时仍核验请求对应的当前状态；取得 reservation 后，按所属会话生命周期与实际目标有效性判断保存、取消是否允许。

只调整待发送编辑的有效性边界，不全局放宽其他操作的 revision 检查。会话终止、投影不可用和真实目标删除、发送或替换后的陈旧写入仍须拒绝。

会话生命周期由 live session 判断，队列目标及 reservation 结算由现有队列管理负责，不在 UI 复制第二套队列有效性规则。

### 失败内容与队列能力分离

由待发送编辑的应用状态拥有尚未保存的内容及失败展示状态。真正失效时，可以结束 reservation 并完成资源清理，但不能因此直接清空用户内容。

保留内容的生命周期不依赖失效的保存能力；原编辑位置需要能够展示失效后的内容。主动丢弃后才释放这份内容，不把它自动复制到主草稿或其他会话。

实现计划应追踪现有 `reconcile`、`closeInvalid`、owner 变化及组件卸载路径，保证真正失效不会先卸载编辑器再尝试保留内容。会话切换不能将旧编辑内容或操作能力归入新会话；涉及带未保存修改的应用内关闭时，遵守上述关闭确认语义。

### 契约与界面

操作结果继续依赖 `activeThreadSession` 与 `composerInputQueue` 的权威契约；UI 只消费其结果。新增的失败内容状态属于前端编辑语义，不镜像协议类型，不新增后端协议或持久化格式。

界面沿用项目 HeroUI v3 组件体系。失败提示、复制、丢弃和关闭确认需区分语义；具体组件、焦点行为与文案在实施计划中结合现有组件入口核验。

## 必须保持的约束

- 原待发送内容可恢复，成功保存保持原队列身份与位置。
- `disposed`、`projectionUnavailable` 及真实目标失效仍阻止陈旧写入。
- reservation 清理只结算一次，保留失败内容不延长旧能力寿命。
- 不自动重发、不自动重新入队，不绕过未知投递或恢复暂停约束。
- 不覆盖主输入框草稿，不跨会话混用内容与操作能力。
- 不通过删除断言、关闭检查或扩大豁免来消除失败。

## 验收条件

1. 编辑期间发生普通 delta 刷新，同一有效目标的修改仍可保存。
2. 目标或会话真正失效时，保存被拒绝，但本次修改仍能查看、复制和主动丢弃。
3. 失败后的队列原内容恢复及单次清理约束仍成立，迟到保存不能写入旧目标。
4. 有未保存修改时，支持的面板关闭入口均先确认；返回保留内容，明确丢弃后才关闭。
5. 失败保留和关闭确认均不覆盖主草稿，不让旧编辑影响其他会话。
6. 空输入等既有可修正失败仍保留编辑，不被误归类为目标失效。

后续计划分别安排单元与 Browser 自动化回归，以及当前真实 Codex 运行时的无头交互验收；本设计未执行这些验证。不涉及系统窗口或输入法行为，当前不要求可见桌面验收。
