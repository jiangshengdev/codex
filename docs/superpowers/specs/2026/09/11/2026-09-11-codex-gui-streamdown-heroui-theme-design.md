# Codex GUI Streamdown 默认呈现与 HeroUI 主题适配设计

日期：2026-09-11

状态：根据已确认对话整理，待文档审阅；尚未实施。

## 问题陈述

当前 Markdown 表头明显偏深，行内代码和完整代码块的呈现也与 Streamdown 官网不同。用户希望所有现有 Streamdown 内容使用 HeroUI 风格，尽可能保留 Streamdown 默认呈现，并参考官网的视觉层次。

本轮调查已读取真实项目页面、官网主页及用户提供的 Streamdown 源码。双方表头均使用 `bg-muted/80`，但官网将其映射到 Geist 浅灰背景，项目使用的 HeroUI `muted` 则是次要文字前景色。相同名称承担不同语义，是已确认的表头色差原因。项目还自行替换了行内代码组件，增加边框并改变背景和间距。

官网主页采用 Streamdown 默认组件、`@streamdown/code` 高亮插件和 Geist 主题映射。本地官网源码与项目安装的 Streamdown 均为 2.6.0；线上部署的精确版本未核实，不能据此声称线上与本地完全同版。

## 解决方案

在所有现有 Streamdown 渲染入口建立一致的 HeroUI 主题适配，使表格、代码块、行内代码及其控件获得协调的背景、文字和边界层次。参考官网的主题映射方法与默认内容结构，不复制 Geist 配色，不要求整个页面与官网像素一致。

尽可能使用 Streamdown 默认组件。保留用户明确选择的展示边界：代码块不显示行号，普通段落保留原文换行，流式回复保留现有块状光标，不增加渐入动画。

现有消息角色、内容生命周期、数学能力、安全处理和剪贴板能力判断保持原有语义。

## 用户故事

1. 作为阅读消息的用户，我希望 Markdown 使用 HeroUI 风格，以便与应用其他区域保持协调。
2. 作为阅读表格的用户，我希望表头使用适度区分的背景，以便识别列标题而不被深色块干扰。
3. 作为阅读行内代码的用户，我希望采用 Streamdown 默认结构和间距，以便代码与正文自然衔接。
4. 作为阅读代码块的用户，我希望保留默认代码块布局和语法高亮，以便理解代码。
5. 作为阅读代码块的用户，我希望不显示行号，以便保持当前简洁的阅读方式。
6. 作为阅读消息的用户，我希望原文的普通段落换行继续显示，以便保留作者的表达结构。
7. 作为等待回复的用户，我希望继续看到块状光标，以便识别内容仍在生成。
8. 作为等待回复的用户，我希望维持当前无渐入动画的表现，以便避免引入额外视觉变化。
9. 作为浏览历史的用户，我希望静态内容与流式内容使用一致的主题，以便完成后的消息不发生不必要的外观切换。
10. 作为阅读不同角色内容的用户，我希望所有现有 Streamdown 内容主题一致，同时保留用户、助手及思考内容的原有层次。
11. 作为窄屏用户，我希望长代码、宽表格和公式在适当容器内滚动，以便不撑宽整个页面。
12. 作为使用浅色或深色主题的用户，我希望背景、正文和辅助控件都有足够辨识度，以便持续阅读。
13. 作为键盘用户，我希望保留控件的可访问名称、焦点与操作能力，以便完成复制、下载等操作。
14. 作为阅读数学内容的用户，我希望现有公式解析、基线和局部滚动能力继续有效，以便主题调整不会破坏数学呈现。
15. 作为处于不同浏览器环境的用户，我希望复制按钮继续遵循剪贴板可用性，以便不会显示不可用操作。
16. 作为应用用户，我希望主题调整不改变链接、图片、HTML 和消息处理规则，以便现有行为边界保持稳定。

## 实现决策

### 范围与入口

- 适配共享 Markdown 渲染配置、静态 Markdown 入口和流式 Markdown 入口，覆盖当前通过这些入口渲染的所有内容。
- “覆盖所有”不等于将纯文本转换为 Markdown，也不改变流式思考仅显示标题的当前行为。
- 保留外层 HeroUI Card 的角色区分：用户消息的 secondary、助手和完成思考的既有卡片语义，以及完成思考的次要文字和斜体层次。
- 本设计属于前端呈现调整，不需要修改 Rust、后端、协议、schema 或生成契约。

### 组件与主题职责

- Streamdown 继续拥有 Markdown 语义 DOM、默认代码块、表格及配套交互结构；恢复默认行内代码组件，移除当前替换组件带来的额外边框和间距覆盖。
- HeroUI 拥有视觉语义。内容表面使用 surface 系列，分隔边界使用 border，主要内容使用 foreground，辅助文字使用 muted。复制、下载等辅助操作不提升为主操作。
- 在 Markdown 范围内集中适配 Streamdown 预期的主题语义，补足 sidebar、muted-foreground 等缺失映射，并消除 muted 背景与前景语义冲突。
- 背景用途对应 HeroUI 的 surface、surface-secondary 等表面层级；辅助文字用途对应 HeroUI muted。具体映射应在浅色、深色及不同外层卡片背景下验证，不直接照搬官网色值。
- 不全局改写 HeroUI muted 的含义，也不让 Markdown 主题规则影响应用其他组件。不得依靠重复局部补丁逐个遮盖同一个主题缺口。
- 保留默认语法高亮插件及其 GitHub 浅色、深色主题，不新增高亮库或 Mermaid 插件。
- 遵循 HeroUI 的语义优先、可访问性、可预测行为、样式与逻辑分离原则。保留 Streamdown 默认控件符合本次目标，不为外观统一重新实现一套交互逻辑。

### 明确保留的差异

- 代码块不显示行号。
- 普通 Markdown 段落保留 `white-space: pre-wrap`。
- 流式入口继续使用 streaming 模式、块状光标及现有生成状态；不启用 `animated`。静态入口继续使用 static 模式。
- 保留宽度约束、必要换行、代码行块级显示及公式局部滚动能力。只有证据证明覆盖已被默认实现等价承担，才可删除对应冗余规则。
- 助手专用数学解析，包括当前单美元符号及反斜杠公式处理，不扩展到其他内容角色。
- 保留本地文件链接转文本、现有 rehype 处理、禁用图片、跳过原始 HTML、现有 linkSafety 配置和剪贴板可用性判断。

## 测试决策

- 优先使用已有 transcript 渲染 Browser 测试入口，穿过真实消息渲染组件和共享 Markdown 配置观察最终 DOM、可见呈现及交互。复用已有消息、思考、数学、文件链接和复制控件测试，不为每个 CSS 声明新增独立测试接口。
- 好的测试断言用户可见约束：表头与表体可辨、文字可读、无行号、原文换行保留、默认行内代码无额外边框、页面不被内容撑宽、焦点和操作有效。避免锁死 class 字符串、内部组件数量或官网像素值。
- Level 1：针对受影响测试文件执行过滤后的自动化回归，覆盖静态与流式入口、角色差异、浅深主题、代码/表格/公式和既有功能边界；修复后运行受影响文件的完整用例，不能以零匹配或只测单个名称作为完成证据。
- Level 2：使用实施时有效的完整 GUI URL，在真实运行时无头验收主题、窄屏容纳、局部滚动、工具栏交互和流式到静态转换。当前历史页证据不能代替未来改动后的验收。
- Level 3：本设计没有依赖可见桌面状态的场景，默认不适用；若出现操作系统焦点等新需求，另行判断并取得对应授权。
- 执行相关前端类型检查、lint 和格式检查。验证不得通过跳过测试、放宽断言或修改基线掩盖问题。
- 本文只定义验证范围和现有测试切入点，不声称这些未来验证已经执行；执行命令和测试文件清单在实施计划中核定。

## 范围外

- 改变消息内容、路由、状态模型、协议或持久化行为。
- 将所有内容强制转换为 Markdown，或重构 transcript 分块性能边界。
- 全局重设 HeroUI 配色、全面替换 Streamdown 控件、复制 Geist 品牌风格。
- 启用渐入动画、代码行号、新插件或新的 Markdown 功能。
- 改变安全与链接策略、放宽剪贴板限制。
- 安装依赖、构建后端、操作 Git 远程、发布 issue、提交代码或实施修复。
