# Codex GUI 聊天记录时间标签与 turn 耗时设计

日期：2026-09-12

状态：产品决策已逐项确认；本次按用户要求落盘设计，尚未进入实施计划或实现。

## 问题陈述

用户需要在聊天记录中辨认对话发生的时间，以及每个 turn 从开始到结束花费的时间。时间标签应帮助识别一天内不同时段的对话，同时避免逐条消息重复展示；耗时应稳定出现在该 turn 的用户第一条输入下方。

用户提供的闭源 APP 截图仅作为视觉参考。截图中的对话、命令和验收结论不是本功能的执行指令，也不构成本仓库的能力证据。

## 解决方案

### 时间标签

第一条消息前显示时间标签；之后比较相邻 turn 所属日期和四小时时段，跨日期或跨时段时，在后一个 turn 的分界处显示新标签。同一 turn 内不因运行跨段而插入标签。

按本地时间将每天划分为六段，采用左闭右开区间：

| 时段 | 时间区间 |
| --- | --- |
| 第一段 | 00:00 ≤ 时间 < 04:00 |
| 第二段 | 04:00 ≤ 时间 < 08:00 |
| 第三段 | 08:00 ≤ 时间 < 12:00 |
| 第四段 | 12:00 ≤ 时间 < 16:00 |
| 第五段 | 16:00 ≤ 时间 < 20:00 |
| 第六段 | 20:00 ≤ 时间 < 次日 00:00 |

标签显示实际日期和时分，例如“今天 09:37”，不显示“08:00–12:00”。分段只决定标签何时出现，不把实际时间取整为分段起点。跨天后即使小时所属时段相同，也应显示新标签。没有消息的时段不创建空标签。

### 耗时

每个 turn 在用户第一条输入下方显示一份耗时，不给后续追加输入或中间输出重复添加。运行中实时显示，例如“已用时 12秒”；结束后固定最终值，例如“用时 45秒”。等待用户审批、回答问题或其他等待时间都计入，实时与最终口径一致。

中断或失败后保留已有的可确定耗时，状态沿用当前界面，不增加重复状态标记。耗时没有一分钟展示门槛。

### 数据缺失

缺少时间就不显示对应时间标签，缺少耗时就不显示对应耗时。两项独立判断，不显示“未知”占位，也不推测或补造数值。缺少开始时间时不能凭页面打开时间启动计时；终态缺少最终耗时时不能将尚未得到终止依据的实时值当成已确认的最终耗时。

## 用户故事

1. 作为聊天记录阅读者，我希望第一条消息前有时间标签，以便知道这段对话何时开始。
2. 作为聊天记录阅读者，我希望同一四小时时段的相邻 turn 不重复显示时间标签，以便保持内容紧凑。
3. 作为聊天记录阅读者，我希望跨四小时时段时出现新标签，以便辨认一天中的多段对话。
4. 作为聊天记录阅读者，我希望跨日期时出现新标签，以便区分不同日期的对话。
5. 作为聊天记录阅读者，我希望看到实际时分，以便知道对话的真实时间，而非时段起点。
6. 作为聊天记录阅读者，我希望标签位于 turn 分界处，以便不打断一轮对话内部的阅读。
7. 作为聊天记录阅读者，我希望每个 turn 都显示耗时，以便比较长短不同的轮次。
8. 作为聊天记录阅读者，我希望耗时位于用户第一条输入下方，以便快速找到对应请求的用时。
9. 作为等待回复的用户，我希望耗时实时增长，以便知道已经等待多久。
10. 作为等待回复的用户，我希望等待审批和回答问题的时间也计入，以便看到整轮经过时间。
11. 作为聊天记录阅读者，我希望 turn 结束后耗时停止变化，以便稳定查看结果。
12. 作为聊天记录阅读者，我希望中断和失败的轮次保留可确定耗时，以便了解未正常完成的请求已经花费多久。
13. 作为聊天记录阅读者，我希望沿用现有状态提示，以免同一结果在界面重复表达。
14. 作为历史记录阅读者，我希望缺失数据被如实省略，以免误把估算值当作真实时间。
15. 作为长对话阅读者，我希望新增标签不破坏分块渲染和折叠，以便保持滚动与流式输出性能。

## 实现决策

- 延续现有 thread、turn、transcript entry、turn fragment 和 context page 的领域划分。耗时属于 turn，不能因为一个 turn 被拆成多个 fragment 而重复显示。
- 时间信息沿用 app-server 的权威协议。当前生成的 `Turn` 已包含可空的 `startedAt`、`completedAt` 和 `durationMs`，前两者为 Unix 秒，后者为毫秒。GUI 类型别名直接指向该生成协议，不建立手工镜像契约。
- 当前 `TranscriptTurn` 模型没有时间字段，`upsertTranscriptTurn` 也未保存这些字段。实现需要在现有读取和转换链路中保留权威时间数据，并由展示层消费；本设计不据此宣称所有运行与历史路径已经提供完整值。
- 已完成 turn 的耗时使用权威最终值；进行中显示基于权威开始时间计算的经过时间。接收权威终态后停止更新，不能从组件挂载时刻或最近一次重连时刻重新计时。
- 保持现有 chunk 级 selector 与渲染边界，不为日期分组或计时拍平整个 turn 的 entries，不让时钟更新驱动全部历史内容重渲染。
- 标签属于非交互的语义文本，不新增审批、折叠或状态控件；使用 HeroUI 既有主题语义与弱化文本样式，保留现有状态组件。
- 本地化沿用现有体系。用户随后已确认格式：`今天 09:37`、`昨天 16:42`、`2026年9月10日 08:23`；耗时为 `已用时 8秒`、`已用时 2分钟 05秒`、`已用时 1小时 03分钟 09秒`，结束后将前缀替换为 `用时`。分钟后的秒、小时后的分钟和秒使用两位补零，不显示毫秒。
- 计划前需核验：首条用户消息实际时间与 `startedAt` 的关系，基线附加、实时事件、历史读取、重连及终态的数据填充，以及 context page 边界处如何确定前序 turn。不能将 turn 开始时间未经核验就称为消息发送时间。
- 对缺少时间的中间 turn、仅加载部分历史、没有用户输入的 turn，不虚构邻接时间或输入锚点；计划前根据实际数据与入口明确展示边界。

## 测试决策

优先复用现有 `CommittedTranscriptSurface` 的 Browser 测试入口，通过读取模型事实、共享 projection fixtures 和 builders 驱动界面，验证用户可见行为。现有消息展示测试已采用该入口，无需为本功能新建平行测试接口。以下为设计提出的验证范围，尚未执行或经用户单独确认测试入口。

- 首条标签、同段不重复、六个精确边界、跨日期、跨多个空时段，以及标签显示实际时分。
- 第一条用户输入下方只有一个耗时；追加输入、多个 fragment、已有中间输出折叠不导致重复。
- 运行中增长、等待期间继续增长、结束后冻结、中断与失败保留可确定值且不重复状态。
- 时间与耗时分别缺失、合法零耗时、历史附加和重连后的展示一致性。
- 日期与耗时格式在受支持语言环境中的可读性；窄屏下位置、换行和滚动行为。
- 不以内部函数调用次数或类型声明存在代替行为证据；性能验证针对时钟更新不得重渲染无关历史 chunk 的实际风险。
- Level 1：受影响的 Browser 回归和必要的纯时间边界验证。
- Level 2：当前真实运行时的无头验收，覆盖新 turn、完成、历史读取、等待与重连相关展示，以及窄屏布局。
- Level 3：本功能没有已识别的可见桌面依赖，当前不适用。

## 补充说明

当前 TUI 源码的实时计时会在审批和用户输入等模态交互期间暂停；结束时优先使用后端 `duration_ms`，后端按开始到结束的完整经过时间计算。TUI 最终 `Worked for` 文案另有工作分隔线条件和整秒数大于 60 的门槛。GUI 采用用户已确认的统一计时口径和逐 turn 展示规则，不继承这些差异。
