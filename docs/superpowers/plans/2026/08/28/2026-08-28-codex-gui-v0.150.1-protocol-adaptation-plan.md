## 唯一目标

按已确认设计修复 `rust-v0.150.1` 合入后 `codex-gui` 的 19 条 TypeScript build error：

- 四种新增 collaboration tool 在 started/terminal transcript policy 中逐项显式 ignore；
- `SubAgentActivityKind.completed` 形成独立追加的 `Completed <agent>` 活动；
- 四处合法 `SkillMetadata` fixture 显式提供 `pluginId: null`；
- 保留生成协议的单一权威、所有 `never` 穷尽检查和未来协议变化的编译期失败传播；
- 通过原始 `pnpm run build`、目标测试和完整 frontend 验证闭环。

## 已闭合事实与固定边界

- 权威 Rust schema、生成 TypeScript 和 GUI validators 当前一致；本计划不修改生成物。

  运行语义，而不是兼容 fallback。

## 描述式 DAG

计划确认后的初始 ready set 只有 `DOC-STATUS`。`DOC-COMMIT` 是所有实现动作的统一稳定前提；其后
`WT-TR` 与 `WT-FX` 同时 ready，但共享 Git worktree-admin lock，只能依次取得资源并创建。两者完成后
在 `WT-BARRIER` fan-in。预配屏障完成后，`TR-EDIT` 与 `FX-EDIT` 同时进入 ready set，并在独立
worktree、branch 和 index 中运行。两条分支各自形成提交后在 `INTEGRATE` fan-in，随后运行组合验证
和最终审查。

粗粒度关键路径：`DOCS → worktree 预配与 fan-in → TRANSCRIPT 较长分支 → INTEGRATE → FINAL-VERIFY →
FINAL-REVIEW`。SKILL_FIXTURES 不依赖 TRANSCRIPT；只有共享主 repo worktree metadata 的预配阶段、
最终 dev integration 和最终验证需要汇合。

TRANSCRIPT 与 SKILL_FIXTURES 的 edit/generate/format 可真实并行。两个 worktree 的 `node_modules`
symlink 指向同一物理目录，TypeScript/Vitest project 又把 `.tsbuildinfo` 写入共享
`node_modules/.vite/vitest/**`；TypeScript project 另把 `.tsbuildinfo` 写入共享 `node_modules/.tmp`。
因此分支 Vitest 节点独占共享 Vitest cache，最终 CI、Browser Mode 与 build 节点同时声明实际写入的
共享 Vitest/TypeScript cache。分支只运行目标 unit 测试；完整 type-check、Browser Mode、CI 与 build
在 cherry-pick fan-in 后串行执行。资源锁只延迟冲突节点，不制造 taskBoundary 间的源码硬依赖。

- `replanTriggers`：提交边界、最终 tree、验证证据或禁止写集合不一致
- `authorizationGate`：当前 `pending`；计划确认后激活只读最终审查

## Ready set、资源与失败传播

- 初始 ready set：`DOC-STATUS`。
- `DOC-COMMIT` 后：`WT-TR` 与 `WT-FX` 同时 ready；共享 worktree-admin lock 使脚本依次运行。
- `WT-TR` 与 `WT-FX` 完成后：`WT-BARRIER` ready。
- `WT-BARRIER` 后：`TR-EDIT` 与 `FX-EDIT` 同时 ready，必须在容量与锁允许时同时启动。
- 两分支没有源码 writeSet 交集；共享 `node_modules` 只读。full-directory formatter 作用于各自独立
  物理 worktree，不形成交叉 write lock。
- `TR-VERIFY` 与 `FX-VERIFY` 的 Vitest 命令共享 physical `node_modules/.vite/vitest/**` write lock；未拿到
  锁的节点保持 ready，不伪造 hard predecessor。两个分支不运行 type-check、Browser 或 build。
- 任一实现分支失败只暂停该分支及 `INTEGRATE`/最终后继；另一分支继续耗尽已授权 ready/running
  节点并形成自己的稳定 commit，除非失败推翻共享协议或工具链前提。
- `INTEGRATE` 只有在两个 task commits 均稳定后 ready；`FINAL-VERIFY` 只读取集成后的 stable tree。

本计划没有有效 `deferralEvidence`。所有 ready 节点的延迟只能来自容量、尚未激活的授权门禁或本文
声明的 canonical resource lock。

## 修正与范围变化

- 未提交 candidate 的计划内失败：在原 taskBoundary 插入最小 edit/format/verification 节点，保持
  原 writeSet 和提交边界。
- 已形成 commit 后发现计划内问题：创建独立修正 commit，禁止 amend；只重新运行受影响验证和最终
  组合验证。
