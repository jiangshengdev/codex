# Lingui Catalog Workflow

This skill governs field classification, generated-artifact boundaries, complete diff review, and repeat-extraction stability for Codex GUI Lingui catalogs. It does not authorize command execution or catalog modifications, and does not duplicate rules for work stages, plan documents, authorization, or execution graphs.

## Boundaries with Other Lingui Skills

- Use `$lingui-best-practices` for message macros, plurals, placeholders, locales, and general extraction practices.
- Use `$enhanced-message-context` to determine which messages need translator comments and whether those comments are accurate.
- Use this skill to determine the meaning of each catalog field after extraction, which changes may be generated metadata only, whether the complete catalog boundary is preserved, and whether the generation chain is stable.

These skills may apply together. Lingui conventions do not replace field-level diff review.

## Verify Authoritative Project Entrypoints and Boundaries First

Before running or planning extraction, verify the following against current project configuration, package scripts, applicable `AGENTS.md` files, and established project entrypoints:

- The authoritative extraction entrypoint and its working directory.
- Lingui configuration, source include/exclude rules, and source locale.
- The locale set, catalog path templates, and complete set of catalog files this entrypoint will write.
- Which catalog content permits manually supplied translations.

Do not invent or bypass project entrypoints, or infer the complete catalog set from historical commands, expected diffs, or currently modified files. Both planning and execution must use the verified complete file set as the generated-artifact boundary. Each field within that boundary still requires acceptance review; do not approve the entire set without review.

## PO Field Classification

### `#:` source references

`#:` is location metadata generated by extraction from current source, not message identity or translation content. Additions, deletions, merges, or line-number changes qualify as metadata closure only when all of the following hold:

- References point to the correct source allowed by current configuration and agree with the corresponding message mapping.
- Changes remain within the verified catalog file set.
- The same input reproduces the result deterministically, and the result remains stable when the same authoritative entrypoint is run again.
- No unplanned changes to `msgid`, `msgstr`, translator-comment semantics, or status accompany them.

Incorrect message mappings, unexpectedly missing source, source outside the boundary, or continued drift across repeated extraction are not metadata-only changes.

### `#.` extracted translator comments

`#.` comes from translator context in source. Extraction maintains it, but it affects translation decisions; do not accept it as location metadata only merely because it is a comment.

- For planned new or modified messages, verify that comments accurately explain UI location, purpose, ambiguity, and placeholders, and confirm that extraction preserves them on a subsequent run.
- For existing messages, separately review any comment addition, deletion, or semantic change that current source cannot explain.
- `$enhanced-message-context` determines comment quality and necessity; this skill verifies only catalog projection and stability.

### `msgid`

`msgid` represents message identity and source-language semantics, not metadata. Additions, modifications, merges, deletions, or unexpected obsolete entries must trace back to planned source-message changes. Any unplanned drift requires pausing subsequent work on the current catalogs.

### `msgstr`

`msgstr` is user-visible translation, not metadata. Extraction must preserve existing nonempty translations. Translations for new messages must remain within the locales and manual-translation boundaries allowed by the plan. Pause if existing translations are emptied, rewritten, or mismatched, if placeholder or ICU structure changes, or if translations in nontarget locales change.

### fuzzy and obsolete

fuzzy/obsolete status affects translation availability and catalog completeness; it is not metadata only. New fuzzy entries, valid translations becoming fuzzy, unexpected obsolete entries, obsolete entries becoming active again, or cleanup-policy changes permit continuation only when the confirmed objective explicitly includes that status change. Otherwise, pause.

## Catalog Verification Loop

1. Perform the first extraction through the verified authoritative entrypoint.
2. Review the complete catalog diff, not only hunks near expected messages. Classify changes by `#:`, `#.`, `msgid`, `msgstr`, fuzzy/obsolete status, and file boundary, and record their source or generation basis.
3. Supply manual translations only within the scope allowed by the plan. Do not manually restore old line numbers or references owned by extraction to shape the diff.
4. Run extraction again through the same entrypoint and confirm that all catalogs are stable: no new structural diffs, repeated reference movement, lost comments or manual translations, new status drift, or expanded catalog boundary.
5. Provide field-level diff conclusions, the complete file set, and repeat-extraction stability results as closure evidence for the current work-stage assessment.

Expected hunks, old source line numbers, old source-reference sets, and diff line counts are not authoritative output allowlists. A "generated file" label does not exempt a file from review. A large number of changes does not establish an error, and generation does not establish correctness.

## Conditions Requiring Subsequent Catalog Work to Stop

If any field fails the classification conditions above or repeat extraction is unstable, including overwriting comments, translations, or other manual content, stop subsequent catalog work. Do not classify these failures as metadata closure. Also stop in the following cases:

- New locales, catalogs, directories, formats, configuration outputs, or other files outside the boundary.
- An unclear extraction entrypoint, input, configuration, tool provenance, or complete output set.
- Accepting the diff would require skipping stability verification, weakening checks, changing the baseline, or manually preserving old metadata that the generator has normalized.

Report the specific fields, files, provenance evidence, and affected subsequent catalog work. `$managing-work-stages` determines whether to update the plan or return to other gates.
