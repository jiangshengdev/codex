# codex-gui

## 仓库格式化范围

- 当且仅当任务修改了至少一个由当前 `scripts/format.py` 管理的文件时，才运行仓库级 `just fmt`；即使任务同时修改了不受其管理的文件，也适用此规则。目前的管理范围包括仓库 Justfile、由 `cargo fmt` 处理的 Rust 文件、由 buildifier 处理的 Bazel/Starlark 文件，以及 `sdk/python` 和 `scripts` 下的 Python 文件；如果这些范围发生变化，以当前实现为准。
- 仅修改不受其管理的路径，例如 `codex-gui/**` 下的前端文件、`docs/**` 或 Markdown 文件，不触发 `just fmt`。纯前端格式化使用 `codex-gui/package.json` 中适用的脚本。

使用 `$codex-gui-toolchain` 选择并运行前端格式化工具、package scripts 和验证入口。

## Skill 路由

- 对普通的 `GUI 启动`、`启动 GUI`、`/gui` 或仅请求 URL 的任务，使用 `$gui-launch`。真实 GUI 调试与验收按下文规则路由。
- HeroUI v3 的文档、包和 API 细节使用 `$heroui-react`；Redux Toolkit 的文档、API 和架构规则使用 `$redux-toolkit`。
- 当范围涉及 Lingui 消息提取、目录文件差异、目录文件中的翻译修改或提取稳定性时，使用 `$lingui-catalog-workflow`。

## 前端工程约束

- 在 `codex-gui/**` 中，Rust 模块代码行数（LoC）、变更行数，以及 TypeScript、TSX 或 JavaScript 文件长度衡量的是不同对象。不得将它们相互换算，也不得仅凭其中任何一项作为硬性停止条件。
- 根据职责、状态所有权、耦合、函数作用域、可测试性和可审查性评估前端结构。公共接口小或文件短，不足以成为将多种操作或多类状态转换集中到一个函数、工厂或闭包中的理由。
- 不得仅为满足长度指标而拆分、压缩、削弱或删除前端测试。只有对于稳定、用户可见且存在具体回归风险的产品约束，才添加样式测试。
- 有类型约束的进程内边界，默认应依靠类型、所有权、复制和封装。引入运行时防御，必须记录这些边界无法应对的行为主体、受支持路径及失败影响；除非运行时抵御能力本身就是产品或安全要求，否则不得通过测试固定防御机制。
- 当某个指标、历史实现或某种做法“更安全”的说法将决定停止、拆分、防御机制或测试范围时，使用 `$evaluating-engineering-constraints`。

## 权威契约不变量

- 将 `codex-gui` 使用的每个跨模块契约或生成契约视为只有一个权威来源。直接使用其权威产物，或通过机械方式从中派生。
- 保留来自权威来源的失败传播。影响所引用字段、类型或变体的不兼容上游变更，必须在生成、类型检查或构建阶段失败。
- 不得用运行时拒绝、静默兼容或由消费方拥有的回退行为，替代编译期契约失败。
- 不得在消费方拥有的 DTO、接口、类型别名、字面量联合、字段列表、schema、验证器、解析器、测试夹具或兼容适配器中，手工复制权威契约。
- 不得先将权威类型擦除为 `unknown`、宽泛的 record、宽泛的泛型或通过断言跨越类型边界，再用消费方自己的声明或检查重建契约。
- 表达权威契约的运行时验证，必须从同一权威来源机械生成。如果不存在生成的运行时验证器，不得手工重建契约。
- 允许使用 `Pick`、`Omit`、`Extract`、索引访问及其他类型系统变换等机械关联的派生方式，前提是保留对权威类型的依赖。
- 仅当由前端拥有的领域模型表达独立的前端语义，而非对契约进行重命名、收窄或复制时，才允许使用。其转换边界必须接受权威类型，并保留对变体的编译期穷尽性检查。
- 对本地未使用的兼容性上游新增内容，无须人为制造失败。不得抑制影响现有消费方的真实不兼容问题。
- 设计、计划和审查必须明确受影响契约的权威来源及派生路径。如果提案复制了契约或中断了编译期失败传播，必须停止，并在实现前重新设计。

## 前端证据闭包

- 对高风险 GUI 变更，读取并应用 `$managing-work-stages` 的 `references/vertical-impact-closure.md`，覆盖所有适用的入口、导出、消费方、生命周期、恢复和验证链路。范围应包括真实生产入口和挂载入口、动态注册及其间接消费方、DOM/ARIA 选择器、测试夹具，以及 Browser Mode/E2E 验证。
- 对涉及契约的变更，应用上面的权威契约不变量，并追踪权威 TypeScript 契约、运行时验证器、schema 输入、生成产物和生成的测试夹具。

## GUI 验收等级

- Level 1 是在隔离环境或测试环境中进行的自动化回归。它覆盖浏览器测试、DOM 与事件断言、无障碍、截图和几何检查，但在真实 Codex 集成受到影响时，不能替代对该集成的验证。
- Level 2 是针对当前 Codex 运行时、目标路由和所需真实状态进行的无头真实应用验收。用于验证受影响的布局和响应式几何；浮层、展开方向、遮挡、裁剪和滚动；指针与键盘交互及焦点流转；默认、悬停、禁用、无效和 `focus-visible` 等组件状态；以及其他无须可见桌面窗口即可观察的集成行为。
- Level 3 是可见桌面验收，仅适用于结果本身依赖操作系统窗口、桌面或跨应用焦点、DevTools、系统输入法 UI，或其他无头自动化无法证明的行为。将其路由到 `$debug-responsive-gui`，并在打开或复用任何可见浏览器窗口或桌面窗口前，针对可见窗口影响取得单独明确授权。
- 计划和最终报告必须分别记录各等级的适用性和结果。当所有适用的 Level 1 和 Level 2 场景均通过，且 Level 3 不适用时，可以报告 GUI 变更已完成全面验证。当 Level 3 适用但未执行时，报告 `可见桌面验收未执行`，不得声称已完全完成或全面验证。
- 纯类型变更、生成产物、不可见的内部逻辑，以及不产生上述任何影响的前端变更，不会仅因位于 `codex-gui/**` 下而触发 GUI 验收。

## HeroUI 设计系统不变量

- `codex-gui` 中的 UI 设计、实现计划和代码变更，默认应使用 HeroUI v3 作为组件系统。在创建自定义 HTML/CSS 控件之前，优先使用 `@heroui/react` 组件实现交互控件、浮层、反馈、布局基础组件和排版。
- 根据语义意图而非视觉外观选择组件变体，并在语义上区分主要操作、备选操作、取消或关闭操作、破坏性操作和关键操作。
- 使用 surface、background、separator 和 field token 表达层级与状态，避免临时采用强烈的颜色变化。
- UI 工作的实现计划必须列出拟使用的 HeroUI 组件、变体和语义 token。如果计划选择自定义标记或样式而非 HeroUI，必须说明理由，例如缺少对应组件、协议驱动的标记、Markdown 语义输出或对话记录性能约束。
- 当 `main`、`section`、`article`、Markdown AST 输出标签、滚动哨兵或对话记录分块边界等语义文档元素或布局元素承载无障碍、内容或性能含义时，这些规则不要求替换它们。

## 前端性能不变量

- 对话记录渲染必须保留分块级性能边界。除非设计明确论证成本有界，否则不得在渲染路径、选择器或展示分组中，将一个轮次的所有条目展平。
- 分组、折叠、展开或标签等纯 UI 功能，不得将分块的对话记录数据重新转换为完整轮次的数组，也不得在折叠时渲染所有隐藏条目。
- 对话记录的高频执行路径优先使用分块级选择器和分块级 React 组件。未变化的分块应保持选择器结果稳定，并避免在新条目追加到后续分块时重新渲染旧条目。
- 性能验证必须针对可衡量的风险。回归覆盖应体现稳定约束；仅存在某个测试或 issue 记录，并不能证明渲染路径性能良好。

## 过滤测试执行

- 本地开发和验证默认运行经过过滤的前端测试。根据变更行为、其消费方及相关回归覆盖选择测试文件；不得在每次编辑后运行完整的单元测试、Browser、E2E 或 `ci` 套件。
- 通过 `$codex-gui-toolchain` 规定的 fnm 环境，向仓库自有脚本传入明确的测试文件路径。定向定位问题时，可额外使用 Vitest `-t`，以正则表达式匹配完整测试名称（包括 `describe` 名称）。完成行为变更前，应移除名称过滤，运行受影响的测试文件，以保留相邻行为的回归覆盖。
- 在 `codex-gui` 目录中，单元测试使用 `/opt/homebrew/bin/fnm exec --using-file pnpm run test:unit <test-file>`。Browser 测试使用 `/opt/homebrew/bin/fnm exec --using-file pnpm run test:browser:parallel --run <test-file>`；`src/__tests__/sequential/**` 下的文件则使用 `test:browser:sequential`。不得在脚本名与参数之间额外插入 `--`。不得向聚合脚本 `test:browser` 传递过滤条件，应直接选择适用的子脚本。
- 核对实际收集的文件、执行的测试数量及跳过的测试。没有匹配测试不算通过；若意外收集了全套测试，必须先修正过滤条件再继续。报告实际验证范围。
- 只有受影响的依赖或共享初始化逻辑、配置需要，失败或新证据表明有必要，或用户、适用的强制门禁明确要求时，才扩大测试范围。说明原因，并选择覆盖该影响的最小范围。相关检查通过后，没有新变更或尚未解决的证据问题，不得重复或扩大测试。
- 过滤仅选择执行范围，不授权删除覆盖、添加 `.only` 或 `.skip`、削弱断言、抑制失败、减少必需的浏览器覆盖或修改 CI 门禁。必需的类型检查、lint、生成检查及适用的 GUI 验收仍遵循现有规则。

## 测试夹具不变量

- 对前端测试中的合法投影协议载荷，优先使用 `src/features/projection/__tests__/projectionFixtures.ts` 和 `src/features/projection/__tests__/projectionTestBuilders.ts` 中的共享夹具与构建器，而非手写协议对象。
- 当测试需要新的合法投影载荷变体时，先扩展共享投影测试构建器接口，不要在测试文件中添加临时的本地构建器，也不要手工展开 `ThreadProjectionAttachResponse`、`ThreadProjectionEventNotification`、`ThreadRuntimeRecord` 或 `Turn` 的结构。
- 格式错误的载荷、JSON-RPC 信封、出站请求断言，以及 UI/选择器的预期状态对象，应在负责相应断言的测试中明确写出。
